# CLAUDE.md

## Working style

When a request is ambiguous, ask clarifying questions **one at a time** before proceeding. Do not ask several questions at once.

Be concise: short responses, no filler, no restating what was just done.

Do not re-read a file that was already read in the current session unless it may have changed.

When there are multiple valid approaches to a request, present the options and trade-offs first and wait for a choice before starting implementation.

## Git workflow

- Make commits atomic: each commit should represent one logical change and pass tests on its own.
- Write descriptive commit messages that explain the _why_, not just the _what_. Use a short subject line and a body when context is needed.
- If a commit fixes a bug reported in a GitHub issue, include a closing keyword (e.g. `Fixes #N` / `Closes #N`) in the commit body. If the issue number isn't known, ask before committing rather than omitting it.
- Only create a dedicated branch and close it with a merge commit when a feature's development required multiple commits; otherwise commit directly to `main`.

## Commands

```bash
npm install                      # install all workspace dependencies
npm run build                    # build all packages (core → react → vue → solid → vanilla; order matters)
npm run dev:react|vue|solid|vanilla # start a demo dev server
npm run test                     # run tests for all packages
npm run test -w packages/X       # run tests for one package (core | react | vue | solid | vanilla)
npm run test:watch -w packages/X # watch mode for one package
npm run type-check               # type-check all packages
npm run build -w packages/X      # build one package

```

## Development workflow

After implementing any new feature:

1. Review existing tests to see if they need updating; add new tests if the feature isn't covered.
2. Run `npm run test` to verify nothing regressed.
3. Run `npm run type-check` to verify no type errors.
4. Update the demos (`demo/react`, `demo/vue`, `demo/solid`, and `demo/vanilla`) to showcase the new feature if applicable.
5. Update any affected Markdown files (CLAUDE.md, READMEs).

## Architecture

This is an **npm workspaces monorepo** with five publishable packages and four demo apps:

```
packages/
  core/    — @vates/data-table-core    (pure TS, zero dependencies)
  react/   — @vates/data-table-react   (peer dep: react)
  vue/     — @vates/data-table-vue     (peer dep: vue)
  solid/   — @vates/data-table-solid   (peer dep: solid-js)
  vanilla/ — @vates/data-table-vanilla (no framework dependency; wraps @vates/data-table-solid)
demo/
  react/   — Vite app consuming @vates/data-table-react
  vue/     — Vite app consuming @vates/data-table-vue
  solid/   — Vite app consuming @vates/data-table-solid
  vanilla/ — Vite app consuming @vates/data-table-vanilla
```

### Core package (`packages/core`)

All stateless logic lives here:

- **`types.ts`** — shared interfaces: `ColumnDefBase<TRow>`, `AggregateType`, `SortEntry`, `RangeFilter`, `DataTableLabels`, `DEFAULT_LABELS` (English default strings)
- **`logic.ts`** — pure functions: `getColumnValue`, `processData`, `searchData`, `groupData`, `sortWithinGroups`, `computeStringValues`, `computeStringValueCounts`, `computeAggregate`, `paginateData`, `computeTotalPages`, `toggleSort`, `replaceSort`, `appendOrToggleSort`, `cycleFilterValue`, `toggleGroupBy`, `toggleCollapse`, `getOrderedColumns`, `reconcileVisibleColumns`, `reorderColumn`, `moveColumnBy`, `getSortIcon`, `getSortIndex`, `countActiveFilters`
- **`locales.ts`** — built-in locale objects: `LABELS_EN`, `LABELS_FR`, `LABELS_ES`, `LABELS_DE`, `LABELS_PT`
- **`theme.ts`** — `LIGHT_THEME`/`DARK_THEME`/`renderThemeCss()`, consumed only by the Solid adapter (see "Solid package"'s `styles.ts`) since React/Vue theme via inline styles/scoped CSS instead, and vanilla gets it transitively by bundling `@vates/data-table-solid`. Not re-exported from core's main `index.ts` barrel — React/Vue consumers importing `@vates/data-table-core` directly would otherwise see theme APIs with no relevance to them. Reachable via its own `@vates/data-table-core/theme` sub-path export, same pattern as `/locales`.

The internal `asRecord(row: object): Record<string, unknown>` helper exists because the generic constraint is `TRow extends object` (not `Record<string, unknown>`) — TypeScript interfaces lack index signatures so the wider constraint is needed, and `asRecord` lets internal logic access arbitrary keys.

### React package (`packages/react`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase` with `render?` and `renderFilterLabel?` (render props)
- **`useTableState.ts`** — wraps core logic with `useState`/`useMemo`; signature `useTableState(data, columns, options?)` where `options` is `UseTableStateOptions` (`{ defaultVisibleColumns?, labels?, defaultPageSize?, defaultGroupsCollapsed?, getRowId? }`) — a single options object rather than 4 positional params, both for parity with Vue's shape below and because a positional-param footgun is exactly the kind of thing this library tries not to have: a consumer must not need to remember argument order, or pass `undefined, undefined, undefined` just to reach the option they actually want. Returns a `TableState<TRow>` namespaced by concern — see "Namespaced TableState" above (React is migrated to this shape; `DataTableView.tsx`'s one destructuring block aliases each namespace's fields back to the same bare local names the rest of the ~2600-line component already used, so nothing past that block needed to change). Also exports `TableState<TRow>` (`ReturnType<typeof useTableState<TRow>>`) and `UseTableStateOptions`.
- **`DataTableView.tsx`** — the actual render layer; takes a `TableState<TRow>` (the `useTableState` return value) as a `table` prop instead of calling the hook itself
- **`DataTable.tsx`** — thin wrapper: calls `useTableState` internally and renders `<DataTableView table={table} .../>`

Cell rendering priority: `col.render(value, row)` → `col.format(value)` → `String(value)`. Group headers use the same `cellValue()` function so custom renders apply there too.

### Vue package (`packages/vue`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase` (no render props; customization is via slots)
- **`useTableState.ts`** — same signature shape as React: `useTableState(data, columns, options?)` where `options` is `UseTableStateOptions` (`{ defaultVisibleColumns?, labels?, defaultPageSize?, defaultGroupsCollapsed?, getRowId? }`); uses `ref`/`computed` and accepts `MaybeRefOrGetter` for reactive inputs. Returns a `TableState<TRow>` namespaced by concern like React/Solid — see "Namespaced TableState" above; `DataTableView.vue`'s one destructuring block aliases each namespace's fields back to the same bare local names its script and template already used, so nothing past that block needed to change. Also exports `TableState<TRow>` (`ReturnType<typeof useTableState<TRow>>`) and `UseTableStateOptions`
- **`DataTableView.vue`** — the actual render layer; uses `<script setup lang="ts" generic="TRow extends object">` and takes a `TableState<TRow>` as a `table` prop instead of calling `useTableState` itself
- **`DataTable.vue`** — thin wrapper: calls `useTableState` internally, renders `<DataTableView :table="table" .../>`, and forwards its own slots straight through. Also the one adapter with `v-model` sugar: `page`/`searchQuery` props + matching `update:page`/`update:searchQuery` emits, wired via two `watch` pairs (prop → `table.pagination.setPage`/`table.search.setQuery`, and `table.pagination.page`/`table.search.query` → emit, both `{ immediate: true }` so a bound v-model reflects the real initial value at mount, not just later changes). Scoped to `<DataTable>` only — a direct `useTableState` + `<DataTableView>` consumer already has `table.pagination.page`/`table.search.query` refs to bind however they like. `selection` deliberately has no `v-model:selection` alongside it: `selectionChange`/`onSelectionChange` already covers observing it, and a `v-model` counterpart would just be a second, redundant mechanism for the same event — "set it from outside" is also an awkward fit for a `Set<TRow>`-by-object-identity model (the caller would need to pass the exact same row references already in `data`).
- **`components/Dropdown.vue`** — self-manages open/close state and exposes it to `#trigger` slot

Vue customization uses **scoped slots** instead of render props:

- `#cell-{key}` — custom table cell; slot scope: `{ value: unknown, row: TRow }`
- `#filter-{key}` — custom filter dropdown label; slot scope: `{ value: string }`
- `#group-{key}` — custom group header value; slot scope: `{ value: unknown, row: TRow }`

### Solid package (`packages/solid`)

**A real, standalone Solid adapter** — `solid-js` is a `peerDependency` here (never bundled), so a project already using Solid shares its own `solid-js` instance instead of a second, non-interoperable copy. This package was split out of `packages/vanilla` (which now just wraps it — see below); the code and reasoning are unchanged by the split. Built with Solid + TSX (not a hand-rolled `innerHTML`-rebuilding implementation) because Solid's setup-once + fine-grained-signal model matches a closure-based architecture better than React/Preact's re-render-the-world model, and eliminates whole categories of hand-maintained code (manual focus/scroll restore, a render-placeholder-and-patch mechanism, an `input`-vs-`change` event split for drag gestures).

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase<TRow>` with `render?: (value, row) => Node` and `renderFilterLabel?: (value: string) => Node` (mirrors React's `renderFilterLabel`, adapted to Solid's Node-returning convention; same `type: 'date'` caveat — see "Filter dropdown" below). `packages/vanilla` mirrors both fields on its own independently-declared `ColumnDef` and gets `renderFilterLabel` for free through the same bundled `FilterDropdown.tsx`.
- **`styles.ts`** — the CSS string + `injectStyles()`, called automatically by `DataTableView` on mount
- **`createTableState.ts`** — internal state/action logic mirrors react/vue's `useTableState` field-for-field (`createSignal`/`createMemo` instead of `useState`/`useMemo`), but the _returned object_ is namespaced (see "Namespaced TableState" below) rather than the flat shape react/vue still return. `data`/`columns` accept a plain value or an `Accessor`; an accessor gets a `createRenderEffect` wiring it to `setData`/`columns.set` for the table's lifetime. `columns.set` reconciles `columns.visible` against the new key set (see "Reconciling `visibleCols`" below). The 3rd `options` argument accepts a plain `CreateTableStateOptions` object or an `Accessor` returning one — unlike `data`/`columns`, individual option fields can't each independently be "value or Accessor" (`getRowId` is itself a function, indistinguishable at runtime from an Accessor returning one), so reactivity is lifted to the whole options object instead, mirroring how Vue's `useTableState` treats its own whole `options` argument as one `MaybeRefOrGetter`. This makes `labels`/`defaultGroupsCollapsed`/`getRowId` live (a later change takes effect with no need to recreate the table), matching React/Vue, where these three were already live — Solid was the one adapter that froze them at construction until this was fixed. `table.labels` is accordingly a `createMemo` (call it as `table.labels()`), not a plain object — the one adapter where this field isn't a plain object, since it must itself react to a changed `labels` option. `defaultVisibleColumns`/`defaultPageSize` stay seed-only (read once, untracked) regardless of whether `options` is reactive, matching every adapter's frozen behavior for those two.
- **`DataTableView.tsx`** — composes the toolbar, `ActiveBar`, `TableBody`, and `Pagination`; takes a `table: TableState<TRow>` prop instead of calling `createTableState` itself.
- **`components/`** — `Dropdown.tsx`, `SearchBox.tsx`, `ColumnsDropdown.tsx`, `SortDropdown.tsx`, `GroupDropdown.tsx`, `FilterDropdown.tsx`, `RangeSlider.tsx`, `DateTreeItem.tsx`, `ActiveBar.tsx`, `TableBody.tsx`, `Pagination.tsx`, `dragReorder.ts`, `checkboxSync.ts` (see below).
- **`DataTable.tsx`** — thin wrapper: builds `createTableState` internally (passing `data`/`columns` as accessors) and renders `<DataTableView>`.
- **`index.ts`** — re-exports `createTableState`/`DataTableView`/`DataTable`/`ColumnDef`, core's locales/`DataTableLabels`, and the grouping/sort helpers. `injectStyles` is deliberately not re-exported (called automatically).

Known, deliberate simplifications vs. React/Vue: the flat filter checklist isn't virtualized yet; roving Up/Down/Home/End nav inside an open dropdown, dropdown focus-on-open, and Sort/Group's activate/remove focus retention aren't implemented; the Filter dropdown's Left/Right pane-crossing nav isn't implemented; `TableBody`'s Home/End only jump within the current page. None of this affects mouse/touch interaction.

`checkboxSync.ts` exists for one specific Solid + native-checkbox race: a tri-state checkbox must call `e.preventDefault()` to stay controlled, but a checkbox's native "canceled activation steps" run _after_ the click finishes dispatching, silently reverting `.checked` a moment after Solid's own synchronous write. `applyCheckboxState` is the plain synchronous setter used everywhere; `deferCheckboxCorrection` (called from the click handler right after the state change) re-applies the correct state from a microtask, scoped to just the clicked element so other update paths aren't penalized with a one-tick-late DOM read.

Most "vanilla does X via `data-action`/`data-focus-key`" asides elsewhere in this file actually describe code that now lives in `packages/solid`, not `packages/vanilla` — `packages/vanilla` today is only the thin wrapper described in its own section below.

Full rationale — the accessor/effect mechanism, every deferred-feature detail, and more — lives in [docs/solid-package.md](docs/solid-package.md).

### Namespaced TableState

`useTableState`/`createTableState`'s returned object used to be one flat ~45-field object — every raw state signal, every derived value, and every action as a sibling top-level property, with no grouping. That was hard to scan (autocomplete on `table.` is a wall of ~45 entries) and made related concerns (e.g. `sorts`/`toggleSort`/`replaceSort`/`moveSortBy`/`getSortIcon`, all "sort") look unrelated to each other purely because they didn't share a prefix consistently.

The shape is now namespaced by concern — one sub-object per feature area, each holding that area's own state and actions with the redundant prefix dropped (`toggleSort` → `sort.toggle`, `moveGroupBy` → `group.moveBy`):

- **`columns`** — `{ visible, active, ordered, toggleVisibility, move, moveBy }`, plus Solid-only `list`/`set` (the raw full column array/setter — React/Vue never had this on `TableState` at all, since they get fresh `columns` as a constructor argument instead)
- **`sort`** — `{ entries, toggle, replace, appendOrToggle, remove, toggleDir, move, moveBy, clear, icon, index }`
- **`filter`** — `{ include, exclude, ranges, activeCount, valueMap, toggleAll, setValues, cycleValue, clearExcludeValues, setRange, clearColumn, clear }`
- **`group`** — `{ by, collapsed, defaultCollapsed, toggle, remove, move, moveBy, toggleCollapse, clear }`
- **`selection`** — `{ all, rows, toggle, toggleAll, clear }`, plus Solid/vanilla-only `setAll` (was `setSelectionRows` — replaces the selection outright by reference, backing vanilla's imperative `setSelection(rows)`, which has no reactive value of its own to mutate directly)
- **`pagination`** — `{ page, pageSize, numPages, setPage, setPageSize }`. `page` is always the already-clamped value (`Math.min(rawPage, numPages)`) — `numPages` can shrink (a group collapsing, data changing) without any `setPage` call, and exposing the raw, pre-clamp state would leave the page label/prev/first-page button state stale until the next explicit navigation. `setPage` still clamps against `numPages` at set time the same as before; only what's read back changed. All three of React/Vue/Solid derive `page` this way (`clampedPage` was already computed internally for `pagedData`/`groupedData` in every adapter — only the public field was still the raw one). Solid's `Pagination.tsx` used to re-derive this itself locally since the underlying fix lived only in the component, not `createTableState`; that workaround is gone now that the table-level `page` is already clamped.
- **`search`** — `{ query, setQuery }`

Stays top-level — these are the pipeline's actual output, not a "concern" of their own, and nesting the single most commonly accessed values under one more property hop would hurt the common case for no benefit: `data`/`setData` (Solid only), `processedData`, `pagedData`, `groupedData`, `visibleItems`, `labels` (was `L`), `getViewState`/`setViewState` (cross-cutting; `persistence.ts` in every adapter reaches these and nothing else, so this split leaves it completely untouched), `clearAll` (also cross-cutting).

`filter` keeps all six of its mutators despite the temptation to trim it further (e.g. one `setColumn(key, patch)` replacing all six) — `clearExcludeValues` looked like it was purely `toggleAll`'s own internal helper for clearing stale exclusions before a "select all", but `FilterDropdown`'s shift-click checklist range-select calls it directly too, so it's genuinely part of the built-in UI's own needs, not just an implementation detail safe to fold away.

This reduces top-level members from ~45 to 15 (7 namespace objects + 8 top-level entries), a real cut in perceived surface area, at the cost of being a breaking change — every field/action moved. Pre-1.0 (core is at 0.8.0, Solid at 0.1.0), so this shipped as a hard cut with no flat-property compatibility shim, rather than a getter-based deprecation bridge that would add real runtime complexity for a temporary bridge undermining the entire point of the change. **All three of Solid, React, and Vue are migrated to this shape** (see their own package sections above) — `TableState<TRow>` is consistent across every adapter (only `@vates/data-table-vanilla`'s own `DataTableInstance` differs, since it always had its own distinct public method names rather than exposing `TableState` directly, and needed no changes here).

### Vanilla package (`packages/vanilla`)

**A thin wrapper around `@vates/data-table-solid`** (see that section above for everything about the actual UI/state implementation — `createTableState`, `DataTableView`, every `components/*` file, and the Solid-specific reasoning behind them). This package's own `src/` is now just:

- **`types.ts`** — re-exports `ColumnDef` from `@vates/data-table-solid`, plus `DataTableOptions`/`DataTableInstance` (the imperative wrapper's own option/instance shapes — unchanged from before the split)
- **`index.tsx`** — `createDataTable(container, options)`: builds a `createTableState` (from `@vates/data-table-solid`) inside a `createRoot`, mounts `<DataTableView>` via `solid-js/web`'s `render()`, and returns the public instance object backed by that state (`onViewChange` is a `createEffect`/`on(..., { defer: true })` reading `table.getViewState()`, skipping the initial mount so it only fires from an actual subsequent change)
- **`persistence.ts`** — `persistViewToLocalStorage`/`syncViewToUrl`/`resetView` (see "View persistence" below); unaffected by the split, since it only ever talked to the imperative `ViewStateApi` shape (`getViewState`/`setViewState`/`onViewChange`), not to Solid internals directly

Both `solid-js` and `@vates/data-table-solid` are bundled into this package's own `dist/` as internal implementation details — see `vite.config.ts`'s `rollupOptions.external` (only `@vates/data-table-core` is external) and `package.json` (both are `devDependencies`, never runtime ones). The public API (`createDataTable(container, options)` returning `{ setData, setColumns, getViewState, setViewState, onViewChange, onSelectionChange, getSelection, setSelection, clearSelection, setRowKey, setSelectable, setOnRowClick, setLabels, setDefaultGroupsCollapsed, setGetRowId, destroy }`) is otherwise unchanged by the split — every `createDataTable.*.test.tsx` test still exercises it end-to-end exactly as before, now as a regression check that the wrapper still delegates correctly.

`onSelectionChange(cb): () => void` mirrors `onViewChange`'s subscribe/unsubscribe shape (a `Set` of listeners, seeded with the constructor's `onSelectionChange` option if given) — a listener can now be attached after construction too, not just at construction time.

`rowKey`/`selectable`/`onRowClick`/`labels`/`defaultGroupsCollapsed`/`getRowId` are each backed by their own `createSignal` inside the wrapper, with a matching `setXxx` method to change them after construction — `setRowKey`/`setSelectable`/`setOnRowClick` work because `DataTableView`/`TableBody` already read those props lazily (a signal call passed as a JSX prop stays live, the same mechanism `table={table}` already relies on); `setLabels`/`setDefaultGroupsCollapsed`/`setGetRowId` work because `createTableState` now accepts its whole `options` argument as an Accessor (see "Solid package" above). `data`/`columns` are deliberately **not** threaded through as Accessors, even though `createTableState` supports that for a genuinely reactive source — vanilla's own `options` object is a plain, one-time JS value with no reactivity of its own to feed one from, so `setData`/`setColumns` stay the only way to update them, same as before. `defaultVisibleColumns`/`defaultPageSize` have no setter at all — they're seed-only constructor values in every adapter (see "Namespaced TableState" above).

### Row selection

Selection lives in `useTableState` in both adapters. Key design notes:

- Selection is tracked as `Set<TRow>` by **object identity** — no `rowKey` dependency. Row references must be stable (the same object in memory) across re-renders for selection to persist through sort/filter changes. `rowKey`'s own JSDoc (all three adapters' `types.ts`) and each README's props table now spell this out explicitly — it's a rendering-identity hint only (React `key`/Vue `:key`/vanilla DOM key), not a selection identifier the way "row key" reads in most other table libraries (TanStack Table, AG Grid, MUI); this was previously undocumented and easy to assume otherwise.
- **`getRowId?: (row: TRow) => string | number`** (all four adapters' options, alongside `defaultVisibleColumns`/`labels`/etc.) is the opt-in escape hatch for the identity limitation just above: a refetch or re-map of `data` that produces new row objects (even with identical content) silently drops object-identity selection, since a `Set` can only ever match by reference. Supplying it switches selection to match by id instead, surviving that kind of refresh. Built entirely in core (`logic.ts`'s "Selection identity" section) as a handful of `getRowId?`-parameterized functions that are a no-op passthrough to today's exact object-identity behavior when omitted, so this is purely additive — nothing changes for a consumer who doesn't set it:
  - `isRowSelected(selection, row, getRowId?)` / `getSelectedRows(rows, selection, getRowId?)` — the membership check and its array-filter form (the latter backs `selectedRows`), matching by id (linear scan / one id-`Set` built up front) instead of `Set.has` when `getRowId` is given.
  - `toggleRowInSelection(selection, row, getRowId?)` / `toggleAllInSelection(selection, rows, getRowId?)` — replace each adapter's own inline `Set` add/delete logic in `toggleRowSelection`/`toggleSelectAll`; with `getRowId`, "toggle" finds and removes whichever existing entry shares the row's id (not necessarily the exact reference passed in) rather than requiring an exact match.
  - `reconcileSelection(nextData, selection, getRowId?)` — run whenever `data` changes, remaps each selected id to its fresh object reference in `nextData` and drops ids no longer present. React does this inline during render (the same `data !== prevData` "adjust state when a prop changes" pattern as the `visibleCols`/`columnKeys` reconciliation); Vue via a `watch(data, ...)`; Solid inside a wrapped `setData` (mirroring `setColumns`'s own `visibleCols` reconciliation wrapper); vanilla gets it for free through Solid's `setData`.
  - Shift-click range selection (`selectRange`) is **not** id-aware — the anchor/target still match by reference within `processedData`, so a data refresh between a plain click and a later shift-click can fall back to selecting just the target, the same pre-existing fallback that already applies when the anchor is sorted/filtered away. Not fixed here; considered acceptable given the anchor is always re-set to the exact just-clicked row on every non-shift click, so this only bites a shift-click whose anchor click and target click straddle a data refresh.
- React uses `useState<Set<TRow>>` (always assigns a new Set on mutation). Vue uses `shallowRef<Set<TRow>>` — `ref` would cause `UnwrapRefSimple<TRow>` type errors because Vue's deep-unwrap conflicts with generic constraints.
- Vanilla's imperative selection methods don't share names 1:1 with `TableState.selection`: `clearSelection()` ↔ `selection.clear()`, `getSelection()` ↔ `selection.all`, `setSelection(rows)` ↔ `selection.setAll(rows)` (the latter exists on Solid's `TableState` specifically to back this vanilla method — React/Vue have no `setAll` of their own). Worth checking this mapping by hand rather than assuming a name carries over, since vanilla intentionally flattens every namespaced group into its own distinct flat method names (see "Vanilla package" above).
- `table.selection.rows` is `processedData.filter(r => selection.has(r))` — rows removed by filtering disappear from `selection.rows` but stay in `selection.all` and reappear if the filter is cleared.
- `table.selection.toggleAll(rows: TRow[])` takes an explicit row array — the caller decides what to pass (typically `processedData`, not just the current page). It deselects all if any are currently selected (so an indeterminate _or_ fully-checked state clears on click, matching Gmail's select-all-checkbox convention), and only selects all when none are selected.
- Vue uses a local `vIndeterminate` directive (mounted + updated hooks) to set `el.indeterminate` reactively; React uses inline callback refs (re-run on every render because they are arrow functions).
- **Shift-click range selection**: `table.selection.toggle(row, shiftKey?)` takes an optional second argument. A plain click toggles just that row and remembers it as the anchor (an internal `selectionAnchor` closure/state var — not part of the public `TableState`, since nothing outside needs to read it). A shift-click computes the contiguous run between the anchor and the clicked row via core's `selectRange(items, anchor, target)` (an inclusive slice by `indexOf`, falling back to `[target]` alone if the anchor isn't in `items` anymore — e.g. sorted/filtered away) over `processedData` (the full filtered/sorted order, not just the current page, so a range can span a page boundary the same way it would in a scrollable list). The direction (select vs deselect) mirrors what a plain click on the _target_ row would do — i.e. it's based on the target's own checked state before the click — so shift-click can both extend and shrink a selection with the same modifier. Row checkboxes read the modifier off `onClick`/`@click` (a `MouseEvent`), not `onChange`/`@change`, since `change` events on checkboxes don't carry `shiftKey`; React additionally marks the checkbox `readOnly` to suppress its controlled-input-without-`onChange` warning.
- **Vanilla's imperative selection API**: React/Vue/Solid expose selection reactively (`table.selection.all`/`.rows`/`.clear`/`.toggleAll`/`.toggle`, readable and callable anytime). Vanilla has no reactive state to read directly, so `DataTableInstance` gained matching methods — `getSelection()` (mirrors `selection.all`, not `selection.rows`: it returns every selected row including ones currently hidden by a filter, so `setSelection(getSelection())` round-trips predictably regardless of what's filtered), `setSelection(rows)`, and `clearSelection()` — so a consumer can wire an external "Clear selection" button or pre-select rows on load, the same things React/Vue/Solid could already do by calling `table.selection.clear()`/`table.selection.toggle(row)` directly outside the component. Both mutating methods call the existing `render()` (refreshing checkboxes from the mutated `selection` Set, the same pattern every internal selection handler already follows) and fire `onSelectionChange` with the current `_processedData`-filtered view, consistent with how every other selection change already notifies it.

### Row click

`onRowClick` (React/vanilla prop) / `rowClick` (Vue emit) fires when a data row is clicked, receiving the full row object and the native click event — no `rowKey` lookup needed. Group header rows, the aggregate row, and the selection checkbox cell never trigger it:

- **React** — the checkbox `<td>` already calls `e.stopPropagation()`, which is what keeps checkbox clicks from bubbling to the row's `onClick`. A `cursor: 'pointer'` inline style is applied to the row only when `onRowClick` is set. Since rows are styled with inline `style` objects (no stylesheet to hold a `:hover` rule), the hover highlight is JS-driven: `onMouseEnter`/`onMouseLeave` track a single `hoveredRow` state value, which the row's background ternary checks ahead of the stripe/selected fallback.
- **Vue** — the checkbox `<td>` uses `@click.stop` for the same reason. Since `rowClick` is a declared emit, Vue strips any `onRowClick` listener out of `$attrs` before it reaches the component, so presence can't be detected via `useAttrs()`; `getCurrentInstance()?.vnode.props?.onRowClick` reads the raw incoming listener instead, and drives the `dt__tr--clickable` class (which sets the pointer cursor and a `:hover` background rule — real CSS pseudo-classes work here because rows are styled via classes, not inline styles). `.dt__tr--selected` uses `!important` so a selected row's highlight always wins over the hover background.
- **Vanilla** — the row `<tr>` carries `data-action="row-click"` and `data-proc-idx`; the checkbox `<td>` carries `data-no-row-click`, which the `row-click` case in `handleClick` checks via `target.closest('[data-no-row-click]')` before invoking the callback (same guard pattern as `data-no-collapse` for group-row checkboxes). The `dt-tr--clickable` class is added whenever `onRowClick` is set; its `:hover` rule is declared in `styles.ts` _before_ `.dt-tr--selected .dt-td` so a selected+hovered row keeps the selected color on the equal-specificity tie. Firing the callback returns early without calling `render()` itself — it does update `focusedRow` (see "Keyboard navigation" below), but that's picked up by whichever render happens next rather than forcing one here.

Custom cell renders (React `render`, Vue `#cell-*` slots) that put clickable elements (buttons, links) inside a cell are responsible for calling `stopPropagation()` themselves if they don't want the click to also reach `onRowClick`.

### Header click sorting

Clicking a column header is a single-column-sort shortcut, distinct from the Sort dropdown (which remains the tool for building a deliberate multi-column sort with explicit priority/direction control):

- **Plain click** sorts by that column alone, discarding every other active sort — `replaceSort(sorts, key)` (core; named to read as distinct from `toggleSort`/`appendOrToggleSort` rather than a near-synonym, since all three sound alike despite very different effects on the rest of the multi-sort): if `key` is already the sole active sort, cycles its direction the same way `toggleSort` does (asc → desc → none); otherwise replaces `sorts` outright with a fresh `[{ key, dir: 'asc' }]`, regardless of what was sorted before.
- **Shift-click** adds the column to the existing multi-sort (ascending) if it isn't already part of it, or flips its direction in place if it is — `appendOrToggleSort(sorts, key)` (core). It deliberately never removes an entry: cycling through "none" would both surprise someone who only meant to flip direction, and — because the next shift-click would then re-add the column at the _end_ of the priority stack — silently lose its original position. Removing a column from the multi-sort stays a dedicated action: the active-bar chip's `×` or the Sort dropdown's own remove button.
- The Sort dropdown's own "add sort" entries keep using the original `toggleSort` (append, cycling to removal) — unaffected by either of the above, since those entries only ever fire on a column that isn't already active (already-active columns render as reorderable "active sort" rows with their own direction toggle/remove controls instead), so the removal branch is unreachable from there in practice.
- The header's own sort-icon index number (`1↑`, `2↓`, …) is only rendered once **more than one currently-visible header** is sorted — with just one, a bare `↑`/`↓` is enough and a lone "1" would be noise. "Visible" matters because a `groupBy` column keeps its own `sorts` entry (`sortWithinGroups` uses it to order the groups themselves) but has no `<th>` of its own once grouped (see "Grouped columns"); counting it toward the total, or numbering off its raw position in `sorts`, could show a stray "2" on the only visible sorted header with nothing numbered "1" to match. Each adapter filters `sorts` down to entries whose key is still in `activeColumns` before computing both the threshold and the index itself, local to the header-row render (React: an inline `headerSorts` computed via an IIFE in the `activeColumns.map`; Vue: a `headerSorts` computed plus `isHeaderSorted`/`headerSortLabel` helpers; vanilla: a `headerSorts` local computed once before the header loop in `render()`) — this doesn't touch the sort dropdown's or active-bar chip's own numbering, which still reflects every entry in `sorts` regardless of header visibility.
- `table.sort.replace`/`table.sort.appendOrToggle` are exposed alongside the pre-existing `table.sort.toggle`; Solid's `TableBody.tsx` wires both directly into the header `<th>`'s `onClick`, reading `e.shiftKey` to choose between them (vanilla gets this for free — see "Vanilla package" above).
- **`ColumnDefBase.sortable?: boolean`** (default `true`) excludes a column from header-click/shift-click sorting entirely and from the Sort dropdown's own "add a sort" list — the same `sortable !== false`-style opt-out convention `filterable` already uses (`groupable` is the opposite, opt-_in_). Each adapter enforces this itself (`c.sortable !== false` guarding both the addable-columns list and the header click handler's early-return) since core's `toggleSort`/`replaceSort`/`appendOrToggleSort` have no `columns` argument to check it against. An already-active sort entry on a `sortable: false` column (set programmatically via `setViewState`, or from before the flag was added) stays fully intact and removable via its active-bar chip or the Sort dropdown's own remove button — only _adding a new_ header-driven sort is blocked.
- **`ColumnDefBase.defaultSortDir?: SortDir`** (default `'asc'`) picks which direction a _fresh_ sort on that column starts at — e.g. `'desc'` for a "last modified" date column or a score/count column, where descending is the more useful first click. It's opt-in per column only; there's no type-based inference (a `type: 'date'` column doesn't default to `'desc'` on its own), to avoid a surprising behavior change for existing columns. `toggleSort`/`replaceSort`/`appendOrToggleSort` (core) all take it as an optional 3rd `defaultDir` param and cycle `none → defaultDir → opposite(defaultDir) → none` instead of the fixed `none → asc → desc → none` — so a `'desc'`-default column's first click sorts descending, second click flips to ascending, third clears it. Only where a _new_ sort entry starts (and which direction its cycle removes from) changes; an already-active entry's `toggleSortDir` flip (chip click, Sort dropdown row) is unaffected, since it just alternates whatever direction is already set regardless of where the cycle began. Each adapter looks up `columns.find(c => c.key === key)?.defaultSortDir ?? 'asc'` at the call site (React/Vue's `useTableState` actions; vanilla's `header-sort`/`toggle-sort` handlers) and passes it through — no new state, no persistence changes (`TableViewState.sorts` already stores each entry's resolved `dir` explicitly).

### Keyboard navigation

Rows use a **roving tabindex**: exactly one item — a data row or a group header row — is a Tab stop at a time (`tabIndex`/`tabindex` `0`, the rest `-1`), arrow keys move it. This only covers the table body; toolbar buttons, dropdowns, and filter checkboxes are already native focusable elements.

`getVisibleRows` (core) flattens grouped data into a `VisibleItem<TRow>[]` display-order sequence (group headers, even collapsed ones, followed by their rows unless collapsed) that backs Up/Down/Home/End navigation; `isSameVisibleItem`/`indexOfVisibleItem` (core) relocate a stored focus target inside a freshly-computed sequence. Each adapter derives `navigableItems` by filtering out row items when the table isn't otherwise interactive (`selectable || onRowClick`) — group headers are never filtered out. The tracked `focusTarget` self-heals to the first navigable item if it's sorted/filtered/grouped away.

Key bindings on the row/header itself: `ArrowUp`/`ArrowDown` move focus (crossing page boundaries when paginated); `Home`/`End` jump within the current page, `Ctrl`/`Cmd+Home`/`End` jump across all pages; `Space` toggles row/group-header selection (when `selectable`); `Enter` fires `onRowClick`/toggles a group's collapse. `Shift+ArrowUp/Down/Home/End` additionally range-selects via the existing anchor/`selectRange` logic. The row checkbox gets `tabIndex={-1}` unconditionally when `selectable`, since row-level keys already cover selection. `aria-selected`/`aria-expanded` reflect state.

Each adapter wires focus differently: React uses a `rowRefs` map + `onFocus` + a `pendingFocusTarget` ref/effect for page-boundary crossings; Vue mirrors this with `shallowRef`/`@focusin`/`watch(page, ..., { flush: 'post' })`; vanilla resolves the focused element via ancestor DOM lookup in a delegated `keydown` listener and restores focus after every `innerHTML` rebuild.

Full per-adapter wiring, the page-boundary-crossing mechanism, and `paginateVisibleItems` are documented in [docs/keyboard-navigation.md](docs/keyboard-navigation.md).

### Pagination

`pageSize: 0` disables pagination — all rows are returned on a single page. Both adapters default to `0`. `processedData` holds all filtered/sorted rows regardless of pagination. `computeTotalPages`/`paginateData` (core) treat a non-finite `pageSize`/`page` the same as `<= 0`/`1` rather than propagating `NaN` into the slicing math.

Grouping and pagination compose as: group the full `processedData` → flatten to visible items (`getVisibleRows`) → paginate that flattened header+row sequence → re-chunk the page's slice back into per-group form for rendering — a deliberate reversal of "paginate rows then group," so a page never renders more than `pageSize` rows total (headers count against the same budget as data rows), at the cost of a group's rows being able to split across a page boundary.

- **`paginateVisibleGroups`** (core) is the re-chunking step, returning `PagedGroup<TRow>[]` with a `continued` flag (a repeated header on a later page) and a `sampleRow` (for rendering a header/aggregate even when this page's chunk has zero of the group's own rows).
- **`paginateVisibleItems`** (core) is the equivalent per-page slice for keyboard navigation, prepending a synthetic group header when the slice starts mid-group.
- **`numPages`** is `computeTotalPages(visibleItems.length, pageSize)` — grows/shrinks as groups expand/collapse, with the pre-existing `Math.min(page, numPages)` clamp handling the fallout.
- **`mergePageSizeOptions`** (core) inserts the current `pageSize` into the hardcoded `[10, 20, 50, 100]` option list when missing, so the `<select>` always has a matching option.

Full detail on `PagedGroup`, the `continued`/`sampleRow` semantics, and the keyboard-navigation integration is in [docs/pagination.md](docs/pagination.md).

### Filter dropdown

A master-detail layout — a left pane listing every filterable column (string/numeric/date unified, dot indicator for an active filter) and a right pane with that column's controls (search + checklist for string, min/max + slider for numeric, a Year › Month › Day tree for date) — replacing an older flat stacked-checklist design that didn't scale to high-cardinality columns (GitHub issue #8).

Key mechanics: checklist values support **include and exclude** (tri-state cycle: neutral → include → exclude → neutral) via `cycleFilterValue`, kept mutually exclusive in `filters`/`excludeFilters`; each checklist item shows a **facet count** (`computeStringValueCounts`, scoped via `targetKeys` for performance — see "Performance" below) and a value with a count of 0 is hidden unless already selected; `type: 'date'` columns get a `computeDateTree` tree instead of a range, reusing the same include-only-checklist model; `type: 'number'`/`'date'` ranges get a **two-thumb slider** (`computeValueBounds`) alongside the plain min/max inputs; the flat checklist is **virtualized** (`computeVirtualRange`) for large value lists; shift-click range-selects in both the flat list (`selectRange`) and the date tree (`selectDateRange`, a chronological interval, not a rendered-row sweep); a sort-order toggle cycles alpha/count order (`cycleValueSort`) for string columns or chronological direction for dates. Active-bar chips are per-kind (include/exclude/range each get their own, `clearColumnFilter(key, kind)`) rather than one reset-everything chip.

Full design, every core primitive (`filterValuesBySearch`, `toggleFilterAll`, `setFilterValues`, `filterValuesByRange`, `getDateTreeNodeState`, etc.), and per-adapter wiring quirks (React's combined filters/excludeFilters state atom, Vue's `preventDefault()` checkbox fix, vanilla's `data-exclude`/indeterminate patch) are in [docs/filter-dropdown.md](docs/filter-dropdown.md).

### Global search

`searchData(data, query, columns)` filters rows before `processData` runs — it matches any column's string value (using `col.format` when defined) case-insensitively against the query. Both adapters expose `searchQuery` state and a `setSearchQuery` action; `clearAll` resets it. The vanilla adapter restores focus on the search input across re-renders via `data-focus-key="search"`. `ColumnDefBase.searchable?: boolean` (default `true`) excludes a column from this match entirely — for a column whose underlying value isn't user-facing text (e.g. an image URL rendered via `render`), matching against it would surface rows on an accidental substring hit the user has no way to anticipate. Independent of `filterable`/`sortable`/`groupable`, which gate unrelated concerns.

### Computed columns

`ColumnDefBase.value?: (row: TRow) => unknown` decouples a column's cell value from its `key`. `key` stays a plain `string` (loosened from `keyof TRow & string`) and is only ever used as the column's identity — for sort/filter/group/visibility state and list keys. `value` governs how the cell value is actually read: omitted reads `row[key]` (unchanged default behavior), a function computes the value from the whole row — covering both simple aliasing (`value: (row) => row.name`) and true computed columns with no single backing property (`value: (row) => row.price * row.qty`). A string form (reading a named property instead of `key`) was considered and rejected: it's strictly redundant with the function form (which already covers aliasing, plus nested access like `value: (row) => row.address.city`, at no extra API cost), so it would just be a second way to do the same thing. `getColumnValue(col, row)` in `logic.ts` is the single accessor implementing this and is used everywhere a cell value is read: `processData`'s filter/range-filter/sort, `groupData`, `computeStringValues`, `searchData`, and `computeAggregate`. All of these already accepted a `columns` array except `groupData`, which gained one (`groupData(data, groupBy, columns, emptyLabel)`) so groupBy columns can be computed too.

Each adapter's own cell/group-header rendering (React `cellValue()`, Vue `cellText()`/`groupValue()`, vanilla `cellStr()`) calls `getColumnValue` instead of reading `row[col.key]` directly. `rowKey` (React/vanilla prop, Vue prop) is a separate, unrelated concept — it identifies a row for list keys/DOM identity and still reads a real row property directly, untouched by this.

### Grouped columns

When a column is added to `groupBy`, `useTableState` removes it from `activeColumns`, so it disappears from the table header and cells automatically. When grouping is cleared, the column reappears. Group header values are rendered with the same `cellValue()` / slot logic as table cells.

`ColumnDefBase.keepVisibleWhenGrouped?: boolean` (default `false`) opts a column out of that auto-hide (GitHub issue #16) — for the two cases where the group header no longer shows the same thing the row would, so hiding is a net information loss rather than a redundancy: a `groupValue`-bucketed column (header shows only the bucket, e.g. "3–10h" — the row's exact value is otherwise visible nowhere) and a multi-value/array column (grouping fans a row out into one group per value, so hiding the column removes the only way to see a row's _other_ values from within one particular group's expansion). Deliberately explicit rather than auto-detected off `groupValue`/array-shaped values — `value` is an arbitrary function, so whether a column's cells can be arrays isn't knowable from the column def alone, only from actual data. `activeColumns`' filter (identical across React/Vue/Solid — vanilla gets it for free) became `visibleCols.has(c.key) && (!groupBy.includes(c.key) || c.keepVisibleWhenGrouped === true)`; rendering when kept visible is unchanged (the same `format`/render/slot pipeline as ungrouped, showing the row's real value — including the full array for a multi-value column — with no filtering-out of the value that matched the current group).

`ColumnDefBase.groupValue?: (value, row) => unknown` lets a column bucket into a coarser group key than its exact value (e.g. a percentage rounded to a 10-point range, a timestamp truncated to its month) — spliced into `groupData` right where the exact-value key would otherwise be read, affecting grouping only. `ColumnDefBase.groupFormat?: (keyPart) => string` renders that bucket key for the group header, bypassing the column's normal `format`/render/slot pipeline. `bucketNumericRange`/`formatNumericRange`/`bucketDatePart`/`formatDatePart`/`bucketLogRange`/`formatLogRange` (core, re-exported from every adapter) are ready-made pairs for the common cases — see "Ready-made `groupValue` bucketers" below.

### Ready-made `groupValue` bucketers (GitHub issue #18)

`bucketNumericRange(step)`/`bucketDatePart(part, parseDate?)` return `null` for a missing (`null`/`undefined`) or (for the numeric one) non-numeric value, rather than coercing it — `Number(null) === 0` would otherwise silently merge "no value" into the same bucket as a real, confirmed `0`, and `Number(undefined)`/`Number('abc')` being `NaN`, or `String(null) === "null"`, would otherwise flow through `groupData`'s `multiValues` to a group key that stringifies to the literal visible text `"NaN"`/`"null"`. `null` stringifies to `''` the same way an _unbucketed_ missing scalar already does (`multiValues`' `String(value ?? '')`), so a bucketed column's missing-value group lands on the exact same key an unbucketed column's missing rows already use — no new sentinel introduced. `formatNumericRange`/`formatDatePart` each take a 3rd `missingLabel = '(none)'` param and render it for that `''` key; a genuinely invalid _but present_ value (e.g. `bucketDatePart`'s raw string when it doesn't parse as a date) still returns unchanged, since — unlike a missing value — it's real text worth keeping.

`bucketLogRange(options?)`/`formatLogRange(options?, unit?, missingLabel?)` bucket a `type: 'number'` column on a logarithmic scale instead of a linear step — for a right-skewed column spanning several orders of magnitude (review counts, hours played, file sizes), where any single linear `bucketNumericRange` step is either too coarse for the long tail or too fine for the low end. `LogRangeOptions` is `{ base?, divisions?, min? }`: `base` (default `10`) is the multiplier per exponent step (`2` for octaves/binary doublings); `divisions` (default `[1]`, plain order-of-magnitude) lists the bucket starts within one `base` cycle as multipliers of `base ** exponent` — `[1, 3]` splits each decade into a "1–3"/"3–10" half-decade grid, `[1, 2, 5]` gives the classic "1-2-5" grid; `min` (default `1`) collapses everything below it (and always `<= 0`, since `log` is undefined there) into one low bucket instead of extending the grid toward zero — pass `min: 0` to opt out of the collapse for positive values (zero/negative still always collapse, regardless of `min`). The below-`min` bucket uses a dedicated `-Infinity` sentinel, kept distinct from the `null` "missing" key so the two don't merge; `formatLogRange` renders it as `"<<min><unit>"`. Bucket boundaries are always an exact `base ** exponent * divisions[i]`, so `formatLogRange`'s k/M magnitude-suffix formatting (`>= 1e3` → `k`, `>= 1e6` → `M`) never needs decimal rounding. No named preset division arrays (e.g. IEC 60063's E-series, ISO 3's Renard series) ship built in — `divisions` accepts any array, and a consumer needing a named standard passes its values directly.

`numericRangeGroup(step, unit?, missingLabel?)`/`datePartGroup(part, parseDate?, missingLabel?)`/`logRangeGroup(options?, unit?, missingLabel?)` each return `{ groupValue, groupFormat }` — the exact property names `ColumnDefBase` uses — from one set of arguments, since `groupValue`/`groupFormat` otherwise need the same `step`/`unit`, `part`, or `options`/`unit` passed to both independently; a mismatch between the two (e.g. changing `step` on one side and forgetting the other) previously failed silently, producing a group header that disagreed with its own bucket's real boundaries. Spread directly into a column def: `{ key: 'hoursPlayed', ...logRangeGroup({ divisions: [1, 3] }, 'h') }`. The standalone `bucket*`/`format*` functions stay exported too, for a consumer that wants just one half or needs to pass mismatched-on-purpose arguments (e.g. a `unit` that only applies to the header, not the bucketing itself — not a real case today, but the two were never coupled at the type level).

`defaultGroupsCollapsed` (default `true`) controls initial collapse state via `isGroupCollapsed(collapsedGroups, key, defaultCollapsed)` — `collapsedGroups` is reinterpreted as _manual toggles away from the default_ rather than absolute state, so a never-seen group key picks up the default for free with no seeding needed.

`sortWithinGroups(groups, sorts, groupBy, columns)` (core), called right after `groupData`, fixes GitHub issue #12: a multi-value column's row fan-out has no single per-row comparable value, so pre-fan-out sorting alone left both row order within a bucket and the groups' own order arbitrary. It splits `sorts` into entries matching a `groupBy` column (reorder the top-level `groups` array by each group's own `keyParts[i]`) and the rest (re-sort each group's `rows`, with groupBy-matching entries excluded as no-ops).

Full mechanics are in [docs/grouped-columns.md](docs/grouped-columns.md).

### Custom sort order (`compare`)

`ColumnDefBase.compare?: (a: unknown, b: unknown, dir: SortDir) => number` (see GitHub issue #15) is a plain `Array.prototype.sort`-style comparator over two already-resolved column values — not full rows (`sortWithinGroups`' group-order pass has no single owning row for a bucket, so a row-aware signature couldn't be reused there anyway) — for a column whose natural order is neither numeric nor alphabetical (an enum/tier column: `Bronze < Silver < Gold`, not alphabetical). It overrides the default numeric-or-lexicographic comparison (factored out as `defaultCompare` in `logic.ts`) everywhere a column's values are ordered: `processData`'s row sort and `sortWithinGroups`' per-bucket row sort (both via the shared `sortRows`), `sortWithinGroups`' group-order pass (comparing `keyParts[idx]` directly instead of through `comparableFromKeyPart`'s type coercion), `computeStringValues`' default checklist order, and `sortFilterValues`' explicit alpha-mode sort toggle including count-mode's tie-break (replacing `localeCompare` in both). `compare` takes priority over `type: 'number'`/`'date'` coercion when both are set on a column — `sortRows` reads the raw value via `getColumnValue` instead of the type-coercing `getComparableValue` whenever `col.compare` is present. Doesn't affect `groupValue`/`groupFormat` bucketing, which solves the equivalent problem for grouping instead.

The 3rd `dir` argument is the active ascending/descending direction at that sort site (a fixed `'asc'` at the two checklist-ordering sites, which have no direction of their own — `computeStringValues`'s default order, and `sortFilterValues`'s count-mode tie-break, which — like `computeStringValueCounts`'s existing "tie-break alphabetically" behavior — is always ascending regardless of the checklist's own `sort.dir`, itself only ever governing the count comparison above it). An ordinary comparator should ignore it: every call site already flips the _return value_'s sign for a descending sort (`dir === 'asc' ? cmp : -cmp`) the same way the default comparison does, so a direction-naive `(a, b) => …` behaves correctly for free. `dir` exists only for the rarer case of a value that must stay pinned to one end regardless of which direction is active (e.g. a missing value sorting last whether ascending or descending) — genuinely impossible to express as a plain `(a, b) => number` return, since that return's sign gets flipped for `desc` right along with everything else, flipping "always after" to "always before" the moment the direction is toggled.

`compareMissingLast(compare?, isMissing?)` (core, re-exported from all three adapter packages alongside `bucketNumericRange`/`bucketDatePart`) is a ready-made comparator built on this: `isMissing` (default `(v) => v == null || v === ''`, covering both a real `null`/`undefined` raw value — row-level sort, where `getColumnValue`/`getComparableValue` can return either — and the empty string a missing scalar stringifies to wherever grouping/the filter checklist need a string instead, `multiValues`' `String(value ?? '')`) decides which values get pinned; `compare` (default: this module's own numeric-or-lexicographic fallback) orders any two non-pinned values, direction-naive same as any other comparator. Two pinned values compare as equal (`return 0`), falling through to the next sort key the same way a tied `compare` result would; a pinned value against a normal one returns `dir === 'asc' ? rel : -rel` for a fixed `rel` — pre-cancelling the call site's own upcoming flip so the net result stays "pinned always after" in both directions. Combine it with a custom order by passing that order's own comparator as `compareMissingLast`'s first argument, e.g. `compareMissingLast((a, b) => TIER_ORDER.indexOf(a) - TIER_ORDER.indexOf(b))` ranks by tier with an empty tier always last.

No adapter-level wiring was needed beyond passing `filterDetailCol.compare` through to `sortFilterValues`'s existing 4th param (React/Vue's `filterDetailValues`/`filteredValuesFor`, vanilla's `_filterDetailValues` computation) — `compare` lives on `ColumnDefBase` and every other call site is internal to `logic.ts`.

### Reconciling `visibleCols` against a replaced column set

`table.columns.visible` (`visibleCols` internally) is normally seeded once (from `defaultVisibleColumns`, or every initial column — see "Column definition") and otherwise only ever mutated by `table.columns.toggleVisibility`. Every adapter's `table.columns.active` is filtered by it, so if a table's whole `columns` can be swapped for a differently-keyed set without a fresh mount — a consumer keeping the same `<DataTable>`/`TableState` but changing what kind of data it shows, e.g. `xapi-data-table`'s `ObjectsView` switching between XAPI object types — an unreconciled `visibleCols` would still hold the _old_ keys, none of which exist in the new `columns`, and every column would filter out as "not visible": the table would silently render with none at all.

`reconcileVisibleColumns(prevColumns, nextColumns, visibleCols)` (core) fixes this: a column present in both keeps whatever visibility choice it had; a column only in `nextColumns` (genuinely new) starts visible by default, the same default used when no `defaultVisibleColumns` override is given at construction. This also covers a fully disjoint replacement for free — with nothing carried over to preserve, every column in `nextColumns` counts as "new" and ends up visible.

Each adapter reaches this from a different trigger, matching how each already owns `columns`:

- **Solid** — `createTableState.columns.set` (its own explicit setter, exposed publicly and also used internally by the accessor-tracking effect) calls it directly: `setVisibleCols((prevVisible) => reconcileVisibleColumns(prevColumns, cols, prevVisible))`, where `prevColumns` is `columns()` read just before the signal is updated.
- **React** — `useTableState` gets fresh `columns` on every render (no explicit setter of its own), so the reconciliation runs inline during render, comparing against the previous render's column keys — the same "adjust state when a prop changes" pattern already used for `filterListScrollTop` in `DataTableView.tsx` (a plain `if` calling `setState` synchronously during render, not inside an effect, which both avoids an extra render and sidesteps the `react-hooks/set-state-in-effect` lint error). A `sameKeySet` guard (order-insensitive) prevents this from re-running every render when `columns` is a fresh array with the identical key set — without it, the state update on every render would defeat the whole "only reconcile on a genuine key-set change" point.
- **Vue** — a `watch(columns, (nextColumns, prevColumns) => { visibleCols.value = reconcileVisibleColumns(...) })`, since `useTableState` (like Solid's `createTableState`) is only called once per component instance, unlike React's re-invocation-per-render — `watch` is Vue's equivalent mechanism for reacting to a later change. `watch` is lazy by default (no `immediate`), so it never runs against the very same `columns.value` that already seeded `visibleCols` above it.

### Column reordering

`columnOrder: string[]` is separate from `visibleCols` — it lists _all_ column keys (visible and hidden) in display order, so hiding a column and showing it again doesn't lose its position. It starts as `[]` (natural order) and is only materialized on the first reorder.

`getOrderedColumns(columns, order)` (core) sorts the full column list per `order`, appending any column missing from it at the end in original relative position. `activeColumns` is `getOrderedColumns(columns, columnOrder).filter(visible && !grouped)`; `orderedColumns` is the unfiltered version, used by the Columns panel.

Two interactions write to `columnOrder`: **drag-and-drop on headers** (native HTML5 DnD; `reorderColumn(order, dragKey, targetKey)` moves `dragKey` to just before `targetKey`, always insert-before) and **drag-and-drop or Alt+ArrowUp/Alt+ArrowDown on rows in the Columns panel** (`moveColumnBy(order, key, delta)`, swap with neighbor, no-op past a boundary). Both materialize `columnOrder` from `columns.map(c => c.key)` first if it's still `[]`.

`reorderColumn`/`reorderSort` (core) both take a 4th `after = false` param, reused by the Sort/Group/Columns dropdown lists' own drag-and-drop (which resolve `after` from cursor position within the hovered row, unlike header dragging which stays insert-before-only). `TableViewState.columnOrder?: string[]` persists/shares the order (wire key `o`).

Full per-adapter drag wiring (React/Vue state, vanilla's CSS-class-only mid-drag feedback, `resolveDragRow`/`resolveDropdownDragRow`) is in [docs/column-reordering.md](docs/column-reordering.md).

### Toolbar clear buttons (Sort/Group/Filter)

The Sort/Group/Filter dropdowns used to render their own "Clear sorts"/"Clear groups"/"Clear filters" row in a `dd-footer` at the bottom of the panel — clearing that state required opening the dropdown first. Each toolbar button now instead grows an adjoining × button (visible only when that state is non-empty, i.e. `sorts.length > 0`/`groupBy.length > 0`/`activeFilterCount > 0`) that clears without opening the dropdown at all — same idea as the search input's own `×` clear button (`dt-search-clear`/`.dt__search-clear`), which the new button matches in color/size (muted `--color-text-tertiary`, `font-size: 14px`). The Columns dropdown is unaffected — it never had a clear concept. The toolbar-level "Clear all" button (`clear-all`) is also unaffected; it coexists with these per-dropdown ones.

A `<button>` can't contain another interactive element, so the × can't nest inside the toggle button itself — it's a sibling, and the two are visually merged into one pill via a shared border (toggle button gets its right corners squared off and its right border dropped; the × button gets the matching left treatment and rounds off the outer right corners).

- **Vanilla** — the trigger markup passed to `buildDd` becomes `<span class="dt-btn-group">` wrapping both `<button class="dt-btn dt-btn--grouped">` (only when active — plain `.dt-btn` otherwise) and the sibling `<button class="dt-btn-clear" data-action="clear-sorts">×</button>`. Since both buttons already live inside the same `.dt-dd-wrap` as before, no changes were needed to the existing "close dropdown on outside click" logic (which checks `.closest('.dt-dd-wrap')`) or to drag-and-drop resolution (which already treats the whole `.dt-dd-wrap` as one region).
- **React/Vue** — the × can't just be placed in the `trigger` prop/slot, because `Dropdown`'s trigger area itself carries the open/close click handler (an ancestor `<div onClick>` in React, `<div @click>` in Vue) — nesting the × there would make clicking it also toggle the dropdown. Both `Dropdown` components instead gained a second slot for this: React's `extraTrigger?: ReactNode` prop and Vue's `#extra-trigger` slot are rendered as a sibling of the trigger's own click-handling wrapper, but still inside the same outer container that the "click outside closes the dropdown" listener checks (`ref.current.contains(...)` in React, `containerRef.value.contains(...)` in Vue) — so clicking × neither toggles the dropdown open/closed via the trigger's own handler, nor spuriously closes an already-open dropdown via the outside-click listener treating it as "outside". That container's `display` changed from `inline-block` to `inline-flex` so the trigger and the extra × sit side by side. `ToolbarBtn` gained a `grouped`/`:grouped` prop (mirroring vanilla's `dt-btn--grouped`) for the same squared-off-right-edge treatment, applied only when that dropdown's state is non-empty.
- The × buttons reuse the existing `L.clearSorts`/`L.clearGroups`/`L.clearFilters` labels for their `title`/`aria-label` rather than as visible button text (the visible glyph is a literal `×`, matching `clearSearch`'s convention). Those three labels no longer carry a `'× Clear sorts'`-style leading `×` in `locales.ts` (across all five locales) — it made sense back when the string _was_ visible footer text, but reads redundantly once it's tooltip/aria-label-only text sitting next to a button that already shows its own `×` glyph, the same reasoning `clearSearch` (never prefixed) was already built around. `clearAll` is the one label that correctly keeps its `× ` prefix, since its button still renders the label as real visible text.

### Toolbar layout (shape/find clusters, active state bar)

The toolbar reads as two purposeful clusters instead of one undifferentiated row of buttons: **Columns · Sort · Group** (what's shown and in what order — "shape" the view) then a vertical divider then **Search · Filter** (which rows are shown at all — "narrow" the view), with the toolbar-level "Clear all" button pinned alone at the far right (`margin-left: auto`). Group moved out of its old position (after Filter) to sit with Sort as a fellow "shape" control; Search moved out of its own separate search-specific div to sit next to Filter as a fellow "find" control. The divider (`dt-toolbar-divider`/`S.toolbarDivider`/`.dt__toolbar-divider`) is a plain 1px-wide, 22px-tall vertical bar in `--color-border-secondary` (not the fainter `--color-border-tertiary` the toolbar's own bottom border uses — that token is too close to the background to read as a divider at this size).

Below the toolbar sits a second row, the **active state bar**, always rendered — even with nothing active — rather than only appearing once a filter is set. This gives the row-count stats a single stable home instead of bouncing between "end of the toolbar row" (its old position) and nowhere, and means toggling a sort/filter/group never changes the toolbar's height or shifts anything above it. It shows one chip per active sort entry, group column, and filter column, each independently removable (`remove-sort`/`remove-group`/`clear-filter-key`, all pre-existing actions — no new core primitives needed), followed by the row-count/group-count stats pinned at the far right of _this_ row instead of the toolbar row.

This replaces the old asymmetry where filter chips got a dedicated summary row (because the Filter button only ever showed a column _count_, with no view of which values were selected) while sort/group got only a bare count badge on their own toolbar button (`sorts.length`/`groupBy.length` in a small pill) — on the theory that the dropdown's own active-entries list already showed the detail, so a second copy would be pure duplication. In practice this meant sort/group state was strictly less visible than filter state despite being the same _category_ of thing (something the user did to shape/narrow the view), and you couldn't tell _which_ columns were sorted/grouped without opening the dropdown. The count badges are gone from all three toolbar buttons now (the active bar carries that detail instead); sort/group chips reuse the plain neutral chip look the badges used, while filter chips keep their existing blue tint (`dt-chip--filter`/`S.chipFilter`/`.dt__chip--info`) — the one deliberate color accent in this bar, since filters already carried that "narrowing your view" meaning before sort/group chips existed alongside them.

- **Vanilla** — the toolbar's outer `<div class="dt-toolbar">` now wraps only `.dt-toolbar-actions`; the active bar (`.dt-active-bar`) is a sibling `<div>` rendered after it (same nesting level `.dt-chips` used to have), built in the same `render()` pass right after the toolbar markup.
- **React** — `S.toolbar` dropped its own flex properties (it now just wraps `S.toolbarActions`, no longer lays out children directly); `S.toolbarSearch` was deleted entirely (the search `<span>` moved to be a plain sibling inside `S.toolbarActions`); the active bar is `S.activeBar`, a sibling `<div>` after the toolbar's closing tag.
- **Vue** — mirrors React exactly: `.dt__toolbar` lost its flex properties, `.dt__toolbar-search` was deleted, `.dt__chips` was renamed `.dt__active-bar` (kept as a sibling of `.dt__toolbar`, unchanged position) and is no longer gated behind `v-if="activeFilterCount > 0"`.
- Test gotcha for React specifically: the global search input and the Filter dropdown's own per-column search input share the exact same default placeholder text (`L.search` and `L.filterSearchPlaceholder` are both `'Search…'`). Tests that grab the filter's own search box via `getAllByPlaceholderText('Search…')` must now take the _last_ match, not the first — Search moved from after Filter (in DOM order) to before it, so the global box is now the earlier of the two matches. Vue's equivalent tests were never affected, since they disambiguate by CSS class (`.dt__search-input` vs `.dt__dd-search`) rather than by placeholder text.

### Active-bar chip click actions

Previously a chip's body (the label/icon text) was inert — only its `×` did anything. Each chip's body is now a real, focusable `<button>` (a sibling of the `×` button rather than nested inside it — a `<button>` can't contain another interactive element, the same reasoning already used for the toolbar's grouped clear buttons) that does something specific to that chip's own kind of active state, so tweaking an already-active sort/group/filter no longer requires reopening its dropdown and re-navigating to the same entry:

- **Sort chip** → toggles that column's direction in place (the same action the dropdown's own active-sort row already does) — no dropdown needed for the single most common tweak.
- **Group chip** → opens the Group dropdown and focuses that entry's row. There's no single obvious inline toggle for a group entry the way direction is for sort, so getting straight to it (ready to reorder/remove) is the most useful available action.
- **Filter chip** (both the checklist-values chip and the range chip) → opens the Filter dropdown, sets the active filter column to that key _before_ the panel first renders (so the right pane already shows the right thing on the very first paint, rather than waiting for focus to land and the "focus follows selection" mechanism below to catch up), and focuses that column's button in the left pane.
- Styling: a chip is no longer one bordered/padded pill-shaped element — the border/background/padding moved onto the body and `×` individually, each keeping only its own outer corner rounded and sharing a border between them (mirroring the toolbar's grouped-clear-button seam trick), so the pair still reads as one pill. This also makes chips keyboard-reachable for the first time (real `<button>`s are native Tab stops) — previously the whole chip was a plain, inert element apart from its `×`.

**Vanilla** — reuses the pre-existing `toggle-sort-dir` action as-is for the sort chip; two small, structurally identical new click-handler cases, `open-group-entry`/`open-filter-col`, do the rest — no new core logic needed, since each one only sets pre-existing state (`openDropdown`, `filterActiveCol`, `filterListScrollTop`) the same way the equivalent dropdown-open/column-select interactions already do. The sort chip's button carries a stable `data-focus-key="chip-sort-${key}"` so the existing generic focus-key restore at the top of `render()` (see "Keyboard navigation") keeps it focused across the re-render for free; Group/Filter's buttons get an explicit post-render focus lookup instead (by `grouprow-${key}`'s focus key, or by `.dt-filter-col-item`'s own `data-key`), since a _newly opened_ dropdown's row isn't the thing that had focus before this render, so the generic restore doesn't apply there. `.dt-chip` dropped its own padding/background/border in favor of `.dt-chip-body`/`.dt-chip-x` (`12px 0 0 12px` / `0 12px 12px 0` corner rounding).

- **React** — the sort chip's button keeps the same key/identity across the toggle, so it stays focused for free with no explicit refocus needed. Group/Filter route through the same pending-ref + `useLayoutEffect` pattern already used for the Sort/Group activate/remove focus-retention fix below (`pendingGroupFocusKey`/`pendingFilterColFocusKey`), since clicking either opens a dropdown panel that doesn't exist in the DOM yet at click time. `S.chip` lost its own padding/background/border in favor of new `S.chipBody`/`S.chipX` style objects.
- **Vue** — same reasoning as React: the sort chip needs no refocus code (Vue's reconciliation keeps its `<button>` in place across the reactive update); Group/Filter open their dropdown via a new `open()` method `Dropdown.vue` exposes via `defineExpose` (alongside the existing `close()`), then focus the target row/column button via the same ref maps used by the Sort/Group activate/remove fix, after an `await nextTick()`. `.dt__chip`'s own padding/background/border moved onto new `.dt__chip-body`/`.dt__chip-remove` classes.

### Dropdown viewport clamping and toolbar wrapping

Every dropdown panel (Columns/Sort/Group/Filter) is absolutely positioned off its trigger and would otherwise render partly or fully off-screen — most visibly the ~460px-wide filter panel opened near the right edge of a narrow viewport. Each adapter measures the freshly-opened panel's `getBoundingClientRect()` and, if it overflows the viewport, applies a `transform: translateX(...)` horizontal offset (rather than flipping the anchor side, `left:0` → `right:0` — the overflow is relative to the _viewport_, not the trigger, so flipping the anchor on a trigger near the toolbar's left edge would just push a wide panel off the opposite side instead) and flips the panel above the trigger when it would overflow the bottom edge (`top`/`margin-top` swapped for `bottom`/`margin-bottom` in React/Vue; a `dt-dd--up` CSS class in vanilla). React (`Dropdown.tsx`) and Vue (`Dropdown.vue`) do this in a `useLayoutEffect`/`watch(..., { flush: 'post' })` right after the panel mounts (each open is a fresh, unclamped DOM node, since the panel unmounts entirely when closed); vanilla does it inline in `render()` after `container.innerHTML` is set, via a plain `container.querySelector('.dt-dd')` lookup. All three mutate the node's `style`/`classList` directly rather than through reactive state, to avoid a synchronous re-render-triggering-render loop.

Separately, the toolbar search input is `flex: 1` capped at a `max-width` of 280px instead of a fixed ~160px box, so it grows to use available toolbar space on wide viewports while still shrinking gracefully on narrow ones — a CSS-only responsiveness fix, not a behavioral change. (An earlier iteration also wrapped the toolbar's buttons and the search/clear-all pair into two separate flex sub-containers so they'd wrap as units on narrow viewports; "Toolbar layout" above's shape/find redesign flattened both back into the single `dt-toolbar-actions`/`S.toolbarActions`/`.dt__toolbar-actions` container, so each control now wraps individually again.)

### Dropdown column search and keyboard navigation

The Columns, Sort, and Group dropdowns' full column lists, and the Filter dropdown's left column pane, each have a search box (`.dt-dd-search`, narrowing by `col.label` substring) plus Up/Down/Home/End/Escape navigation and **focus-follows-open** (opening a dropdown focuses its search input or first active row immediately). `.dt-dd` is bounded to `max-height: 420px; overflow-y: auto`.

Activating/removing a Sort or Group entry (moving it between the active and addable sections) explicitly refocuses the equivalent new element after the re-render, since neither framework's/vanilla's rebuild preserves focus across that structural move on its own.

The Filter dropdown additionally supports `ArrowRight`/`ArrowLeft` to cross between its left column pane and right detail pane, plus the same Up/Down/Home/End nav within whichever right-pane list is showing (the virtualized flat checklist, scroll-adjusted for Home/End and window-crossing; or the date tree, which needs no such adjustment). Focus landing on a left-pane column button (via arrow nav, Tab, or a mouse click) drives `filterActiveCol` via a `focusin`-style listener, so the left pane behaves like a listbox rather than needing a separate activate step.

Vanilla implements all of this itself (a generic `handleKeyDown` block scoped to whichever `.dt-dd` is open, `handleFilterColFocus`); React/Vue share a generic panel-level roving-nav mechanism driven by `data-dd-search`/a shared row selector instead of duplicating vanilla's per-dropdown string-building.

Full implementation detail (including the reasoning for why the search-input-then-rows ordering must follow DOM order, not array-concatenation order) is in [docs/dropdown-keyboard-nav.md](docs/dropdown-keyboard-nav.md).

### Aggregation in group headers

`ColumnDefBase.aggregate` accepts `'sum' | 'count' | 'avg' | 'min' | 'max'` or a custom `(rows: TRow[]) => unknown` function. When any active column defines an aggregate, a secondary `dt__agg-row` / `dt-agg-row` row is rendered below each group header with per-column values. `computeAggregate(col, rows)` in core handles all built-in types; `col.format` is used for display when available, passed `sampleRow` (see "Pagination") rather than `rows[0]` since `rows` can legitimately be empty for a header rendered right at a page boundary. The aggregate row is always visible regardless of collapse state — for a collapsed group `rows` is the full group (backfilled by `paginateVisibleGroups`), for an expanded/split group it's whatever chunk of the group is visible on this page (see "Pagination" for why these differ).

### Visual hierarchy (header / group rows / stripes)

Header, group header rows, aggregate rows, and the odd-row stripe used to all share one `--color-background-secondary` token with no other distinguishing treatment, making them hard to tell apart at a glance. Each now reads as its own tier:

- The table header alone uses a new token, `--color-background-tertiary` (defined in `theme.ts`'s `LIGHT_THEME`/`DARK_THEME` alongside the existing tokens, and picked up automatically by `renderThemeCss()`), plus a heavier `1px` (was `0.5px`) bottom border — the strongest visual anchor, sitting above everything else.
- Group header rows keep `--color-background-secondary` (unchanged) but gain a `3px solid` left accent border and switch their text from `--color-text-secondary` to `--color-text-primary` at `font-weight: 600` (was `500`/secondary) — previously group rows used the same muted styling as the header, which made them read as faded captions instead of bold section dividers. The left border is set on the `<tr>` itself (not a `<td>`) and relies on `border-collapse: collapse` (already set on all three adapters' `<table>`) to render at the table's left edge regardless of which cells happen to be present (checkbox column optional, etc).
- The odd-row stripe now uses `color-mix(in srgb, var(--color-background-secondary) 45%, transparent)` instead of the token at full strength, so plain alternating rows read as a subtle texture rather than competing with group rows for the same gray. Hover (`onRowClick` set) and selection stay at full strength, so they still read as a stronger, more "active" cue than the passive stripe.
- Aggregate rows are intentionally left unchanged (still muted `--color-text-secondary`, `font-weight: 500`) — once the group row above it went bold/primary, the contrast between "section title" and "summary line" falls out for free with no separate change needed.

### i18n

`DataTableLabels` in `packages/core/src/types.ts` defines static string keys and 5 formatting functions (`rowCount(filtered, total)`, `groupCount(n)`, `groupLabel(index)`, `rowsInGroup(n)`, `pageOf(page, total)`). `DEFAULT_LABELS` is English. Both adapters accept a `labels?: Partial<DataTableLabels>` prop/option that is shallow-merged over the defaults.

Adding a new locale to `locales.ts` makes it available from both adapters with no further changes.

### View persistence

`TableViewState` in `packages/core/src/view.ts` is a serializable snapshot of everything a user can change through the UI — `visibleCols`, `columnOrder`, `sorts`, `filters`, `rangeFilters`, `groupBy`, `collapsedGroups`, `page`, `pageSize`, `searchQuery` — except `selection`, which is tracked by object identity and isn't meaningful to persist or share. All fields are optional: a partial view (e.g. just a sort) applies on top of whatever defaults are already in place.

`encodeViewState`/`decodeViewState` serialize a view to/from a compact, URL-safe string, kept small by three rules: 1-letter wire keys, tuples instead of objects (`sorts` as `[key, dirFlag]`, `filters` as `[key, values[]]` pairs, `rangeFilters` as `[key, min, max]`), and omitting any field at its natural default (empty array/object/string, `page: 1`, `pageSize: 0`) — most shared/persisted views differ from the defaults in only one or two fields. The string itself is base64url of that compact JSON — hand-rolled (not `btoa`/`TextEncoder`) since core targets ES2020 with no DOM/Node lib and must run identically in browsers, Node (SSR), and the vanilla adapter; base64url is cheaper here than `encodeURIComponent(JSON.stringify(...))` because JSON's punctuation would otherwise be percent-escaped at 3 chars apiece.

Each adapter's `useTableState`/`createDataTable` exposes `getViewState()` (builds a `TableViewState` from current state, omitting `visibleCols` when it equals the full column set) and `setViewState(view)` (applies a partial view, resetting every field absent from it back to its default — so it's idempotent with `getViewState`). `setViewState` falls back to the default visible columns if `view.visibleCols` contains no keys present in the current `columns` (e.g. a stale shared link against a changed column set). The vanilla adapter also exposes `onViewChange(cb)` since it has no reactivity system for external code to hook into; it fires after any UI action that changes the view, but not on selection-only changes.

Actually writing a view to `localStorage` or the URL is opt-in, via separate helpers rather than baked into the main hook (`persistence.ts` in each adapter package — Solid included, promoted from a hand-rolled implementation that used to live only in its demo):

- `usePersistedView(table, storageKey)` (React/Vue/Solid) / `persistViewToLocalStorage(table, storageKey)` (vanilla) — loads on mount/init, saves on every change. `storageKey` may be `undefined` to no-op (React/Vue only — needed so `usePersistence` below can call this hook unconditionally per the Rules of Hooks; Solid/vanilla don't have that constraint but accept `undefined` too, for a consistent signature across all four).
- `useUrlView(table, options?)` (React/Vue/Solid) / `syncViewToUrl(table, options?)` (vanilla) — loads from the `view` query param (configurable via `paramName`) on mount/init and on `popstate`, writes back via `history.replaceState` (not `pushState`, so per-change sort/filter/etc. tweaks don't spam browser history).
- `usePersistence(table, options?)` (React/Vue/Solid) / `persistView(table, options?)` (vanilla) — combines both of the above behind one `{ storageKey?, paramName? }` object instead of passing the same values separately to `usePersistedView`/`useUrlView`/`resetView` (a typo'd/forgotten key at any one of those three call sites is a silent bug). Returns `{ reset }` (vanilla additionally returns `unsubscribe`, matching its own `persistViewToLocalStorage`/`syncViewToUrl`), a `resetView(table, options)` already bound to the same options.

Both URL helpers only apply state when the param is actually present and decodes successfully — an absent or malformed param leaves whatever state is already there alone rather than forcing a reset to defaults. This matters when composing both helpers (as the demos do): on a plain reload with no `view` param, the URL helper's hydration step must not clobber the localStorage-restored view with an empty one. For the same reason, once a view returns to its construction-time defaults, `usePersistedView`/`persistViewToLocalStorage` removes the `localStorage` key entirely rather than writing an encoded-but-empty value — matching `useUrlView`/`syncViewToUrl`'s existing behavior of deleting the query param in that case, so `resetView`'s own `removeItem` can't be immediately undone by a persistence hook's next save.

### DataTableView — reaching state that `<DataTable>` can't expose (React/Vue; Solid follows the same idea, see "Solid package" above for `DataTable.tsx`/`DataTableProps`)

`usePersistedView`/`useUrlView` (and any other external code wanting imperative selection control, e.g. `table.selection.clear()`) need the actual `useTableState` return value — but `<DataTable>` builds one internally and never exposes it, so nothing outside the component can reach it. Rather than bolt on an escape hatch (a `forwardRef`/`useImperativeHandle` or `defineExpose` handle), the render layer itself was split out: `DataTableView` takes a `table: TableState<TRow>` prop (the `useTableState` return value, type-aliased as `TableState<TRow>` and exported from `useTableState.ts`) instead of calling the hook itself, and `DataTable` is now a thin wrapper — `useTableState(...)` + `<DataTableView table={table} .../>`.

This is fully declarative (no ref timing/SSR concerns) and stays complete automatically as `useTableState` grows — passing the whole object through means every current and future action/derived value is reachable via `table`, with no separate "exposed API" surface to keep in sync by hand. A consumer who needs external control does exactly what the "Custom layout"/headless demos already did, just rendering the built-in UI instead of a hand-rolled one:

```tsx
const table = useTableState(data, columns)
usePersistedView(table, 'my-table-view')
return <DataTableView table={table} data={data} columns={columns} />
```

`DataTableViewProps<TRow>` (in each adapter's `types.ts`) holds every prop `DataTableView` needs beyond `table` — `data` (for the unfiltered row count) and `columns` (for filter/sort/group panels, which list _all_ columns, not just active ones) can't be derived from `table` alone, so they're passed separately, same as `<DataTable>` already required them. `DataTableProps` is `Omit<DataTableViewProps<TRow>, 'table'> & { defaultVisibleColumns?, labels?, defaultPageSize? }` — the three fields that only make sense at `useTableState` construction time.

Vue's split has one extra wrinkle around `onRowClick`/`rowClick` detection (see Row click above): `DataTableView`'s `isRowClickable` check reads its own `vnode.props.onRowClick`, but `DataTable` always forwards the `row-click` emit unconditionally (clicking a row always emits, matching the emit's own semantics, regardless of whether anyone's listening) — so if `DataTableView` self-detected off its incoming listener, it would always see one and always show clickable styling. `DataTable` instead does its own `vnode.props` check (reflecting whether _its_ caller passed a listener) and forwards the result down as an explicit `rowClickable` prop, which `DataTableView` prefers over self-detection when present; `DataTableView` used directly (no wrapper) falls back to self-detection since there's no wrapper to supply the prop.

### Performance

Given pagination, the DOM only ever renders `pageSize` rows regardless of dataset size — so for huge datasets (100k–1M+ rows), the cost lives entirely in `packages/core`'s pure functions, which run over the _full_ dataset on every relevant state change (sort, filter, search, group), not just the visible page.

- **Benchmarks**: `packages/core/src/__tests__/logic.bench.ts` (`npm run bench -w packages/core`, or `npx vitest bench` from `packages/core`) uses Vitest's built-in `bench()` against synthetic datasets at 10k/100k/500k rows (`bench-utils.ts`: 7 columns — string, number, date, and a 20-value low-cardinality category — generated with a seeded PRNG for stable runs). It covers `processData` (plain/filtered/sorted, per column type), `searchData`, `groupData`/`getVisibleRows`/`paginateVisibleGroups`, `computeStringValues`/`computeStringValueCounts` (all-columns vs. single-column), and `computeDateTree`. There's no CI regression gate on these yet — they're a manual profiling tool, run before/after a perf-sensitive change to check the actual impact rather than guessing.
- **`computeStringValueCounts` was the single biggest cost found**: ~15–17x faster at 500k rows/7 columns when scoped to one column via `targetKeys` instead of every filterable column — see "Filter dropdown" above for the fix (removed `stringValueCounts` from React/Vue's `useTableState` entirely; vanilla scopes it via `filterActiveKey` inside `derive()`).
- **`processData`'s sort** now precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) instead of recomputing them inside the comparator — see "Filter dropdown"'s date-sort note above. ~4x faster sorting a `type: 'date'` column at 500k rows.
- Sorting a plain numeric column is inherently ~1.5–2x costlier than sorting an equivalent string column in V8 for large arrays of objects (reproduced with a bare `(a,b) => a.price - b.price` comparator outside any library code) — this is a JS-runtime characteristic of comparing boxed doubles on objects, not something fixable in library code, so it isn't a benchmark target.
- Global search (`searchData`) and `groupData`/`getVisibleRows` scale linearly and stay well under the cost of a full re-sort even at 500k rows; they weren't found to need optimization for the "pagination keeps the DOM small" scenario this section is scoped to. Revisit if a future use case needs `pageSize: 0` (unpaginated) on a huge dataset, which would shift the bottleneck to DOM size instead.
- **The filter dropdown's checklist is a DOM-rendering cost, not a `packages/core` pure-function one** — the benchmark suite above doesn't exercise it, since it's specific to how many DOM nodes each adapter mounts, not to any core computation. A column with thousands of distinct values (a customer name, an order ID) used to mount one `<label>` per value regardless of scroll position; see "The flat checklist is virtualized" under "Filter dropdown" above for the fix (windowed rendering via `computeVirtualRange`).

### Cross-package resolution in development

Packages and demo apps resolve each other without a build step via:

- **`tsconfig.json` `paths`** — maps `@vates/data-table-core` → `../core/src/index.ts`, `@vates/data-table-core/locales` → `../core/src/locales.ts`, and (solid only, the sole consumer) `@vates/data-table-core/theme` → `../core/src/theme.ts` for type checking. `packages/vanilla/tsconfig.json` additionally maps `@vates/data-table-solid` → `../solid/src/index.ts`, so `tsc --noEmit` type-checks against solid's source without needing its `dist/` built first.
- **`vite.config.ts` `resolve.alias`** — maps `@vates/data-table-core` to the `packages/core/src` **directory** (not `index.ts`) so Vite's prefix substitution resolves the bare import and any sub-path (`/locales`, `/theme`) correctly. `packages/vanilla/vitest.config.ts` has the equivalent alias for `@vates/data-table-solid` → `../solid/src` — but only in the _test_ config, not `vite.config.ts` itself: unlike `@vates/data-table-core` (always external, so its production build never actually resolves the import), `@vates/data-table-solid` is bundled into vanilla's `dist/` (see "Vanilla package"), which means the production build genuinely needs its real built output, not source aliased in — hence the build-order requirement below.

In production, `npm run build` must run `core` before `react`, `vue`, and `solid` (all three import from its `dist/`), and `solid` before `vanilla` (which bundles `@vates/data-table-solid`'s own `dist/` into its own).

**Root `package.json`'s `"overrides": { "typescript": "^5.5.0" }` pins every `typescript` install in the workspace to the same 5.x line every package's own `devDependencies` already requests.** Without it, npm's peer-dependency resolution for `typescript-eslint`/`vue-tsc` (whose peer ranges extend into `typescript@6.x`) can hoist a lone `typescript@6.x` to the workspace root — harmless for eslint/vue-tsc themselves, but `vite-plugin-dts`'s cross-package `.d.ts` rollup (`react`/`vue`/`solid`/`vanilla` each importing types from `core/src/*.ts`, and `vanilla` additionally from `solid/src/*.ts`) picks up that hoisted 6.x copy for the analysis pass instead of each package's own pinned 5.9.3, and silently emits an **empty** `dist/index.d.ts` (`build` still exits 0 — this doesn't fail CI on its own, only a stale/empty type-check downstream would surface it). Confirmed by bisecting a real `npm update`; keep this override in place through future dependency bumps, and re-verify `packages/{react,vue,solid,vanilla}/dist/index.d.ts` is non-trivial after any change to `typescript`, `typescript-eslint`, `vue-tsc`, or `vite-plugin-dts`.

### Release process

`core`/`react`/`vue`/`vanilla`/`solid` share a single version-number pool (`CHANGELOG.md`'s `## [X.Y.Z]` headers cover the whole project, not one package each) — but a release only bumps and publishes the packages that actually changed, not every package unconditionally. A release touching only `packages/vanilla` publishes vanilla at the new version and leaves the others' `package.json` at whatever they were last published at; a release touching several packages together bumps all of those to the same new number. This means packages' versions can drift apart over time (e.g. vanilla at `0.9.0` while core/react/vue were still at `0.8.0`), and a later release that finally touches a lagging package again jumps it straight to whatever the shared pool is at by then, skipping the numbers in between — that's expected, not a mistake. Cross-package `dependencies` ranges (e.g. `"@vates/data-table-core": "^0.10.0"` in react/vue/solid/vanilla's `package.json`) always reference the dependency's own actual last-published version, not the release's shared number.

`@vates/data-table-solid` started its own independent version count at `0.1.0` when it was split out of `packages/vanilla`, rather than joining the shared pool immediately — it was a brand-new package with no prior published version to jump from. The `0.10.0` release folded it into the shared pool (it was bumped alongside the other four, and had accumulated enough of its own churn — including a breaking change — that tracking it separately no longer bought anything), so from `0.10.0` onward it follows the same shared-pool rules as the other four.
