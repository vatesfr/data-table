# CLAUDE.md

## Working style

When a request is ambiguous, ask clarifying questions **one at a time** before proceeding. Do not ask several questions at once.

Be concise: short responses, no filler, no restating what was just done.

Do not re-read a file that was already read in the current session unless it may have changed.

When there are multiple valid approaches to a request, present the options and trade-offs first and wait for a choice before starting implementation.

## Git workflow

- Make commits atomic: each commit should represent one logical change and pass tests on its own.
- Write descriptive commit messages that explain the _why_, not just the _what_. Use a short subject line and a body when context is needed.
- If a commit fixes a bug reported in a GitHub issue, include a closing keyword (e.g. `Fixes #N` / `Closes #N`) in the commit body. If the issue number isn't known, ask before committing rather than omitting it.
- Only create a dedicated branch and close it with a merge commit when a feature's development required multiple commits; otherwise commit directly to `main`.

## Development workflow

After implementing any new feature:

1. Review existing tests to see if they need updating; add new tests if the feature isn't covered.
2. Run `npm run test` to verify nothing regressed.
3. Run `npm run type-check` to verify no type errors.
4. Update the demos (`demo/react`, `demo/vue`, and `demo/vanilla`) to showcase the new feature if applicable.
5. Update any affected Markdown files (CLAUDE.md, READMEs).

## Architecture

This is an **npm workspaces monorepo** with four publishable packages and three demo apps:

```
packages/
  core/    — @vates/data-table-core    (pure TS, zero dependencies)
  react/   — @vates/data-table-react   (peer dep: react)
  vue/     — @vates/data-table-vue     (peer dep: vue)
  vanilla/ — @vates/data-table-vanilla (no framework dependency)
demo/
  react/   — Vite app consuming @vates/data-table-react
  vue/     — Vite app consuming @vates/data-table-vue
  vanilla/ — Vite app consuming @vates/data-table-vanilla
```

### Core package (`packages/core`)

All stateless logic lives here:

- **`types.ts`** — shared interfaces: `ColumnDefBase<TRow>`, `AggregateType`, `SortEntry`, `RangeFilter`, `DataTableLabels`, `DEFAULT_LABELS` (English default strings)
- **`logic.ts`** — pure functions: `getColumnValue`, `processData`, `searchData`, `groupData`, `sortWithinGroups`, `computeStringValues`, `computeStringValueCounts`, `computeAggregate`, `paginateData`, `calcTotalPages`, `toggleSort`, `replaceSort`, `appendOrToggleSort`, `cycleFilterValue`, `toggleGroupBy`, `toggleCollapse`, `getOrderedColumns`, `reorderColumn`, `moveColumnBy`, `getSortIcon`, `getSortIndex`, `countActiveFilters`
- **`locales.ts`** — built-in locale objects: `LABELS_EN`, `LABELS_FR`, `LABELS_ES`, `LABELS_DE`, `LABELS_PT`
- **`theme.ts`** — `LIGHT_THEME`/`DARK_THEME`/`renderThemeCss()`, consumed only by the vanilla adapter (see "Vanilla package"'s `styles.ts`) since React/Vue theme via inline styles/scoped CSS instead. Not re-exported from core's main `index.ts` barrel — React/Vue consumers importing `@vates/data-table-core` directly would otherwise see theme APIs with no relevance to them. Reachable via its own `@vates/data-table-core/theme` sub-path export, same pattern as `/locales`.

The internal `asRecord(row: object): Record<string, unknown>` helper exists because the generic constraint is `TRow extends object` (not `Record<string, unknown>`) — TypeScript interfaces lack index signatures so the wider constraint is needed, and `asRecord` lets internal logic access arbitrary keys.

### React package (`packages/react`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase` with `render?` and `renderFilterLabel?` (render props)
- **`useTableState.ts`** — wraps core logic with `useState`/`useMemo`; exposes all state, derived values, and actions; also exports `TableState<TRow>` (`ReturnType<typeof useTableState<TRow>>`)
- **`DataTableView.tsx`** — the actual render layer; takes a `TableState<TRow>` (the `useTableState` return value) as a `table` prop instead of calling the hook itself
- **`DataTable.tsx`** — thin wrapper: calls `useTableState` internally and renders `<DataTableView table={table} .../>`

Cell rendering priority: `col.render(value, row)` → `col.format(value)` → `String(value)`. Group headers use the same `cellValue()` function so custom renders apply there too.

### Vue package (`packages/vue`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase` (no render props; customization is via slots)
- **`useTableState.ts`** — same purpose as React but different signature: `useTableState(data, columns, options?)` where `options` is `{ defaultVisibleColumns?, labels?, defaultPageSize? }`; uses `ref`/`computed` and accepts `MaybeRefOrGetter` for reactive inputs; also exports `TableState<TRow>` (`ReturnType<typeof useTableState<TRow>>`)
- **`DataTableView.vue`** — the actual render layer; uses `<script setup lang="ts" generic="TRow extends object">` and takes a `TableState<TRow>` as a `table` prop instead of calling `useTableState` itself
- **`DataTable.vue`** — thin wrapper: calls `useTableState` internally, renders `<DataTableView :table="table" .../>`, and forwards its own slots straight through
- **`components/Dropdown.vue`** — self-manages open/close state and exposes it to `#trigger` slot

Vue customization uses **scoped slots** instead of render props:

- `#cell-{key}` — custom table cell; slot scope: `{ value: unknown, row: TRow }`
- `#filter-{key}` — custom filter dropdown label; slot scope: `{ value: string }`
- `#group-{key}` — custom group header value; slot scope: `{ value: unknown, row: TRow }`

### Vanilla package (`packages/vanilla`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase<TRow>` with `render?: (value, row) => Node`
- **`styles.ts`** — CSS string injected once into `<head>` via a `<style data-dt-styles>` tag on first `createDataTable` call; imports `renderThemeCss` from `@vates/data-table-core/theme` (not the main package entry — see "Core package")
- **`index.ts`** — exports `createDataTable(container, options)` which returns `{ setData, setColumns, destroy }`

`createDataTable` manages all state in a closure, re-renders via `innerHTML` on every state change, and uses **event delegation** (single `click`/`input`/`change` listener on the container). All interactive elements carry `data-action` attributes; the handler dispatches on those. Dropdowns open/close state is tracked in the closure (`openDropdown: string | null`) and re-rendered into the HTML on each update.

Focus is saved/restored across re-renders (via `data-focus-key` attributes on range filter inputs and the search input) so typing doesn't lose cursor position. The `.dt-table-wrap` scroll position is saved/restored the same way — read before `container.innerHTML = html` and reapplied after — so a scrolled table doesn't jump to the top on every state change (sort, filter, page, `setData`), which matters most for streaming/live-update data.

Cell customization: `col.format(value, row) → string` for plain text (always HTML-escaped), or `col.render(value, row) → Node` for arbitrary DOM (images, links, badges — see GitHub issue #3) — `render` takes priority over `format` when both are set, mirroring React's `render`/`format` priority. `render` support is threaded through the single `formatStr(v, row, col)` helper, so it applies uniformly to data cells, group header values, and aggregate cells (same column-reuse pattern as React's `cellValue()`).

Since `render()` builds the whole table as one HTML string and assigns it via `innerHTML` in a single shot, a real DOM node can't be inlined into that string. Instead `formatStr` leaves a numbered placeholder (`<span data-render-slot="N">`) and queues `{ id, col, value, row }` into a `pendingRenders` array (reset at the top of each `render()` call); once `container.innerHTML = html` runs, a follow-up pass resolves each placeholder via `container.querySelector('[data-render-slot="N"]')` and `slot.replaceWith(col.render(value, row))`. This keeps the callback API DOM-native (matching React's `render`, no second string-based dialect to learn) without restructuring the rest of `render()` away from its string-building model.

### Row selection

Selection lives in `useTableState` in both adapters. Key design notes:

- Selection is tracked as `Set<TRow>` by **object identity** — no `rowKey` dependency. Row references must be stable (the same object in memory) across re-renders for selection to persist through sort/filter changes. `rowKey`'s own JSDoc (all three adapters' `types.ts`) and each README's props table now spell this out explicitly — it's a rendering-identity hint only (React `key`/Vue `:key`/vanilla DOM key), not a selection identifier the way "row key" reads in most other table libraries (TanStack Table, AG Grid, MUI); this was previously undocumented and easy to assume otherwise.
- React uses `useState<Set<TRow>>` (always assigns a new Set on mutation). Vue uses `shallowRef<Set<TRow>>` — `ref` would cause `UnwrapRefSimple<TRow>` type errors because Vue's deep-unwrap conflicts with generic constraints.
- `selectedRows` is `processedData.filter(r => selection.has(r))` — rows removed by filtering disappear from `selectedRows` but stay in `selection` and reappear if the filter is cleared.
- `toggleSelectAll(rows: TRow[])` takes an explicit row array — the caller decides what to pass (typically `processedData`, not just the current page). It deselects all if any are currently selected (so an indeterminate _or_ fully-checked state clears on click, matching Gmail's select-all-checkbox convention), and only selects all when none are selected.
- Vue uses a local `vIndeterminate` directive (mounted + updated hooks) to set `el.indeterminate` reactively; React uses inline callback refs (re-run on every render because they are arrow functions).
- **Shift-click range selection**: `toggleRowSelection(row, shiftKey?)` takes an optional second argument. A plain click toggles just that row and remembers it as the anchor (an internal `selectionAnchor` closure/state var — not part of the public `TableState`, since nothing outside needs to read it). A shift-click computes the contiguous run between the anchor and the clicked row via core's `selectRange(items, anchor, target)` (an inclusive slice by `indexOf`, falling back to `[target]` alone if the anchor isn't in `items` anymore — e.g. sorted/filtered away) over `processedData` (the full filtered/sorted order, not just the current page, so a range can span a page boundary the same way it would in a scrollable list). The direction (select vs deselect) mirrors what a plain click on the _target_ row would do — i.e. it's based on the target's own checked state before the click — so shift-click can both extend and shrink a selection with the same modifier. Row checkboxes read the modifier off `onClick`/`@click` (a `MouseEvent`), not `onChange`/`@change`, since `change` events on checkboxes don't carry `shiftKey`; React additionally marks the checkbox `readOnly` to suppress its controlled-input-without-`onChange` warning.
- **Vanilla's imperative selection API**: React/Vue expose selection reactively (`selection`, `selectedRows`, `clearSelection`, `toggleSelectAll`, `toggleRowSelection` are all plain fields/functions on `TableState`, readable and callable anytime). Vanilla has no reactive state to read directly, so `DataTableInstance` gained matching methods — `getSelection()` (mirrors `selection`, not `selectedRows`: it returns every selected row including ones currently hidden by a filter, so `setSelection(getSelection())` round-trips predictably regardless of what's filtered), `setSelection(rows)`, and `clearSelection()` — so a consumer can wire an external "Clear selection" button or pre-select rows on load, the same things React/Vue could already do by calling `table.clearSelection()`/`table.toggleRowSelection(row)` directly outside the component. Both mutating methods call the existing `render()` (refreshing checkboxes from the mutated `selection` Set, the same pattern every internal selection handler already follows) and fire `onSelectionChange` with the current `_processedData`-filtered view, consistent with how every other selection change already notifies it.

### Row click

`onRowClick` (React/vanilla prop) / `rowClick` (Vue emit) fires when a data row is clicked, receiving the full row object and the native click event — no `rowKey` lookup needed. Group header rows, the aggregate row, and the selection checkbox cell never trigger it:

- **React** — the checkbox `<td>` already calls `e.stopPropagation()`, which is what keeps checkbox clicks from bubbling to the row's `onClick`. A `cursor: 'pointer'` inline style is applied to the row only when `onRowClick` is set. Since rows are styled with inline `style` objects (no stylesheet to hold a `:hover` rule), the hover highlight is JS-driven: `onMouseEnter`/`onMouseLeave` track a single `hoveredRow` state value, which the row's background ternary checks ahead of the stripe/selected fallback.
- **Vue** — the checkbox `<td>` uses `@click.stop` for the same reason. Since `rowClick` is a declared emit, Vue strips any `onRowClick` listener out of `$attrs` before it reaches the component, so presence can't be detected via `useAttrs()`; `getCurrentInstance()?.vnode.props?.onRowClick` reads the raw incoming listener instead, and drives the `dt__tr--clickable` class (which sets the pointer cursor and a `:hover` background rule — real CSS pseudo-classes work here because rows are styled via classes, not inline styles). `.dt__tr--selected` uses `!important` so a selected row's highlight always wins over the hover background.
- **Vanilla** — the row `<tr>` carries `data-action="row-click"` and `data-proc-idx`; the checkbox `<td>` carries `data-no-row-click`, which the `row-click` case in `handleClick` checks via `target.closest('[data-no-row-click]')` before invoking the callback (same guard pattern as `data-no-collapse` for group-row checkboxes). The `dt-tr--clickable` class is added whenever `onRowClick` is set; its `:hover` rule is declared in `styles.ts` _before_ `.dt-tr--selected .dt-td` so a selected+hovered row keeps the selected color on the equal-specificity tie. Firing the callback returns early without calling `render()` itself — it does update `focusedRow` (see "Keyboard navigation" below), but that's picked up by whichever render happens next rather than forcing one here.

Custom cell renders (React `render`, Vue `#cell-*` slots) that put clickable elements (buttons, links) inside a cell are responsible for calling `stopPropagation()` themselves if they don't want the click to also reach `onRowClick`.

### Header click sorting

Clicking a column header is a single-column-sort shortcut, distinct from the Sort dropdown (which remains the tool for building a deliberate multi-column sort with explicit priority/direction control):

- **Plain click** sorts by that column alone, discarding every other active sort — `replaceSort(sorts, key)` (core; named to read as distinct from `toggleSort`/`appendOrToggleSort` rather than a near-synonym, since all three sound alike despite very different effects on the rest of the multi-sort): if `key` is already the sole active sort, cycles its direction the same way `toggleSort` does (asc → desc → none); otherwise replaces `sorts` outright with a fresh `[{ key, dir: 'asc' }]`, regardless of what was sorted before.
- **Shift-click** adds the column to the existing multi-sort (ascending) if it isn't already part of it, or flips its direction in place if it is — `appendOrToggleSort(sorts, key)` (core). It deliberately never removes an entry: cycling through "none" would both surprise someone who only meant to flip direction, and — because the next shift-click would then re-add the column at the _end_ of the priority stack — silently lose its original position. Removing a column from the multi-sort stays a dedicated action: the active-bar chip's `×` or the Sort dropdown's own remove button.
- The Sort dropdown's own "add sort" entries keep using the original `toggleSort` (append, cycling to removal) — unaffected by either of the above, since those entries only ever fire on a column that isn't already active (already-active columns render as reorderable "active sort" rows with their own direction toggle/remove controls instead), so the removal branch is unreachable from there in practice.
- The header's own sort-icon index number (`1↑`, `2↓`, …) is only rendered once **more than one currently-visible header** is sorted — with just one, a bare `↑`/`↓` is enough and a lone "1" would be noise. "Visible" matters because a `groupBy` column keeps its own `sorts` entry (`sortWithinGroups` uses it to order the groups themselves) but has no `<th>` of its own once grouped (see "Grouped columns"); counting it toward the total, or numbering off its raw position in `sorts`, could show a stray "2" on the only visible sorted header with nothing numbered "1" to match. Each adapter filters `sorts` down to entries whose key is still in `activeColumns` before computing both the threshold and the index itself, local to the header-row render (React: an inline `headerSorts` computed via an IIFE in the `activeColumns.map`; Vue: a `headerSorts` computed plus `isHeaderSorted`/`headerSortLabel` helpers; vanilla: a `headerSorts` local computed once before the header loop in `render()`) — this doesn't touch the sort dropdown's or active-bar chip's own numbering, which still reflects every entry in `sorts` regardless of header visibility.
- `replaceSort`/`appendOrToggleSort` are exposed from `useTableState` (React/Vue) alongside the pre-existing `toggleSort`; vanilla wires them directly into the header `<th>`'s click handler (`data-action="header-sort"`, distinct from the dropdown add-button's `data-action="toggle-sort"`), reading `e.shiftKey` to choose between them.
- **`ColumnDefBase.defaultSortDir?: SortDir`** (default `'asc'`) picks which direction a _fresh_ sort on that column starts at — e.g. `'desc'` for a "last modified" date column or a score/count column, where descending is the more useful first click. It's opt-in per column only; there's no type-based inference (a `type: 'date'` column doesn't default to `'desc'` on its own), to avoid a surprising behavior change for existing columns. `toggleSort`/`replaceSort`/`appendOrToggleSort` (core) all take it as an optional 3rd `defaultDir` param and cycle `none → defaultDir → opposite(defaultDir) → none` instead of the fixed `none → asc → desc → none` — so a `'desc'`-default column's first click sorts descending, second click flips to ascending, third clears it. Only where a _new_ sort entry starts (and which direction its cycle removes from) changes; an already-active entry's `toggleSortDir` flip (chip click, Sort dropdown row) is unaffected, since it just alternates whatever direction is already set regardless of where the cycle began. Each adapter looks up `columns.find(c => c.key === key)?.defaultSortDir ?? 'asc'` at the call site (React/Vue's `useTableState` actions; vanilla's `header-sort`/`toggle-sort` handlers) and passes it through — no new state, no persistence changes (`TableViewState.sorts` already stores each entry's resolved `dir` explicitly).

### Keyboard navigation

Rows use a **roving tabindex**: exactly one item — a data row _or a group header row_ — is a Tab stop at a time (`tabIndex`/`tabindex` `0`, the rest `-1`), arrow keys move it. This only covers the table body; toolbar buttons, dropdowns, and filter checkboxes are already native focusable elements and needed no changes.

- **`getVisibleRows(groups, collapsedGroups, defaultCollapsed)`** (core) flattens `groupData`'s result into a `VisibleItem<TRow>[]` sequence — `{ kind: 'row', row, groupKey }` or `{ kind: 'group', key }` — in display order: a group header for every group (even a collapsed one, so it stays reachable to re-expand), followed by its rows unless it's collapsed. This is the Up/Down/Home/End order: a collapsed group's rows are not valid arrow-key targets, but its header always is, and expanding/collapsing a group changes what else is reachable. Called with the _full_ grouped data (see "Pagination"), not just the current page's slice. `isSameVisibleItem(a, b)` (core) compares two items — rows by object identity, groups by key — and `indexOfVisibleItem(items, target)` finds `target`'s index (or `-1`), used everywhere a stored focus target needs to be relocated inside a freshly-computed sequence.
- Each adapter derives `navigableItems` from `getVisibleRows`'s result by filtering out row items when the table isn't otherwise interactive: `items.filter(item => item.kind === 'group' || rowNavEnabled)` where `rowNavEnabled = selectable || !!onRowClick`. Group headers are **never** filtered out this way — collapsing a group is already a plain click away regardless of `selectable`/`onRowClick`, so a header is always a valid Tab stop whenever grouping is active, even in an otherwise display-only table.
- The currently-tabbable item is tracked as `focusTarget: VisibleItem<TRow> | null` — ephemeral UI state, same category as `selectionAnchor`/`hoveredRow`, not part of `TableViewState`. Each render derives `effectiveFocusTarget = focusTarget && indexOfVisibleItem(navigableItems, focusTarget) !== -1 ? focusTarget : navigableItems[0]`, the same "stale state still renders something sane" fallback used for `filterActiveKey`/`visibleCols` — so a focused item that scrolls out of view (sorted/filtered/grouped away, or its group collapsed) self-heals to the first navigable item instead of leaving no tab stop at all.
- **Key bindings**, handled on the row/header itself: `ArrowUp`/`ArrowDown` move focus one item (row or group header, whichever is next in `navigableItems`); when pagination is active, moving past the current page's first/last item crosses into the previous/next page instead of clamping there (see "Crossing page boundaries" below). `Home`/`End` jump to the first/last navigable item _of the current page_; `Ctrl+Home`/`Ctrl+End` (or `Cmd+Home`/`Cmd+End` on Mac) jump to the true first/last item across _all_ pages, matching the spreadsheet/ARIA-grid convention. On a **data row**: `Space` calls `toggleRowSelection(row, shiftKey)` (only when `selectable`); `Enter` fires `onRowClick`/`rowClick` (only when it's set), reusing the exact same handler the row's click already calls. On a **group header**: `Enter` always toggles that group's collapse state — unconditionally, mirroring the header's own `onClick`, since collapsing has never depended on `selectable`/`onRowClick` — and `Space` toggles the group's own select-all checkbox (only when `selectable`), mirroring a data row's `Space`. `Shift+ArrowUp/Down/Home/End` (and `Shift+Ctrl+Home/End`) additionally call `toggleRowSelection(target, true)` before moving focus, but only when the target is a row — landing on a group header via a shift-key press just moves focus, since a header isn't a rangeable selection unit at the row level. This composes for free with the existing anchor/`selectRange` logic (see "Row selection" above) with no new core primitive; it also means a shift-crossing selection already spans a page boundary correctly, since `toggleRowSelection`'s range computation runs over `processedData` (the full order), not the current page's slice.
- The row checkbox gets `tabIndex={-1}` / `tabindex="-1"` unconditionally when `selectable` — with row-level keyboard interaction (`Space`/`Shift+Arrow`) covering selection, a separately-tabbable checkbox would just be a redundant second Tab stop per row. Clicking it with a mouse is unaffected; only its presence in sequential Tab order changes. The group header's own select-all checkbox is left natively tabbable (no `tabIndex` override) since, unlike a data row, a header wasn't already part of a "roving" single-stop model before this feature — it wouldn't be a _redundant_ stop.
- `onRowClick` (React/vanilla) and the `rowClick` emit (Vue) are typed to accept `MouseEvent | KeyboardEvent` (`React.KeyboardEvent<HTMLTableRowElement>` in React) instead of just a click event, since `Enter` now fires the same callback with the keyboard event instead of a mouse event. Consumers that only read the row argument are unaffected; ones that read `event.shiftKey` or call `stopPropagation()` still work since both event types share those.
- Selected rows get `aria-selected` (`selectable` only) so the selection state is announced, matching native listbox/grid conventions, without adopting a full ARIA grid (`role="grid"`, per-cell focus) — this table's interactions are all row-level (selection, click, range), never per-cell, so a lighter row-level model was chosen over the heavier grid pattern. Group headers get `aria-expanded` (always, whenever grouping is active) reflecting their collapsed state, matching the standard disclosure-widget ARIA pattern now that they're keyboard-operable.

**Crossing page boundaries**: `navigableItems` covers only the _current_ page — `paginateVisibleItems(visibleItems, page, pageSize)` (core), filtered by the same `rowNavEnabled` rule. `visibleItems` (exposed from `useTableState`/`derive()`) already covers the _full_ filtered/grouped dataset (see "Pagination"), so reaching an item on another page (an ArrowUp/ArrowDown at the edge, or Ctrl+Home/Ctrl+End) is just re-slicing that same array for a different page — each adapter's `visibleItemsForPage(p)` helper is now a thin `paginateVisibleItems(visibleItems, p, pageSize).filter(...)`, no re-grouping needed (a meaningful simplification over the old paginate-then-group pipeline, which had to re-run `groupData`+`getVisibleRows` from scratch for every arbitrary page). `Ctrl`/`Cmd+Home` targets page `1`, `Ctrl`/`Cmd+End` targets `numPages`, taking the first/last item returned; a boundary ArrowDown targets `page + 1`'s first item, ArrowUp targets `page - 1`'s last item.

Per-adapter wiring:

- **React** — `focusTarget` (`useState`) plus a `rowRefs = useRef(new Map<TRow | string, HTMLTableRowElement>())` populated via each row/header's callback `ref` (rows keyed by object identity, headers by their group key string — a plain `Map` allows both key types with no collision risk). Moving focus calls `.focus()` on the target's ref synchronously inside the key handler (not via an effect) — the item is already mounted, so this is simpler than waiting a render cycle. `onFocus` (bubbling in React, unlike the native `focus` event) keeps `focusTarget` in sync when focus lands on an item via Tab or via a mouse click on its (now `tabIndex={-1}`) checkbox. Crossing a page boundary calls `setPage`, whose state update re-renders asynchronously — the item to focus can't be reached via a ref until that render commits, so it's stashed in a `pendingFocusTarget` ref and a `useEffect` keyed on `[page]` calls `focusItem` once the effect fires (i.e. after the new page's items are mounted).
- **Vue** — the same shape: `focusTarget` (`shallowRef` — not `ref`, since `VisibleItem<TRow>` embeds a `TRow` field and Vue's deep-unwrap conflicts with the generic constraint here the same way it does for `selection`, see "Row selection"), a plain (non-reactive) `rowRefs` `Map<TRow | string, HTMLTableRowElement>` populated via a function `:ref`, and `@focusin` (which, unlike `@focus`, bubbles natively) instead of React's auto-bubbling `onFocus`. Crossing a page boundary mirrors React's `pendingFocusTarget` + effect approach, but as a plain closure variable plus `watch(page, ..., { flush: 'post' })` — `flush: 'post'` (rather than the default `'pre'`) is what makes the callback run after the DOM actually updates, so `rowRefs` already holds the new page's items by the time it fires.
- **Vanilla** — `focusTarget` is a closure var. `_visibleItems` (the full flattened sequence) is recomputed in `derive()` alongside `_groupedData`; `_navigableItems` (this page's slice of it) is recomputed every `render()`. The delegated `keydown` container listener (`handleKeyDown`) resolves the target item by checking which of `.dt-tr[data-proc-idx]` (a row) or `.dt-group-row[data-gkey]` (a header) is the closest ancestor of `e.target`, the same ancestor-lookup style `handleClick` already uses, so it fires correctly whether the keydown originated on the row/header itself or bubbled up from something inside it (a row's `tabIndex="-1"` checkbox, a header's select-all checkbox or collapse arrow). The checkbox click handler and the keyboard Space/Shift+Arrow path share one `applyRowSelectionToggle(row, shiftKey)` helper for rows and one `applyGroupSelectionToggle(gkey)` helper for a group's own select-all, so the mouse and keyboard entry points for each can't drift. Because every interaction here re-renders via `innerHTML` (destroying the previously-focused DOM node), `render()` gained a second focus-restore step alongside the existing `data-focus-key` one: it captures whether a `.dt-tr` or `.dt-group-row` had focus before the rebuild, then re-`.focus()`es the new node matching `effectiveFocusTarget` — by object identity for a row (`_processedData.indexOf(...)` + a `data-proc-idx` selector), or by iterating `.dt-group-row[data-gkey]` elements and comparing `.dataset.gkey` in JS for a header (an arbitrary group key could contain characters that break embedding it directly into a CSS attribute selector, the same reason the indeterminate-checkbox restore pass does the same lookup style) — without it, every arrow-key press would drop focus to `<body>` and silently stop working after one keystroke. Since `render()` runs synchronously (no framework re-render delay), crossing a page boundary needs no separate pending-focus mechanism: `moveFocus(target, targetPage)` just sets `focusTarget`/`page` and calls `render()` directly, and the existing focus-restore step above picks up the new item on that same call.

### Pagination

`pageSize: 0` disables pagination — all rows are returned on a single page. Both adapters default to `0`. `processedData` holds all filtered/sorted rows regardless of pagination (used for `toggleSelectAll`, total count, etc.).

`calcTotalPages`/`paginateData` (core) treat a non-finite `pageSize` (e.g. `NaN`, from an unvalidated input forwarded straight to `setPageSize`) the same as `pageSize <= 0` — pagination disabled, all rows returned — rather than propagating `NaN` into `Math.ceil`/`Array.prototype.slice` math, which would otherwise silently collapse the table to an empty page (`slice(NaN, NaN)` coerces both bounds to `0`). `paginateData` similarly falls back `page` itself to `1` when it's non-finite. React/Vue's `setPage`/`setPageSize` actions guard at the call boundary too — a non-finite argument is a no-op (state is left untouched) rather than being stored and then relied on to be caught downstream.

Grouping and pagination compose as: group the _full_ `processedData` → flatten to visible items (`getVisibleRows`, respecting collapse state) → paginate _that_ flattened header+row sequence → re-chunk the page's slice back into per-group form for rendering. This is a deliberate reversal of the more obvious "paginate data rows, then group whatever lands on that page" order — that order would let a page silently render `pageSize` data rows _plus_ however many header rows happened to land on top of them, so a `pageSize: 20` table with grouping active could visibly render 23+ rows. Counting header rows against the same budget as data rows means a page never renders more than `pageSize` rows total, at the cost of a group's rows now being able to split across a page boundary purely because the budget ran out mid-group (this already could happen in a milder form before — grouping was never sort-stable across the old pagination boundary either, so the same group value could already appear as two separate header occurrences on two different pages).

- **`paginateVisibleGroups(groupedFull, visibleItems, collapsedGroups, defaultCollapsed, page, pageSize)`** (core) is the re-chunking step, returning `PagedGroup<TRow>[]` — a `GroupResult` plus `continued: boolean` and `sampleRow: TRow | undefined`. It's the inverse of `getVisibleRows`, scoped to one page: `paginateData` (generic enough to reuse as-is for `VisibleItem<TRow>[]`) slices `visibleItems` for the page, then a single pass rebuilds group chunks from that slice.
  - **`continued`** is `true` when a chunk's header is a _repeat_ — the group's real header rendered on an earlier page and this page's slice starts mid-group (a `'row'` item whose `groupKey` doesn't match the currently-open chunk). Each adapter renders a `continued` chunk's header identically to a real one but appends `L.groupContinued` (e.g. "(cont'd)") next to the row count, so a returning header reads as a continuation rather than an unrelated duplicate group.
  - **A collapsed group's `rows`** are backfilled from the full group (`groupedFull`) rather than accumulated from the page slice, because a collapsed group contributes exactly one item to `visibleItems` (its header, no rows) — it never enters the paginated flow at all, so there's no "this page's portion" of it to fall back to. This also happens to be the more useful answer: collapsing a group is usually precisely so its aggregate/select-all reflect the _whole_ group, not whatever fraction of it shares the current page. An expanded group's `rows`, by contrast, really is just the chunk visible on this page — consistent with the pre-existing behavior that a group's aggregate was never a true full-dataset total, only ever scoped to whatever page/slice it appeared in.
  - **`sampleRow`** is a representative row for the group (its first row in `groupedFull`, or the row itself for an ungrouped chunk), always present when `key` is non-null — independent of whether `rows` happens to be empty for this specific page occurrence. This matters because a header can legitimately be the very last item of a page's budget with zero of its own rows following until the next page (an expanded group whose first row is pushed to the next page); rendering the header's groupBy value (via the column's real accessor/formatter) and the aggregate row's `col.format(v, row)` both need _some_ row to read from, and `rows[0]` would be `undefined` in exactly this case. Every adapter reads `sampleRow` (never `rows[0]`) for these two things, while `rows` itself remains correct for the checkbox/aggregate-computation purposes above.
- **`paginateVisibleItems(visibleItems, page, pageSize)`** (core) is the equivalent per-page slice for keyboard navigation (see "Keyboard navigation"): a plain `paginateData` slice, except when that slice starts with row items whose group header rendered on an earlier page — then a synthetic `{ kind: 'group', key }` item is prepended so the repeated ("continued") header, a real focusable row once rendered, is a valid Tab stop here too.
- **`pagedData`** (still exposed from `useTableState`/`derive()`, unchanged type `TRow[]`) is now derived from the same paginated flattening — `paginateData(visibleItems, page, pageSize)` filtered to `'row'` items and mapped to `.row` — rather than a flat data-row slice, so it reflects the data rows actually visible on the page (fewer than `pageSize` whenever headers share the budget), not a fixed-size chunk of `processedData`.
- **`numPages`** is `calcTotalPages(visibleItems.length, pageSize)` — `visibleItems.length` (headers + visible rows) rather than `processedData.length`, so it grows when groups are expanded and shrinks when they're collapsed. Toggling a group's collapse state can therefore change `numPages` out from under the current `page`; this is handled the same way a filter change already could shrink `numPages` — no state reset on toggle, just the pre-existing `Math.min(page, numPages)` clamp applied wherever `page` is used.
- The toolbar's group count stat dedupes `groupedData` by `key` before counting (`new Set(groupedData.map(g => g.key)).size`) rather than using `groupedData.length` directly, since a split group's `continued` chunk would otherwise be counted as a second group.

The "Rows per page" `<select>`'s options are hardcoded to `[10, 20, 50, 100]` in each adapter, but a consumer's `defaultPageSize`/`setPageSize` isn't restricted to those four — a plain `<select>` bound to a value absent from its own `<option>`s can't select anything, so the browser falls back to displaying the first option, silently showing the wrong number while the actual `pageSize` (and the row count on screen) stays correct. `mergePageSizeOptions(options, pageSize)` (core) inserts `pageSize` into the option list (sorted) when it's missing, so the dropdown always has a matching option; each adapter calls it with its own `[10, 20, 50, 100]` base list rather than rendering it directly.

### Filter dropdown

Originally a flat list — one section header + checkbox list per string column, stacked in a single scrolling box — which became unusable for high-cardinality columns (hundreds of checkboxes; see GitHub issue #8). Now a master-detail layout:

- **Left pane** lists every filterable column, string/numeric/date unified: `filterableCols = columns.filter(c => c.filterable !== false)`, in column order. A dot indicator marks a column with an active filter.
- **Right pane** shows the selected column's controls — a search input + checklist for string columns, min/max range inputs for numeric columns, a Year › Month › Day tree for date columns (see below). Selected column defaults to the first filterable column (`filterActiveKey` falls back to `filterableCols[0]?.key`) so the detail pane is never empty on open.
- `filterActiveCol` (selected column) and `filterSearchTerms` (per-column search term) are local, ephemeral UI state — closure vars in vanilla, `useState`/`ref` in React/Vue — same category as `openDropdown`/`dragColKey`: never touches `filters`/`TableViewState`, not persisted or shared.
- `filterValuesBySearch(values, term)` (core) narrows a checklist by case-insensitive substring, called with the active column's `stringValueMap[col.key]` and its search term. No count threshold gates the search input's visibility — because only one column's checklist is shown at a time (not all of them stacked, as before), showing it unconditionally isn't visual noise the way it would've been in the old flat layout.
- A **select-all checkbox** sits on the same row as the search input — no visible label (to save vertical space in an already dense dropdown), accessible via `title`/`aria-label` (`L.selectAll`) instead. It toggles every value _currently listed_, i.e. post-search-narrowing, not the column's full value set: `toggleFilterAll(filters, key, values)` (core) deselects all given values if any is selected, else selects all of them — same clear-if-any-selected convention as row selection's `toggleSelectAll`. Indeterminate when some but not all listed values are selected.
- **Exclude filters** let a checklist value mean "rows without this" instead of just "rows with this" — the only way to narrow a multi-value column (tags) down to rows _lacking_ a value, since a plain include-only checklist can only ever narrow toward a value, never away from one. `filters: Record<string, Set<string>>` stays include-only and unchanged; a parallel `excludeFilters: Record<string, Set<string>>` (same shape, one Set per column) tracks exclusions, kept mutually exclusive with `filters` (a value is never in both at once). A plain click on a checklist value cycles it neutral → include → exclude → neutral via `cycleFilterValue(filters, excludeFilters, key, value)` (core), rendered as a native tri-state checkbox: unchecked, checked, or `indeterminate` (the browser's dash glyph, reused as the "not this" indicator with no extra markup). `processData`'s optional trailing `excludeFilters` param drops a row as soon as it carries _any_ excluded value — a NOR, independent of `col.multiMode` (which only ever governs the include side: "not tagged Action" must exclude the row the moment Action shows up, regardless of how includes combine). `computeStringValueCounts`'s facet counts and `countActiveFilters`'s badge count both take the same optional trailing param, mirroring how they already treat `filters`. Two batch include actions — select-all (`toggleFilterAll`) and shift-range select (`setFilterValues`) — stay include-only and unaware of `excludeFilters` by design (extending shift-range to exclude adds a second direction with no obviously-right UX); a caller that also tracks exclusion calls `clearExcludeValues(excludeFilters, key, values)` (core) alongside them to preserve the mutual-exclusion invariant when values move into `filters`.
  - **The master select-all checkbox** only ever calls `clearExcludeValues` on the "select all ON" branch, where it's unavoidable (every listed value is about to become included, and the invariant means a value can't land in both sets) — the "deselect all" branch calls only `toggleFilterAll` and leaves `excludeFilters` completely alone, since the checkbox's own checked/indeterminate render already reflects `filters` only (no visual concept of exclusion at all) and shouldn't silently clear state it never displayed. This wasn't the original wiring in any adapter — each first called `clearExcludeValues` unconditionally on both branches, which meant clicking an indeterminate select-all checkbox (some values included, unrelated to any excluded ones) silently cleared _every_ listed value's exclusion too, not just the included ones the checkbox was actually showing as selected — the same "action tied to one piece of state silently mutates an unrelated one" shape as the chip bug below.
  - **Each active-bar chip's × clears only the state that chip represents.** A column's include set, exclude set, and range filter (a date column can carry all three) each get their _own_ chip; vanilla's `clear-filter-key` action reads a `data-kind` (`'include' | 'exclude' | 'range'`, set per chip at render time) to know which one, React/Vue's `clearColumnFilter(key, kind)` takes the same `kind` as an explicit parameter (defaulting to `'include'`). This wasn't the original design: the per-column clear action first did an unconditional "full per-column reset regardless of which kind of filter is actually active" (so a date column's range chip and its checklist-tree chip cleared each other too), which read as an acceptable simplification when a column could carry at most an include set _or_ a range filter as alternatives — but once includes and excludes became two states a column can hold at once, clearing one silently dropping the other stopped reading as a reset and started reading as a bug (a real one a user hit — removing a negative filter chip removed the positive filter on the same column, and vice versa).
  - An exclude filter gets its own active-bar chip (`dt-chip--exclude` vanilla, `chipExclude` React, `.dt__chip--danger` Vue — all backed by the same new `--color-*-danger` theme tokens), distinguished by a "≠" prefix rather than a translated word — the same reasoning the sort/value-sort icons already use symbols instead of growing every locale file. `TableViewState.excludeFilters` persists/shares the same way as `filters` (wire key `x`).
  - **Per-adapter wiring quirks, some surfaced by moving from a 2-state toggle to a 3-state cycle:**
    - **Vanilla** renders the checkbox with `data-exclude` when excluded, since `indeterminate` isn't settable via an HTML attribute — a post-render pass (mirroring the date tree's own `data-indeterminate` convention) sets `.indeterminate = true` for every matching node. `buildFilterListInnerHtml`'s checklist markup is patched into the DOM from four separate call sites (the full `render()`, the scroll-only patch, the filter-panel height-correction pass, and the keyboard Home/End scroll-then-focus dance) — each one rebuilds fresh nodes that need the indeterminate fix-up applied again, since it's plain HTML with no persistent DOM identity across a patch.
    - **React** combines `filters`/`excludeFilters` into one `useState` atom (an object holding both, instead of two independent `useState` calls) — `cycleFilterValue` and the exclude-aware branch of `toggleFilterAll` both need to read _and_ write both maps together to decide the next state, and two independent setters each read from that render's own closure; two such actions called synchronously before a re-render (e.g. back-to-back in the same handler, or in a test's single `act()`) would each compute from the same stale pair otherwise. One atom means one functional updater always sees the latest committed value of both, the same guarantee `toggleFilter`/`setFilterValues` already got for free by only ever touching `filters` alone.
    - **Vue's plain `:checked` binding (no `v-model`) only rewrites the DOM property when the _bound value itself_ changes between renders** — unlike React, which force-syncs a controlled `checked` prop on every commit regardless of whether it changed. The old boolean toggle always flipped `checked` on every click, so this never mattered; but `cycleFilterValue`'s exclude→neutral transition changes `indeterminate` while `checked` stays `false` across both renders, so Vue would skip rewriting `.checked` and leave whatever the browser's own native click-toggle left in the DOM — a real bug hit in testing (a value cycled to neutral kept rendering as checked). `onFilterValueClick` now calls `event.preventDefault()` so the checkbox's visible state is exclusively driven by Vue's own binding, never by the native default action.
- The `numericRanges` label was removed — it only existed for the old layout's "Numeric ranges" section header, which the per-column detail pane has no equivalent of.
- Each checklist item shows a row count (see GitHub issue #9), computed by `computeStringValueCounts(data, filters, rangeFilters, columns, emptyLabel, targetKeys?)` (core). It's a _facet_: for a given column, counts are computed over rows narrowed by every _other_ active filter but not that column's own — so ticking a box in one checklist updates the counts shown in another, while a column's own displayed counts stay stable as its own boxes are ticked (unticking one value should never make the others look like they'd match fewer rows than they actually would once unticked). Implemented by re-running `processData` per column with that column's own filter entry deleted from `filters`, then tallying `getColumnValue`/`multiValues` per row. Rendered as a muted, right-aligned `<span>` after the value label (`.dt-filter-count` vanilla, `.dt__filter-count` Vue, inline style in React) — `aria-hidden` in React since it's a supplementary visual cue, not part of the checkbox's accessible name.
  - Since the master-detail layout only ever renders one column's checklist at a time (`filterDetailCol`), computing counts for every filterable column on every filter/search change is O(filterableColumns × rows) for O(rows) of actual use — measured as the single largest cost in the library on large datasets (see "Performance" below; ~15–17x at 500k rows/7 columns). `targetKeys` (optional 6th param) restricts which columns counts are actually computed for; `columns` must still be the _full_ list even when narrowing via `targetKeys`, since it's also used to resolve each _other_ active filter's own accessor. Vanilla passes `[filterActiveKey]` directly inside `derive()` (via a small shared `resolveFilterActiveKey` helper also used by `render()`), since `filterActiveCol` already lives in the same closure. React/Vue can't do this inside `useTableState` — `filterActiveCol` is UI-only state living in `DataTableView`/`DataTableView.vue`, not in `useTableState` — so `stringValueCounts` was removed from `useTableState`/`TableState<TRow>` entirely and is instead computed via a `useMemo`/`computed` inside the view layer, scoped to `filterDetailCol`, right next to where that state already lives.
- Values with a facet count of 0 are dropped from the checklist entirely, via `filterValuesByCount(values, counts, selected)` (core) — there's no point listing a value that can't currently match any row. The one exception: a value the user already has _selected_ stays listed even at 0, so a filter combination that's narrowed a value out of existence can still be found and unticked from the checklist itself, not just via "Clear filters". `filterValuesByCount` composes with `filterValuesBySearch` at each adapter's single `filterDetailValues`/`filteredValuesFor`/`_filterDetailValues` computation point, so select-all/indeterminate logic (which already operates on "currently listed values") automatically respects the same visibility rule with no separate wiring.
- `type: 'date'` columns get a spreadsheet-style (LibreOffice/Excel autofilter) Year › Month › Day tree instead of a min/max range (see GitHub issue #7) — deliberately chosen over a range so it reuses the exact-match `filters: Record<string, Set<string>>` checklist model rather than adding a second filter-state shape: a date column is simply never excluded from `computeStringValues`/`computeStringValueCounts` (previously gated out alongside `number`), and its checklist values (raw stringified dates, e.g. `"2023-05-14"`) are the tree's leaves. `computeDateTree(values, emptyLabel, dir, parseDate)` (core) parses each value with `parseDate` (default `(v) => new Date(v).getTime()`, overridable via `col.parseDate` — see below) and groups into nodes keyed by 4-digit year / 0-padded month / 0-padded day, ordering years/months/days ascending or descending per `dir` (default `'asc'`); values that don't parse land under a single trailing `emptyLabel` leaf instead of being dropped (always last, regardless of `dir`). Each node's `values: string[]` is every raw leaf value underneath it (a day node's own values if multiple raw values share a calendar day, rolled up through month/year) — so **no new toggle primitive is needed**: checking/unchecking any node (leaf or branch) is just `toggleFilterAll(filters, key, node.values)`, identical to the existing select-all-currently-listed action. `getDateTreeNodeState(node, selected)` (core) derives checked/unchecked/indeterminate from how many of `node.values` are selected, and `sumDateTreeNodeCount(node, counts)` (core) rolls up issue #9's per-value facet counts the same way. The tree is built from the column's already search/count-narrowed flat value list (`filterValuesByCount(filterValuesBySearch(...))`, same pipeline as the flat checklist) rather than the full unfiltered value set — so search and the 0-count-hides-the-value rule prune whole branches for free, with no separate tree-search function. Expand/collapse (`expandedDateNodes`, keyed by column then node `path`) is local ephemeral UI state, same category as `filterActiveCol`; a node with an active search term for its column is force-expanded regardless of click history, since the already-narrowed list is small enough to show in full. Each adapter renders the tree recursively — React: a local recursive function (no hooks inside, so no new component needed); Vue: `components/DateTreeItem.vue`, self-importing itself for recursion (safer across build setups than relying on filename-based self-reference) and duplicating the small set of scoped-CSS classes it needs, since a child SFC's `<style scoped>` doesn't inherit the parent's scope id; vanilla: a nested recursive string-building function inside `render()`, with two new delegated actions (`toggle-date-node`, `toggle-date-expand`) and `findDateTreeNode(nodes, path)` (core) so the click handler — which only has the DOM's `data-path`, not a closure over the node object — can re-derive `node.values` from the freshly recomputed tree. The expand arrow sits inside the same `<label>` as the node's checkbox in all three adapters; toggling it calls `preventDefault()`/stops propagation before the click reaches the label, otherwise the browser's native label→control forwarding would also fire the checkbox's own toggle. React's `renderFilterLabel` and Vue's `#filter-{key}` slot (custom per-value label rendering) are **not** applied to date-tree nodes — both are built around one raw checklist value, but a tree branch's label (a year/month) isn't a raw value at all, and even a day leaf's `values` can bundle more than one. Selecting many leaves at once (e.g. a whole year in one click) can put far more values into `filters[key]` than a user manually ticking checkboxes ever would, so the toolbar's active-filters chip caps its value list at 3 (`FILTER_CHIP_MAX`, one per adapter) and appends `L.moreValues(n)` for the rest — otherwise a fully-selected year would dump ~365 comma-joined ISO dates into one chip.
- **Sorting a `type: 'date'` column** (clicking its header, not the filter tree's own sort-order toggle below) parses values the same way as the filter tree instead of comparing them as plain strings (see GitHub issue #10) — `processData`'s sort calls the same `parseDate` (default/override) used by `computeDateTree`/`selectDateRange`, falling back to string comparison if either side fails to parse. `ColumnDefBase.parseDate?: (value: string) => number` lets a column override the default `(v) => new Date(v).getTime()` for formats `new Date` guesses wrong (e.g. `DD/MM` read as `MM/DD`); it's the single source of truth threaded through all three date-aware functions so the header sort and the filter tree never disagree on chronological order for the same column again. `processData`'s sort precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) rather than calling `getComparableValue` from inside the comparator — a comparator re-derives both sides on every comparison, so without this a `type: 'date'` column reparses the same row's date string O(n log n) times during a large sort instead of O(n); benchmarked at ~4x faster for a date-sorted 500k-row column (see "Performance" below).
- The same bug shape existed for `type: 'number'` columns: sort only compared numerically when the raw value was already a JS `number` (`typeof va === 'number'`), so a numeric _string_ (e.g. `"1200"`, common with CSV/JSON-sourced data) silently fell back to alphabetical comparison — while the range filter (`Number(rangeValue(r))`) and `computeAggregate` (`Number(getColumnValue(col, r))`) already coerced correctly, so sort alone disagreed. Fixed by a shared `getComparableValue(col, row)` (core, not exported) that centralizes "what does this column's value mean as a comparable" in one place instead of every call site re-guessing from the raw value's runtime type: `'date'` → `parseDate`, `'number'` → `Number`, anything else (untyped/computed columns) → the raw value unchanged, so a plain numeric column with no `type` set still sorts correctly off its already-numeric raw value. `processData`'s sort is now a single branch (`typeof va === 'number' && !isNaN(va) && ...` → numeric, else string), used for both `'number'` and `'date'` alike. `computeAggregate`'s existing `Number(...)` coercion was deliberately left as-is rather than routed through `getComparableValue` — it already coerces unconditionally regardless of `col.type` (so numeric aggregates were never actually buggy), and routing a `'date'` column through `getComparableValue` there would return a raw epoch number instead of `NaN`, changing `min`/`max` to return a number that a `col.format` written for the original string date wouldn't expect — a behavior change nobody asked for, not a fix.
- A **sort-order toggle** sits next to the search input (string/date columns only — numeric columns have no checklist to sort). For string columns it cycles a `ValueSort` (core type: `{ by: 'alpha' | 'count', dir: SortDir }`) through alpha-asc → alpha-desc → count-desc → count-asc → alpha-asc via `cycleValueSort` (core); `sortFilterValues(values, counts, sort)` (core) applies it as the last step of each adapter's `filterDetailValues`/`filteredValuesFor`/`_filterDetailValues` pipeline, after search/count-narrowing. For date columns the same button only toggles chronological direction via `toggleSortDir` (core), passed straight through as `computeDateTree`'s `dir` param — there's no count-based order for a tree of grouped branches, so `by` never applies there. `getValueSortIcon`/`getDateSortIcon` (core) render the button's compact label (e.g. `"ABC ↑"`, `"# ↓"`, or a bare `"↑"`/`"↓"` for dates). Per-column sort mode (`filterValueSort: Record<string, ValueSort>`) is ephemeral UI state, same category as `filterActiveCol`/`filterSearchTerms` — not part of `filters`/`TableViewState`, defaulting to `{ by: 'alpha', dir: 'asc' }` (matching `computeStringValues`'s existing default order) whenever a column has no entry yet — overridable per column via `ColumnDefBase.defaultValueSort?: ValueSort` (e.g. `{ by: 'count', dir: 'desc' }` for a high-cardinality tag column that reads better "most common first", or `{ dir: 'desc' }` for a date column's tree to open most-recent-year-first). `cycleValueSort` itself needs no change — it's a fixed 4-state rotation, not asymmetric like `toggleSort`'s 3-state one (see "Header click sorting"'s `defaultSortDir`), so a custom starting point still advances through all 4 states the same way. Each adapter's single `valueSortFor`/`findCol`-equivalent fallback point (`filterValueSort[key] ?? DEFAULT_VALUE_SORT`) becomes `filterValueSort[key] ?? columns.find(c => c.key === key)?.defaultValueSort ?? DEFAULT_VALUE_SORT` — the only call site that needed to change in each of the three adapters.
- **Shift-click range selection** works the same way as table rows (see "Row selection" above), for both the flat checklist and the date tree. Each adapter keeps a per-column anchor (`filterSelectionAnchor: Record<string, string>`, ephemeral UI state living alongside `filterActiveCol`/`filterSearchTerms` — the same dict serves both checklist values and date-tree node `path`s, since a column is never both types at once) and, on shift-click, applies `selectRange(filterDetailValues, anchor, value)` (core) against the column's already search/count/sort-narrowed value list. Unlike `toggleFilterAll`'s clear-if-any-selected convention, the direction here always mirrors what a plain click on the target value would do, so it needs its own core primitive: `setFilterValues(filters, key, values, selected)` sets `values` to `selected` unconditionally rather than deriving the direction from the whole group's state. Filter checkboxes read the modifier off `onClick`/`@click`/the vanilla `click` delegation (never `onChange`/`@change`), same reasoning as row selection.
- **Date tree range selection** is a chronological interval, not a sweep over rendered tree rows — the year/month/day grouping is purely a _display_ concern, layered on top of the same flat-list range-selection idea used elsewhere, just re-expressed in terms of dates instead of list positions. A rendered-row sweep (ranging across whatever's visually between the anchor and target, like the row/checklist cases) would be wrong here: a branch node's own `values` already roll up _every_ descendant date, so merely crossing an expanded year's row would pull in that whole year — including dates chronologically after the target (e.g. ranging `2023-02` → `2024-06` must never select `2024-07`, even though the `2024` year row sits "between" them once expanded). `selectDateRange(allValues, anchorNode, targetNode, parseDate)` (core) instead spans the earliest-to-latest raw value across both nodes' own `values` (parsed via the same `parseDate`, default/override shared with `computeDateTree`) and returns every value in the column's flat `allValues` list that parses into that interval — regardless of which branch it's grouped under, and independent of expand/collapse state entirely. `anchorNode`/`targetNode` can each be a leaf (day) or a branch (year/month): a branch endpoint's own min/max simply widens the interval to that whole unit (e.g. anchoring on a year spans its earliest to latest date). The anchor is still tracked as a `path` string (in the same per-column `filterSelectionAnchor` dict as the flat checklist), re-resolved to a node via `findDateTreeNode` on the next click, since node objects themselves are recreated every render. The select-vs-deselect direction mirrors what a plain click on the _target_ node would do — `getDateTreeNodeState(node, selected) !== 'checked'` — the same "clicked node's own new state" rule used for the flat checklist and for rows. Vue wires this by having `DateTreeItem.vue` emit `toggleNode: [node, event]` (rather than just `values: string[]`) so the parent `DataTableView.vue` (which alone holds `filterSelectionAnchor`) can decide plain-toggle vs range; React and vanilla already had direct access to both from within the same render/handler scope, so no signature change was needed there.
- **The flat checklist is virtualized** (windowed rendering) — a column with thousands of distinct values (e.g. a customer name) would otherwise mount one `<label>`/`<input>` per value regardless of how many are actually scrolled into view, which is a real perf cliff distinct from (and on top of) the facet-count cost above. `computeVirtualRange(scrollTop, viewportHeight, itemHeight, totalCount, overscan?)` (core) is pure, fixed-row-height windowing math — given how far a list is scrolled, it returns which item indices should actually be mounted (`startIndex`/`endIndex`, padded by `overscan` rows each side to avoid a blank flash on fast scroll), the pixel `offsetY` to position that window at, and the `totalHeight` so the real scrollbar still reports the full list's size. Each adapter renders the checklist as a scrollable container — a spacer `<div>` sized to `totalHeight`, and an absolutely-positioned inner `<div>` at `offsetY` holding only `values.slice(startIndex, endIndex)` — each row given an explicit `FILTER_LIST_ITEM_HEIGHT` (32px) inline/bound height so it matches what the math assumes exactly, rather than relying on the existing checklist item style's padding + line-height to happen to add up right. This is scoped to the flat checklist only — the date tree (see above) is naturally already "virtualized" in spirit by being collapsed/hierarchical by default, so it was left alone. Select-all, indeterminate, and shift-range selection all continue to operate on the _full_ (unwindowed) `filterDetailValues`/`_filterDetailValues` array — virtualization only changes what's mounted, never what's considered "currently listed" for those operations, so a fully-selected 50,000-value column still shows as `50000 / 50000 rows` even though only ~20 checkboxes were ever in the DOM.
  - **The checklist/date-tree viewport fills the panel's real height instead of a hardcoded constant** (GitHub issues #13/#14) — `.dt-filter-cols` (the column list on the left) and `.dt-filter-detail` (the checklist/date-tree side) are flex row siblings in `.dt-filter-panel`, so a `.dt-filter-cols` taller than the old 260px default stretches `.dt-filter-detail` with it via the flex row's cross-axis stretch; a checklist left at a hardcoded height then left dead space below it (#13), and the date tree — which had no height/scroll bound of its own at all — instead overflowed past the panel onto the page (#14). `.dt-filter-panel` also gained `overflow:hidden` in all three adapters as a safety net regardless, since `max-height` alone doesn't clip.
    - **Vanilla measures the actual rendered height.** `FILTER_LIST_DEFAULT_HEIGHT` (renamed from `FILTER_LIST_VIEWPORT_HEIGHT`, still 260) is now only the floor/initial-guess value; the closure var `_filterListHeight` holds the actual number in use, corrected at the bottom of every `render()` call (right after the dropdown-viewport-clamping pass, since both are "measure the freshly-rendered DOM and patch it directly" steps): the checklist/date-tree wrapper's height is reset to the floor, then the gap between `.dt-filter-detail`'s and the wrapper's `getBoundingClientRect().bottom` is measured and added back — resetting first (rather than only ever growing from the previous measurement) is what lets the wrapper shrink back down too, if `.dt-filter-cols` later becomes shorter (fewer filterable columns, a wider viewport). `_filterListHeight` persists across renders (like `_filterDetailValues`) so the _next_ render's initial HTML and `computeVirtualRange` call already use a close-to-correct number instead of visibly correcting after the fact every time. The date tree gained its own `.dt-date-tree-wrap` scrollable container (sized the same way, just no virtualization — the tree isn't windowed) since previously it had none at all.
    - **React/Vue fill it via CSS flex instead** — `filterDetail`/`.dt__filter-detail` became a flex column (`flex:1` on the pane itself, plus `flexDirection:'column'`/`flex-direction:column`) with the checklist (`filterList`/`.dt__filter-list`) and a new date-tree wrapper (`filterDateTreeWrap`/`.dt__date-tree-wrap`) both set to `flex:1; min-height:0; overflow-y:auto` instead of the old hardcoded height — so both fill whatever room `.dt__filter-detail` is actually stretched to, no JS measurement needed. `computeVirtualRange`'s viewport-height argument still passes the `FILTER_LIST_VIEWPORT_HEIGHT` constant (260) unchanged rather than a real measured number — safe here specifically because `.dt-filter-panel`'s own `max-height:380px` bounds how much taller the checklist can ever actually grow past that default (at most ~60-80px, once the search row/padding above it are accounted for), which is comfortably inside the 5-row/160px overscan `computeVirtualRange` already renders on each side — so the virtualized window always has enough pre-rendered rows to cover the real visible box. This is the same reasoning vanilla's own pre-fix state relied on (see #13's original "Workaround" note), except here it's a provable bound rather than an incidental one, which is why React/Vue didn't need vanilla's fuller measure-and-correct machinery. They didn't get that fuller treatment for a second reason too: React Compiler's lint rules (`react-hooks/set-state-in-effect`, `react-hooks/refs`, both `error` in `eslint.config.mjs`) rule out the two obvious ways to feed a `useLayoutEffect`-measured height back into a render — calling `setState` from inside the effect, or reading a ref's value during render — so a vanilla-equivalent fix would need a materially different mechanism than the one used elsewhere in this file for post-mount DOM correction (see "Dropdown viewport clamping", which sidesteps this by only ever mutating style/classList directly, never state). Vue has no such restriction (per "Filter dropdown"'s virtualization section above) but uses the identical CSS approach anyway, for consistency between the two framework adapters.
  - **React**: scroll position is tracked as `filterListScrollTop` state, updated via a `requestAnimationFrame`-throttled `onScroll` handler that reads the live `scrollTop` from `filterListRef.current` at rAF-fire time (not a value captured back in the triggering scroll event — several scroll events can fire before the callback runs, and only the latest position matters). Reset to 0 whenever the checklist's values change identity (switching column, or narrowing by search) — done inline during render (comparing against the previous render's key, React's own documented pattern for this) rather than in a `useEffect`, since the project's `eslint-plugin-react-hooks`/React Compiler config rejects a synchronous `setState` call inside an effect (`react-hooks/set-state-in-effect`) as a cascading-render risk. A _separate_ effect imperatively syncs the DOM's actual `scrollTop` to 0, keyed specifically on that same reset-key (**not** on `filterListScrollTop` itself) — keying it on `filterListScrollTop` instead re-applies a slightly-stale scroll position on every scroll-driven state update (not just on an actual reset), fighting the browser's own live native scroll and making the list appear to not scroll at all (a real bug hit in testing: `list.scrollTop` stayed pinned at 0 across repeated wheel ticks). React's `DataTableView.tsx` otherwise has zero manual `useMemo`/`useCallback` — it relies entirely on the React Compiler for memoization — so `stringValueCounts` and the virtual-range computation are plain `const`s, not wrapped in `useMemo`, to match.
  - **Vue**: same shape as React (a `ref` for scroll position, rAF-throttled `@scroll` reading the live `scrollTop`), but the reset naturally lives in a `watch([filterActiveKey, searchTerm], ...)` callback scoped to exactly those two triggers — Vue has no render-phase-state-update restriction the way React Compiler does, so this never had the "fights live scrolling" bug in the first place.
  - **Vanilla**: native `scroll` events don't bubble, so they can't join the existing single delegated `click`/`input`/`change` container listener — instead a dedicated `container.addEventListener('scroll', handler, true)` (capture phase) is used, since capturing fires on the way down to the target regardless of whether the event bubbles. Crucially, the scroll handler does **not** call the full `render()` (which rebuilds the _entire_ page via `innerHTML`, destroying and recreating `.dt-filter-list` itself) — if that happened mid-gesture, any further wheel/scrollbar input from the same continuous scroll would be left targeting a now-detached element and fall through to the page (a real bug hit in testing: the checklist stayed pinned at `scrollTop: 0` while the outer page scrolled instead). Instead, `buildFilterListInnerHtml(col)` — the same helper the full `render()` uses for the checklist's initial HTML — is called standalone to patch just `.dt-filter-list`'s own `innerHTML` (its children, not the element itself), leaving the scrollable element untouched and never interrupting the browser's native scroll on it. `_stringValueCounts` is cached as a persistent closure var (alongside the pre-existing `_filterDetailValues`) specifically so this scroll-only patch path can rebuild the rows without re-running the full `derive()`/`render()` pipeline.
- **`type: 'number'`/`type: 'date'` range filters get a slider alongside their 2 min/max inputs** — a "2 inputs + a slider" control, using the two-native-`<input type="range">`-thumbs-sharing-one-track trick (only the thumb itself is a hit target via CSS/pseudo-elements, so grabbing either one works regardless of z-order) rather than a fully custom drag widget, for free keyboard/touch accessibility and a small per-adapter diff. `computeValueBounds(data, col)` (core) is the slider's own `min`/`max` — the column's actual bounds across the full, unfiltered `data` (`'date'` via `parseDate`, `'number'` via `Number`), deliberately not `processedData`, so the slider's range doesn't shrink out from under a mid-drag user just because some other filter narrowed the row set; returns `null` when no row has a parseable value, in which case the slider is omitted and the two plain inputs keep working alone. Both thumbs share one change handler: the actual applied min/max is always `Math.min`/`Math.max` of both thumbs' live values (not "thumb A is always min"), so dragging one thumb past the other just swaps their visual roles on the next render instead of needing cross-clamping — the standard behavior for this widget trick. A date column's slider works in epoch-ms space (`step` = one day, `86400000`) and converts back to an ISO `YYYY-MM-DD` string (`setRangeFilter`'s existing value shape) on commit.
  - **The two plain min/max inputs default to the column's own data bounds when no range filter is set**, rather than sitting empty — a blank box gives no hint of what range is even meaningful for a given column, and it means the slider's thumbs (which already fell back to `computeValueBounds`) no longer visually disagree with the text inputs next to them. This is purely a display default: `rangeFilters[key]` stays unset until the user actually edits a value, so it doesn't light up the column's filter dot, doesn't add an active-bar chip, and isn't persisted in view state — functionally identical to before, just no longer blank. `formatRangeBound(n, col)` (one per adapter — vanilla/React module-level, Vue a `<script setup>` function) converts a bound (epoch ms for `'date'`, a plain number otherwise) back into the string shape `RangeFilter.min`/`.max` expects; it replaces what used to be an inline `fmt` closure duplicated between the slider's drag and commit handlers, and is now also the one place both the inputs' default value and the slider's `onChange` go through. Each adapter computes the column's bounds once per render (vanilla/React: a plain `computeValueBounds` call passed into the slider-building function as a parameter instead of it recomputing internally; Vue: a `filterDetailBounds` computed, with `rangeSliderFor` taking it as a parameter the same way) so the number/date detail pane's two consumers of "this column's bounds" — the inputs' default and the slider itself — never compute it twice.
  - **For a `type: 'date'` column, the range filter narrows the Year › Month › Day tree itself** ("runs before the tree"), not merely an independent filter ANDed onto the final row set — same idea as the existing search box, one step earlier in the same pipeline. `filterValuesByRange(values, range, parseDate)` (core) is `filterValuesBySearch`'s sibling: given the column's flat value list and its `rangeFilters` entry, it drops every value outside `[min, max]` (parsed via `parseDate`; a value that fails to parse is dropped whenever a bound is active, same "not part of any chronological range" reasoning as `selectDateRange`) — a no-op when the range has no bounds set, and safe to call unconditionally for every column type since a string/number column never populates `rangeFilters` in the first place. Each adapter's `filterDetailValues`/`filteredValuesFor`/`_filterDetailValues` pipeline calls it between `filterValuesBySearch` and `filterValuesByCount`, so both the flat leaf list and the tree built from it (`computeDateTree`) shrink together. `computeStringValueCounts`'s existing facet-count exclusion (own checklist filter excluded, but never `rangeFilters` — see above) already meant a column's own range filter was never excluded from its own counts either, so the tree's per-leaf counts narrow along with the visible leaves with no core change needed there.
  - `processData`'s range-filter loop is now type-aware instead of always coercing via `Number(...)`: a `type: 'date'` `rangeFilters` entry parses each row's value with `col.parseDate ?? defaultParseDate` (matching sort/tree), but always parses the _bounds themselves_ with the default ISO parser regardless of `col.parseDate` — the bounds are always `YYYY-MM-DD` from the range filter's native `<input type="date">`s, a fixed format the column's own custom parser (built for its own raw value format, e.g. `DD/MM/YYYY`) isn't meant to read. Every other column type keeps the original `Number(...)` behavior, unchanged.
  - **Vanilla is the one adapter that can't just fire a full `render()` on every slider `input` tick.** `render()` rebuilds the whole filter panel via `innerHTML`, and replacing the thumb `<input>` the mouse has mid-drag would abort the native drag (same reasoning column header drag-and-drop already avoids `render()` until `drop`, and the filter-list scroll handler avoids it entirely — see above). So the slider's `data-action="range-slider"` splits across two event types: `input` (fires continuously while dragging) only patches the fill `<div>`'s `left`/`right` inline style directly via a `.closest('.dt-range-slider')` lookup — no state write, no render; `change` (fires once, when the drag/click/keyboard-press actually commits) is where `rangeFilters` is actually updated and `render()` runs, safe now that the gesture has ended. React and Vue don't need this split at all — reconciling a controlled input's `value` prop on a state-driven re-render updates the same DOM node in place rather than destroying and recreating it, so a native drag's pointer capture is never disturbed; both just call the equivalent of `setRangeFilter` on every `input`/`@input` tick, identical to how the plain min/max text inputs already work.
  - **React has no stylesheet mechanism at all otherwise** (see "Cross-package resolution", the whole package is styled via inline `style` objects) — but a properly-styled thumb (round handle, hidden default track) needs `::-webkit-slider-thumb`/`::-moz-range-thumb`, pseudo-elements no inline `style` prop can reach. `ensureRangeSliderStyles()` injects one small, idempotent `<style data-dt-range-slider-styles>` tag into `<head>` on first mount (from a `useEffect`, so it never runs during SSR) — the same "inject once into `<head>`" precedent the vanilla adapter already uses for its whole stylesheet, deliberately scoped to just this one class name rather than a broader pattern change. Vue needs no such exception — `DataTableView.vue`'s existing `<style scoped>` block (and a new sibling `components/RangeSlider.vue`, mirroring `DateTreeItem.vue`'s existing self-contained-component pattern) can declare the same pseudo-element rules directly, the way `.dt__tr--clickable:hover` already does elsewhere in this file.

### Global search

`searchData(data, query, columns)` filters rows before `processData` runs — it matches any column's string value (using `col.format` when defined) case-insensitively against the query. Both adapters expose `searchQuery` state and a `setSearchQuery` action; `clearAll` resets it. The vanilla adapter restores focus on the search input across re-renders via `data-focus-key="search"`. `ColumnDefBase.searchable?: boolean` (default `true`) excludes a column from this match entirely — for a column whose underlying value isn't user-facing text (e.g. an image URL rendered via `render`), matching against it would surface rows on an accidental substring hit the user has no way to anticipate. Independent of `filterable`/`sortable`/`groupable`, which gate unrelated concerns.

### Computed columns

`ColumnDefBase.value?: (row: TRow) => unknown` decouples a column's cell value from its `key`. `key` stays a plain `string` (loosened from `keyof TRow & string`) and is only ever used as the column's identity — for sort/filter/group/visibility state and list keys. `value` governs how the cell value is actually read: omitted reads `row[key]` (unchanged default behavior), a function computes the value from the whole row — covering both simple aliasing (`value: (row) => row.name`) and true computed columns with no single backing property (`value: (row) => row.price * row.qty`). A string form (reading a named property instead of `key`) was considered and rejected: it's strictly redundant with the function form (which already covers aliasing, plus nested access like `value: (row) => row.address.city`, at no extra API cost), so it would just be a second way to do the same thing. `getColumnValue(col, row)` in `logic.ts` is the single accessor implementing this and is used everywhere a cell value is read: `processData`'s filter/range-filter/sort, `groupData`, `computeStringValues`, `searchData`, and `computeAggregate`. All of these already accepted a `columns` array except `groupData`, which gained one (`groupData(data, groupBy, columns, emptyLabel)`) so groupBy columns can be computed too.

Each adapter's own cell/group-header rendering (React `cellValue()`, Vue `cellText()`/`groupValue()`, vanilla `cellStr()`) calls `getColumnValue` instead of reading `row[col.key]` directly. `rowKey` (React/vanilla prop, Vue prop) is a separate, unrelated concept — it identifies a row for list keys/DOM identity and still reads a real row property directly, untouched by this.

### Grouped columns

When a column is added to `groupBy`, `useTableState` removes it from `activeColumns`, so it disappears from the table header and cells automatically. When grouping is cleared, the column reappears. Group header values are rendered with the same `cellValue()` / slot logic as table cells.

**Bucketed grouping (`groupValue`/`groupFormat`)** — grouping buckets rows by a groupBy column's exact value, which is meaningless for a continuous or near-unique column (a percentage, a raw timestamp): every row lands in its own group. `ColumnDefBase.groupValue?: (value: unknown, row: TRow) => unknown` lets a column bucket into a coarser group key instead — e.g. a percentage rounded down to a 10-point range, or a timestamp truncated to its month. It's spliced into `groupData` right where the exact-value key would otherwise be read (`col.groupValue ? col.groupValue(raw, row) : raw`, then through the same `multiValues`/fan-out path unchanged), so it affects grouping _only_ — sort/filter/aggregate/cell rendering keep reading the column's real value via `getColumnValue`, untouched. The bucket key still flows through `keyParts`, so `sortWithinGroups`' existing type-aware group comparison (`comparableFromKeyPart`, keyed off `col.type`) orders bucketed groups correctly for free — a `groupValue` returning a number for a `type: 'number'` column, or a `parseDate`-parseable string for `type: 'date'`, needs no separate sort key. The group header, however, can't just render a sample row's real value through the column's normal `format`/cell pipeline as it does for exact-value grouping — a bucket's representative row's real value (e.g. `47%`) isn't the bucket it's displayed under (`"40–50%"`). `ColumnDefBase.groupFormat?: (keyPart: string) => string` renders the bucket key for the group header instead (falling back to the raw key when omitted); a bucketed column's group header renders `gCol.groupFormat?.(keyParts[gi]) ?? keyParts[gi]` directly, bypassing every other per-column display hook it would otherwise go through (React's `col.render`/`col.format` via `formatValue`; Vue's `#group-{key}` slot, which has no single raw value to hand the slot's scope in the first place — the same reasoning the date filter tree already skips its own per-value slot for a branch node; vanilla's `formatStr`/`col.render`). `bucketNumericRange(step)`/`formatNumericRange(step, unit?)` and `bucketDatePart(part)`/`formatDatePart(part)` (core, `part: 'year' | 'month' | 'day'`) are ready-made pairs for the two common cases, re-exported from each adapter package (alongside `DEFAULT_LABELS`/locales) since — unlike most other core pure functions, which stay internal to each adapter's own state/render logic — these are meant for direct use in a consumer's column definitions. Vue's `DataTableView.vue` renames its own pre-existing group-header helper from `groupValue(group, key, i)` to `groupRawValue(...)` to avoid colliding with the new `ColumnDefBase.groupValue` column property; the bucketed-label path is a separate `groupBucketLabel(group, key, i)` helper.

A `defaultGroupsCollapsed` option/prop (`useTableState`'s 6th positional param in React; a `UseTableStateOptions`/`DataTableOptions` field in Vue/vanilla) controls whether groups start expanded or collapsed, **defaulting to `true`** (collapsed) — pass `false` to start expanded. Rather than seeding `collapsedGroups` with every group key up front (impossible anyway — group keys are only known once the data is actually grouped, and new keys can appear later as data changes), `collapsedGroups: Set<string>` is reinterpreted as _manual toggles away from the default_ rather than absolute collapsed state: `isGroupCollapsed(collapsedGroups, key, defaultCollapsed)` (core, itself defaulting to `false` as a neutral pure-function default) is `defaultCollapsed ? !collapsedGroups.has(key) : collapsedGroups.has(key)`, used everywhere collapse state is checked (`getVisibleRows`, and each adapter's own render of the header's expand icon/aria-expanded and its rows' visibility) in place of a bare `.has(key)`. This means a never-toggled group — including one that's never been seen before — picks up `defaultCollapsed` for free, with no extra "seed new groups" bookkeeping. `toggleCollapse` itself is unchanged (still a plain Set add/remove); only its interpretation flips.

Vue's `<DataTable>` needs its own explicit `withDefaults(..., { defaultGroupsCollapsed: true, ... })` entry, not just `useTableState`'s own `?? true` fallback — Vue casts an absent boolean prop with no explicit default to `false` (not `undefined`) before it ever reaches `useTableState`'s options object, which would otherwise silently force every `<DataTable>` to the expanded-by-default behavior regardless of `useTableState`'s own default. `useTableState` called directly (no `<DataTable>` wrapper) isn't affected — a plain options object literal has no such casting.

**Sorting within (and of) groups** — `processData` sorts the flat row list _before_ `groupData` fans a multi-value column's row out into one bucket per value (e.g. a row tagged `['Action', 'RPG']` lands in both the 'Action' and 'RPG' groups). That fan-out has no single per-row comparable value to sort by ahead of time, so a multi-value sort key falls back to comparing each row's whole array (`String(array)`) — a comparison unrelated to either bucket a row lands in. This breaks two things downstream: it starves any secondary sort key from ever being reached for row order within a bucket (rarely ties between different rows), and it determines the arbitrary order `groupData` first encounters each value in, so the _groups themselves_ (e.g. which skill's header comes first) end up in no meaningful order either (see GitHub issue #12). `sortWithinGroups(groups, sorts, groupBy, columns)` (core), called right after `groupData` in all three adapters, fixes both by splitting `sorts` into entries matching a `groupBy` column (which reorder the top-level `groups` array, comparing each group's own `keyParts[i]` — already the single value that group represents, type-aware per `col.type` the same way a normal column sort is — a well-defined comparison a group actually has available, unlike the pre-fan-out row) and the rest (which re-sort each group's `rows`, with the groupBy-matching entries excluded — every row in one of that column's buckets already shares its relevant value, so re-comparing it would be a no-op at best or reintroduce the same whole-array comparison at worst; dropping it lets the next sort key become the effective within-group row order, the same outcome a single-value groupBy column already got for free). Sorting by a multi-value column that is _not_ itself a `groupBy` column keeps the incidental whole-array comparison, unchanged — there's no per-bucket context to resolve it against.

### Custom sort order (`compare`)

`ColumnDefBase.compare?: (a: unknown, b: unknown, dir: SortDir) => number` (see GitHub issue #15) is a plain `Array.prototype.sort`-style comparator over two already-resolved column values — not full rows (`sortWithinGroups`' group-order pass has no single owning row for a bucket, so a row-aware signature couldn't be reused there anyway) — for a column whose natural order is neither numeric nor alphabetical (an enum/tier column: `Bronze < Silver < Gold`, not alphabetical). It overrides the default numeric-or-lexicographic comparison (factored out as `defaultCompare` in `logic.ts`) everywhere a column's values are ordered: `processData`'s row sort and `sortWithinGroups`' per-bucket row sort (both via the shared `sortRows`), `sortWithinGroups`' group-order pass (comparing `keyParts[idx]` directly instead of through `comparableFromKeyPart`'s type coercion), `computeStringValues`' default checklist order, and `sortFilterValues`' explicit alpha-mode sort toggle including count-mode's tie-break (replacing `localeCompare` in both). `compare` takes priority over `type: 'number'`/`'date'` coercion when both are set on a column — `sortRows` reads the raw value via `getColumnValue` instead of the type-coercing `getComparableValue` whenever `col.compare` is present. Doesn't affect `groupValue`/`groupFormat` bucketing, which solves the equivalent problem for grouping instead.

The 3rd `dir` argument is the active ascending/descending direction at that sort site (a fixed `'asc'` at the two checklist-ordering sites, which have no direction of their own — `computeStringValues`'s default order, and `sortFilterValues`'s count-mode tie-break, which — like `computeStringValueCounts`'s existing "tie-break alphabetically" behavior — is always ascending regardless of the checklist's own `sort.dir`, itself only ever governing the count comparison above it). An ordinary comparator should ignore it: every call site already flips the _return value_'s sign for a descending sort (`dir === 'asc' ? cmp : -cmp`) the same way the default comparison does, so a direction-naive `(a, b) => …` behaves correctly for free. `dir` exists only for the rarer case of a value that must stay pinned to one end regardless of which direction is active (e.g. a missing value sorting last whether ascending or descending) — genuinely impossible to express as a plain `(a, b) => number` return, since that return's sign gets flipped for `desc` right along with everything else, flipping "always after" to "always before" the moment the direction is toggled.

`compareMissingLast(compare?, isMissing?)` (core, re-exported from all three adapter packages alongside `bucketNumericRange`/`bucketDatePart`) is a ready-made comparator built on this: `isMissing` (default `(v) => v == null || v === ''`, covering both a real `null`/`undefined` raw value — row-level sort, where `getColumnValue`/`getComparableValue` can return either — and the empty string a missing scalar stringifies to wherever grouping/the filter checklist need a string instead, `multiValues`' `String(value ?? '')`) decides which values get pinned; `compare` (default: this module's own numeric-or-lexicographic fallback) orders any two non-pinned values, direction-naive same as any other comparator. Two pinned values compare as equal (`return 0`), falling through to the next sort key the same way a tied `compare` result would; a pinned value against a normal one returns `dir === 'asc' ? rel : -rel` for a fixed `rel` — pre-cancelling the call site's own upcoming flip so the net result stays "pinned always after" in both directions. Combine it with a custom order by passing that order's own comparator as `compareMissingLast`'s first argument, e.g. `compareMissingLast((a, b) => TIER_ORDER.indexOf(a) - TIER_ORDER.indexOf(b))` ranks by tier with an empty tier always last.

No adapter-level wiring was needed beyond passing `filterDetailCol.compare` through to `sortFilterValues`'s existing 4th param (React/Vue's `filterDetailValues`/`filteredValuesFor`, vanilla's `_filterDetailValues` computation) — `compare` lives on `ColumnDefBase` and every other call site is internal to `logic.ts`.

### Column reordering

`columnOrder: string[]` is a separate piece of state from `visibleCols` — it lists _all_ column keys (visible and hidden) in display order, not just the visible ones, so hiding a column and showing it again doesn't lose its position. It starts as `[]` (natural order, i.e. `columns` as passed in) and is only materialized on the first reorder.

`getOrderedColumns(columns, order)` in core sorts the full column list per `order`, appending any column missing from it (added later, or `order` still `[]`) at the end in its original relative position — the same "stale/partial state still renders something sane" pattern used for `visibleCols` in `setViewState`. `activeColumns` in each adapter is `getOrderedColumns(columns, columnOrder).filter(visible && !grouped)`; a second derived value, `orderedColumns`, is the unfiltered version — all columns in display order, visible or not — used to render the Columns panel with its own drag/order controls.

Two interactions both write to `columnOrder`, backed by two core primitives:

- **Drag-and-drop on headers** — native HTML5 Drag and Drop API (`draggable`, `dragstart`/`dragover`/`drop`), not a pointer-events implementation, to keep the per-adapter diff small and avoid a dependency. `reorderColumn(order, dragKey, targetKey)` moves `dragKey` to just before `targetKey`; dropping doesn't distinguish drop-before vs drop-after halves of the target header, it always inserts before — a deliberate simplification.
- **Drag-and-drop, or Alt+ArrowUp/Alt+ArrowDown, on rows in the Columns panel** — replaces the old ▲▼ buttons entirely. Dragging a row uses the same mechanism as the Sort/Group dropdowns' own active-entry lists (see "Drag-and-drop reordering inside the Sort/Group/Columns dropdown lists" below); `moveColumnBy(order, key, delta)` swaps `key` with its neighbor `delta` positions away (`-1`/`+1`) and is a no-op past either boundary, now fired via `Alt+ArrowUp`/`Alt+ArrowDown` on the row's own visibility checkbox rather than a dedicated button.

Both actions materialize `columnOrder` from `columns.map(c => c.key)` before calling the core primitive if it's still `[]`, so the first reorder always operates on a complete key list rather than an empty one.

Per-adapter drag wiring:

- **React/Vue** — `dragColKey`/`dragOverColKey` local state (React `useState`, Vue `ref`) drives inline opacity/box-shadow feedback on the dragged and hovered-over headers; both are cleared on `dragend` as well as `drop`, since a drag cancelled outside a valid target (e.g. dropped off the table) still fires `dragend` but not `drop`.
- **Vanilla** — drag feedback bypasses the render()/innerHTML flow entirely: replacing the dragged `<th>`'s DOM node mid-drag (as a `render()` call would) aborts the native drag operation in most browsers. So `dragstart`/`dragover`/`dragend` only toggle CSS classes directly on the existing DOM nodes via `classList`; only `drop` (the terminal action, after which a fresh render is safe) mutates `columnOrder` and calls `render()`. These four drag listeners are registered on the container alongside the existing `click`/`input`/`change` delegation, since native drag events aren't part of that delegation.

`TableViewState.columnOrder?: string[]` persists/shares the order the same way as every other field in `view.ts` — omitted when empty (natural order), wire key `o`.

**Drag-and-drop reordering inside the Sort/Group/Columns dropdown lists** (the active-entries list in each, plus the Columns panel's row list) is a separate interaction from header dragging above, but shares the same core primitives — `reorderColumn`/`reorderSort` (core) both take a 4th `after = false` param: `false` splices the dragged entry just before the target (the header-drag behavior, unchanged), `true` splices it just after. Unlike header dragging (which deliberately stays insert-before-only, see above), these three lists resolve `after` from where the cursor is within the hovered row's own bounds (top half vs bottom half via `getBoundingClientRect()`/`clientY`) — without that, a row could only ever be a valid "insert before" target, so the _last_ row in a list could never actually become non-last (dropping onto it could only ever push it to second-to-last). When the cursor isn't over any row at all (dead space below the last row, e.g. the "add" section) it snaps to the nearest edge row instead of rejecting the drop — a plain `closest()`-on-target-row-only design would `return` before calling `preventDefault()` there, and the browser treats a `dragover` that never calls `preventDefault()` as an invalid drop target, silently swallowing the subsequent `drop`.

- **Vanilla** — `resolveDragRow(e, selector)` (a closure helper alongside the drag handlers) queries all of a list's rows via `container.querySelectorAll(selector)` (each row already carries a `data-sort-key`/`data-group-key`/`data-col-row-key` attribute) and returns the hit row + `after`, or the first/last row snapped to an edge. `dt-dd-item--drag-over-after` (bottom inset line, mirroring the existing top-inset `dt-dd-item--drag-over`) renders the after-case's insertion point.
- **React/Vue** — the per-row `dragover`/`drop` handlers were removed; instead `<Dropdown>` itself accepts `onDragOver`/`onDrop` (React: new optional props forwarded onto the panel `<div>`; Vue: `Dropdown.vue` sets `inheritAttrs: false` and binds `v-bind="$attrs"` on the menu panel div instead of its own root, so a consumer's `@dragover`/`@drop` land on the panel rather than falling through to the outer wrapper) — bound once per dropdown rather than once per row, so hovering _past_ the last row (still inside the panel) reaches a handler at all. `resolveDropdownDragRow(root, e, attr)` (React: module-level function; Vue: a plain function in `<script setup>`) is the same row-query-and-snap logic as vanilla's `resolveDragRow`, scoped via the panel element (`e.currentTarget`) instead of a closure-held `container`. A second boolean ref/state (`dragOverSortAfter`/`dragOverGroupAfter`/`dragOverColRowAfter`) alongside the existing `dragOverXKey` picks which inset (`inset 0 2px 0` vs `inset 0 -2px 0`) the hovered row renders.
- `moveColumn`/`moveSort`/`moveGroup` (all three adapters' `useTableState`) each gained an optional 3rd `after` param (default `false`), threaded straight through to the corresponding core `reorderColumn`/`reorderSort` call.

### Toolbar clear buttons (Sort/Group/Filter)

The Sort/Group/Filter dropdowns used to render their own "Clear sorts"/"Clear groups"/"Clear filters" row in a `dd-footer` at the bottom of the panel — clearing that state required opening the dropdown first. Each toolbar button now instead grows an adjoining × button (visible only when that state is non-empty, i.e. `sorts.length > 0`/`groupBy.length > 0`/`activeFilterCount > 0`) that clears without opening the dropdown at all — same idea as the search input's own `×` clear button (`dt-search-clear`/`.dt__search-clear`), which the new button matches in color/size (muted `--color-text-tertiary`, `font-size: 14px`). The Columns dropdown is unaffected — it never had a clear concept. The toolbar-level "Clear all" button (`clear-all`) is also unaffected; it coexists with these per-dropdown ones.

A `<button>` can't contain another interactive element, so the × can't nest inside the toggle button itself — it's a sibling, and the two are visually merged into one pill via a shared border (toggle button gets its right corners squared off and its right border dropped; the × button gets the matching left treatment and rounds off the outer right corners).

- **Vanilla** — the trigger markup passed to `buildDd` becomes `<span class="dt-btn-group">` wrapping both `<button class="dt-btn dt-btn--grouped">` (only when active — plain `.dt-btn` otherwise) and the sibling `<button class="dt-btn-clear" data-action="clear-sorts">×</button>`. Since both buttons already live inside the same `.dt-dd-wrap` as before, no changes were needed to the existing "close dropdown on outside click" logic (which checks `.closest('.dt-dd-wrap')`) or to drag-and-drop resolution (which already treats the whole `.dt-dd-wrap` as one region).
- **React/Vue** — the × can't just be placed in the `trigger` prop/slot, because `Dropdown`'s trigger area itself carries the open/close click handler (an ancestor `<div onClick>` in React, `<div @click>` in Vue) — nesting the × there would make clicking it also toggle the dropdown. Both `Dropdown` components instead gained a second slot for this: React's `extraTrigger?: ReactNode` prop and Vue's `#extra-trigger` slot are rendered as a sibling of the trigger's own click-handling wrapper, but still inside the same outer container that the "click outside closes the dropdown" listener checks (`ref.current.contains(...)` in React, `containerRef.value.contains(...)` in Vue) — so clicking × neither toggles the dropdown open/closed via the trigger's own handler, nor spuriously closes an already-open dropdown via the outside-click listener treating it as "outside". That container's `display` changed from `inline-block` to `inline-flex` so the trigger and the extra × sit side by side. `ToolbarBtn` gained a `grouped`/`:grouped` prop (mirroring vanilla's `dt-btn--grouped`) for the same squared-off-right-edge treatment, applied only when that dropdown's state is non-empty.
- The × buttons reuse the existing `L.clearSorts`/`L.clearGroups`/`L.clearFilters` labels for their `title`/`aria-label` rather than as visible button text (the visible glyph is a literal `×`, matching `clearSearch`'s convention). Those three labels no longer carry a `'× Clear sorts'`-style leading `×` in `locales.ts` (across all five locales) — it made sense back when the string _was_ visible footer text, but reads redundantly once it's tooltip/aria-label-only text sitting next to a button that already shows its own `×` glyph, the same reasoning `clearSearch` (never prefixed) was already built around. `clearAll` is the one label that correctly keeps its `× ` prefix, since its button still renders the label as real visible text.

### Toolbar layout (shape/find clusters, active state bar)

The toolbar reads as two purposeful clusters instead of one undifferentiated row of buttons: **Columns · Sort · Group** (what's shown and in what order — "shape" the view) then a vertical divider then **Search · Filter** (which rows are shown at all — "narrow" the view), with the toolbar-level "Clear all" button pinned alone at the far right (`margin-left: auto`). Group moved out of its old position (after Filter) to sit with Sort as a fellow "shape" control; Search moved out of its own separate search-specific div to sit next to Filter as a fellow "find" control. The divider (`dt-toolbar-divider`/`S.toolbarDivider`/`.dt__toolbar-divider`) is a plain 1px-wide, 22px-tall vertical bar in `--color-border-secondary` (not the fainter `--color-border-tertiary` the toolbar's own bottom border uses — that token is too close to the background to read as a divider at this size).

Below the toolbar sits a second row, the **active state bar**, always rendered — even with nothing active — rather than only appearing once a filter is set. This gives the row-count stats a single stable home instead of bouncing between "end of the toolbar row" (its old position) and nowhere, and means toggling a sort/filter/group never changes the toolbar's height or shifts anything above it. It shows one chip per active sort entry, group column, and filter column, each independently removable (`remove-sort`/`remove-group`/`clear-filter-key`, all pre-existing actions — no new core primitives needed), followed by the row-count/group-count stats pinned at the far right of _this_ row instead of the toolbar row.

This replaces the old asymmetry where filter chips got a dedicated summary row (because the Filter button only ever showed a column _count_, with no view of which values were selected) while sort/group got only a bare count badge on their own toolbar button (`sorts.length`/`groupBy.length` in a small pill) — on the theory that the dropdown's own active-entries list already showed the detail, so a second copy would be pure duplication. In practice this meant sort/group state was strictly less visible than filter state despite being the same _category_ of thing (something the user did to shape/narrow the view), and you couldn't tell _which_ columns were sorted/grouped without opening the dropdown. The count badges are gone from all three toolbar buttons now (the active bar carries that detail instead); sort/group chips reuse the plain neutral chip look the badges used, while filter chips keep their existing blue tint (`dt-chip--filter`/`S.chipFilter`/`.dt__chip--info`) — the one deliberate color accent in this bar, since filters already carried that "narrowing your view" meaning before sort/group chips existed alongside them.

- **Vanilla** — the toolbar's outer `<div class="dt-toolbar">` now wraps only `.dt-toolbar-actions`; the active bar (`.dt-active-bar`) is a sibling `<div>` rendered after it (same nesting level `.dt-chips` used to have), built in the same `render()` pass right after the toolbar markup.
- **React** — `S.toolbar` dropped its own flex properties (it now just wraps `S.toolbarActions`, no longer lays out children directly); `S.toolbarSearch` was deleted entirely (the search `<span>` moved to be a plain sibling inside `S.toolbarActions`); the active bar is `S.activeBar`, a sibling `<div>` after the toolbar's closing tag.
- **Vue** — mirrors React exactly: `.dt__toolbar` lost its flex properties, `.dt__toolbar-search` was deleted, `.dt__chips` was renamed `.dt__active-bar` (kept as a sibling of `.dt__toolbar`, unchanged position) and is no longer gated behind `v-if="activeFilterCount > 0"`.
- Test gotcha for React specifically: the global search input and the Filter dropdown's own per-column search input share the exact same default placeholder text (`L.search` and `L.filterSearchPlaceholder` are both `'Search…'`). Tests that grab the filter's own search box via `getAllByPlaceholderText('Search…')` must now take the _last_ match, not the first — Search moved from after Filter (in DOM order) to before it, so the global box is now the earlier of the two matches. Vue's equivalent tests were never affected, since they disambiguate by CSS class (`.dt__search-input` vs `.dt__dd-search`) rather than by placeholder text.

### Active-bar chip click actions

Previously a chip's body (the label/icon text) was inert — only its `×` did anything. Each chip's body is now a real, focusable `<button>` (a sibling of the `×` button rather than nested inside it — a `<button>` can't contain another interactive element, the same reasoning already used for the toolbar's grouped clear buttons) that does something specific to that chip's own kind of active state, so tweaking an already-active sort/group/filter no longer requires reopening its dropdown and re-navigating to the same entry:

- **Sort chip** → toggles that column's direction in place (the same action the dropdown's own active-sort row already does) — no dropdown needed for the single most common tweak.
- **Group chip** → opens the Group dropdown and focuses that entry's row. There's no single obvious inline toggle for a group entry the way direction is for sort, so getting straight to it (ready to reorder/remove) is the most useful available action.
- **Filter chip** (both the checklist-values chip and the range chip) → opens the Filter dropdown, sets the active filter column to that key _before_ the panel first renders (so the right pane already shows the right thing on the very first paint, rather than waiting for focus to land and the "focus follows selection" mechanism below to catch up), and focuses that column's button in the left pane.
- Styling: a chip is no longer one bordered/padded pill-shaped element — the border/background/padding moved onto the body and `×` individually, each keeping only its own outer corner rounded and sharing a border between them (mirroring the toolbar's grouped-clear-button seam trick), so the pair still reads as one pill. This also makes chips keyboard-reachable for the first time (real `<button>`s are native Tab stops) — previously the whole chip was a plain, inert element apart from its `×`.

**Vanilla** — reuses the pre-existing `toggle-sort-dir` action as-is for the sort chip; two small, structurally identical new click-handler cases, `open-group-entry`/`open-filter-col`, do the rest — no new core logic needed, since each one only sets pre-existing state (`openDropdown`, `filterActiveCol`, `filterListScrollTop`) the same way the equivalent dropdown-open/column-select interactions already do. The sort chip's button carries a stable `data-focus-key="chip-sort-${key}"` so the existing generic focus-key restore at the top of `render()` (see "Keyboard navigation") keeps it focused across the re-render for free; Group/Filter's buttons get an explicit post-render focus lookup instead (by `grouprow-${key}`'s focus key, or by `.dt-filter-col-item`'s own `data-key`), since a _newly opened_ dropdown's row isn't the thing that had focus before this render, so the generic restore doesn't apply there. `.dt-chip` dropped its own padding/background/border in favor of `.dt-chip-body`/`.dt-chip-x` (`12px 0 0 12px` / `0 12px 12px 0` corner rounding).

- **React** — the sort chip's button keeps the same key/identity across the toggle, so it stays focused for free with no explicit refocus needed. Group/Filter route through the same pending-ref + `useLayoutEffect` pattern already used for the Sort/Group activate/remove focus-retention fix below (`pendingGroupFocusKey`/`pendingFilterColFocusKey`), since clicking either opens a dropdown panel that doesn't exist in the DOM yet at click time. `S.chip` lost its own padding/background/border in favor of new `S.chipBody`/`S.chipX` style objects.
- **Vue** — same reasoning as React: the sort chip needs no refocus code (Vue's reconciliation keeps its `<button>` in place across the reactive update); Group/Filter open their dropdown via a new `open()` method `Dropdown.vue` exposes via `defineExpose` (alongside the existing `close()`), then focus the target row/column button via the same ref maps used by the Sort/Group activate/remove fix, after an `await nextTick()`. `.dt__chip`'s own padding/background/border moved onto new `.dt__chip-body`/`.dt__chip-remove` classes.

### Dropdown viewport clamping and toolbar wrapping

Every dropdown panel (Columns/Sort/Group/Filter) is absolutely positioned off its trigger and would otherwise render partly or fully off-screen — most visibly the ~460px-wide filter panel opened near the right edge of a narrow viewport. Each adapter measures the freshly-opened panel's `getBoundingClientRect()` and, if it overflows the viewport, applies a `transform: translateX(...)` horizontal offset (rather than flipping the anchor side, `left:0` → `right:0` — the overflow is relative to the _viewport_, not the trigger, so flipping the anchor on a trigger near the toolbar's left edge would just push a wide panel off the opposite side instead) and flips the panel above the trigger when it would overflow the bottom edge (`top`/`margin-top` swapped for `bottom`/`margin-bottom` in React/Vue; a `dt-dd--up` CSS class in vanilla). React (`Dropdown.tsx`) and Vue (`Dropdown.vue`) do this in a `useLayoutEffect`/`watch(..., { flush: 'post' })` right after the panel mounts (each open is a fresh, unclamped DOM node, since the panel unmounts entirely when closed); vanilla does it inline in `render()` after `container.innerHTML` is set, via a plain `container.querySelector('.dt-dd')` lookup. All three mutate the node's `style`/`classList` directly rather than through reactive state, to avoid a synchronous re-render-triggering-render loop.

Separately, the toolbar search input is `flex: 1` capped at a `max-width` of 280px instead of a fixed ~160px box, so it grows to use available toolbar space on wide viewports while still shrinking gracefully on narrow ones — a CSS-only responsiveness fix, not a behavioral change. (An earlier iteration also wrapped the toolbar's buttons and the search/clear-all pair into two separate flex sub-containers so they'd wrap as units on narrow viewports; "Toolbar layout" above's shape/find redesign flattened both back into the single `dt-toolbar-actions`/`S.toolbarActions`/`.dt__toolbar-actions` container, so each control now wraps individually again.)

### Dropdown column search and keyboard navigation

The Columns, Sort, and Group dropdowns' full column lists, and the Filter dropdown's left column pane, each gained a search box plus proper Up/Down/Home/End/Escape navigation — these lists had no way to narrow or arrow-key through them before, relying on plain sequential Tab. The bullets below describe the feature in vanilla's own terms (its identifiers/markup); see the "Vanilla/React/Vue" bullet at the end of this section for how each adapter implements the same behavior.

- **Search**: a `.dt-dd-search` input (`data-action="dd-search"`, `data-dd="cols"|"sort"|"group"|"filter"`) always renders at the top of each list — no column-count threshold gating its visibility, unlike some other conditionally-shown controls in this file — and narrows the list below by case-insensitive substring match on `col.label`, via `ddSearchTerms: Record<string, string>` (ephemeral UI state, same category as `filterSearchTerms`/`filterActiveCol` — keyed by dropdown id rather than by column, since here there's one search per whole dropdown rather than per column). It reuses `L.filterSearchPlaceholder` rather than adding a new label — the global search box and the filter value-checklist search already share that same placeholder text, so a third reuse follows the existing precedent instead of growing `DataTableLabels` (and all 5 locale files) for what would be identical text. For Sort/Group, the search narrows only the "addable" section; the active-sorts/active-groups section above it is never hidden by a search term, since it's a short list with its own priority order and remove controls. The Filter dropdown's search sits `position: sticky; top: 0` inside `.dt-filter-cols` (its own scrollable pane) since it isn't a separate section the way Sort/Group's is.
- **Ordering**: the Columns dropdown keeps listing `orderedColumns` (real table column order) unchanged — it doubles as the drag-to-reorder surface (see "Column reordering"), so alphabetizing it would conflict with that order's own meaning. Sort's and Group's addable lists, and the Filter dropdown's left column pane, switched from raw column-definition order to alphabetical-by-label — none of those three lists had an order that carried any meaning (nothing in them is sorted/grouped/filtered yet), so alphabetizing just makes a long list easier to scan. None of the four pin "active"/visible columns first — Sort/Group already separate active from addable into two sections, and Filter already flags an active column with a dot marker (see "Filter dropdown"), so a third active-first treatment would be redundant.
- **Keyboard nav**: `.dt-dd` itself gained `max-height: 420px; overflow-y: auto` (previously unbounded — a table with many columns could render a dropdown taller than the viewport with no way to scroll it). Plain (non-Alt) `ArrowDown`/`ArrowUp` move focus between the search input and each row's actual focusable element (a row's own `<button>`/`tabindex="0"` div, or — for a Columns row, which carries no tabindex of its own, see "Column reordering" — its checkbox), clamped at the first/last row (no wrap), in actual DOM/visual order — a single combined `querySelectorAll` covering the search input and every row selector together, not the search input prepended in front of a separately-queried row list. That distinction matters for Sort/Group specifically: their active-entries section renders _above_ the search box and the addable section renders _below_ it (active → search → addable, matching what's on screen), so building the search input as its own array and concatenating it first used to silently reorder the nav to "search → active → addable" regardless of what was actually on screen above/below it. `Home`/`End` jump to the first/last row, skipping the search input. `Escape` clears a non-empty search term first (focus stays in the box); pressed again (or with an already-empty term) it closes the dropdown and refocuses its toggle button — this also covers the Filter dropdown's value-search box (`data-action="filter-search"`, clearing `filterSearchTerms` instead of `ddSearchTerms`), checked as a second, independent condition right alongside the column-search one. This is a new, generic `handleKeyDown` block scoped to whichever `.dt-dd` is open, and deliberately runs _before_ the existing sort-row/group-row/column-row handlers (Alt+↑/↓ reorder, Enter/Space toggle — see "Column reordering") since those unconditionally `return` even for a key they don't handle, which would otherwise swallow a plain arrow key before this block ever saw it; it only acts on a key when the currently-focused element is genuinely one of its own (search input or a row's focusable target) — checked via `focusables.indexOf(document.activeElement)` — so it never hijacks native Left/Right/Up/Down/Home/End behavior on unrelated controls sitting in the same `.dt-dd` (a range-filter slider thumb, a plain number/date input) in the Filter dropdown's right-hand detail pane.
- **Focus follows open**: clicking (or Enter/Space-activating) a dropdown's toggle button now focuses inside the panel immediately — its search input if it has one, else the first active row (e.g. the Sort dropdown when every column is already sorted, so it has no addable section and therefore no search box) — via `focusFirstInDropdown(dd)`, called right after `render()` in the `toggle-dd` click handler whenever `openDropdown === dd` (i.e. this click _opened_ it, not closed it). Previously focus stayed on the toggle button, needing an extra Tab before any of the nav above did anything.
- **Activating/removing a Sort or Group column keeps focus, instead of dropping it to `<body>`**: clicking (or Enter/Space-activating) an addable column's button moves it into the active section — a different element (a `sortrow`/`grouprow` div) at a different position — and `render()`'s `innerHTML` rebuild destroys the button that had focus; the reverse (removing an active entry via its `×`) has the same problem in the other direction. Neither element carries the same `data-focus-key` before and after (the addable buttons have none at all — only the active rows and the search inputs do), so the generic focus-key restore at the top of `render()` has nothing to match and focus was silently lost. `toggle-sort`/`toggle-group`/`remove-sort`/`remove-group` each now explicitly refocus the equivalent new element right after the shared `render()` call in `handleClick` — the new active row (by its `sortrow-${key}`/`grouprow-${key}` focus key) when adding, or the now-addable button (by `data-key`) when removing.
- **Filter dropdown: crossing between the left column pane and the right detail pane**: plain `ArrowRight` on a `.dt-filter-col-item` (left pane) focuses the first focusable control in `.dt-filter-detail` (right pane) — whatever that is for the column's type (the select-all checkbox for a string column, a range-min input for number/date); plain `ArrowLeft` from anywhere in the right pane returns focus to `.dt-filter-col-item--active`, _except_ when focus is on an actual editable control (`filter-search`, `range-min`, `range-max`, `range-slider`) — those need native Left-arrow cursor/value behavior, so `ArrowLeft` is left untouched there. This pane-crossing check runs first, ahead of the column-list `ddPanel` block above (same "runs before, so it isn't swallowed" reasoning), keyed off `.dt-filter-col-item`/`.dt-filter-detail` rather than `.dt-dd` generally.
  - **The right pane's own rows get the same Up/Down/Home/End treatment** as every other list here — the value checklist (`.dt-dd-item` inside `.dt-filter-list`) or the date tree (`.dt-date-tree-item` inside `.dt-date-tree-wrap`), whichever is rendered for the column's type — with only the value-search box (`filter-search`) joining the vertical chain above the rows; the select-all checkbox and sort-order button sit beside the search box on the same row (`.dt-filter-search-row`), not above the list, so they're deliberately left out of Up/Down (still reachable via Tab/click) rather than being stepped through in a direction that wouldn't visually correspond to "down". The flat checklist is virtualized (see "The flat checklist is virtualized" above) — only a scrolled-into-view window of rows actually exists in the DOM — so crossing out of that window, or `Home`/`End` (which must reach the _logical_ first/last value of the full narrowed list, not just whatever happens to be mounted), first computes the target row's pixel offset and adjusts `filterListScrollTop`/`checklistEl.scrollTop`, patches `.dt-filter-list`'s `innerHTML` via the same `buildFilterListInnerHtml` the scroll handler already uses (see "Vanilla" under "The flat checklist is virtualized"), and only then focuses the checkbox matching the target value — all synchronously in the keydown handler, not routed through the scroll listener's own `requestAnimationFrame` throttling. The date tree has no such window (every currently-expanded row is already in the DOM, same as any other dropdown list), so it falls through to the same plain DOM-order nav the column lists use.
  - **The left column pane follows focus like a listbox/radiogroup, rather than needing a separate Enter/Space "activate" step** — the arrow-key nav above only ever calls a plain `.focus()` on a `.dt-filter-col-item`; a delegated `focusin` listener (`handleFilterColFocus`, registered on `container` since `focusin`, unlike `focus`, bubbles) is what actually updates `filterActiveCol`/resets `filterListScrollTop`/re-renders/refocuses the equivalent new button, and it fires for _every_ way focus can land there — arrow-key nav, Tab/Shift+Tab, and a mouse click (which focuses the button natively before the click handler's own `select-filter-col` case even runs). It's guarded by comparing the focused button's key against the _resolved_ active key (`resolveFilterActiveKey`, the same fallback-to-first-filterable-column logic the render side already uses) rather than the raw `filterActiveCol` — so focusing the already-effectively-active column (e.g. on initial mount) is a no-op — and that same guard is what stops the handler from looping: refocusing the new node after `render()` fires another `focusin`, but by then `filterActiveCol` already matches so the second call returns immediately.

**Vanilla** — everything above is this adapter's own implementation (`ddSearchTerms`, the generic `handleKeyDown` block scoped to whichever `.dt-dd` is open, `handleFilterColFocus`).
**React/Vue** — both share the same core design (a generic panel-level roving-nav handler driven by two DOM markers rather than vanilla's per-dropdown string building) instead of duplicating vanilla's exact mechanics one-for-one:

- A `data-dd-search` attribute marks a dropdown's own column-search `<input>`, and a `data-dd-row`-equivalent selector (React: a shared `DD_NAV_SELECTOR` constant in `Dropdown.tsx`; Vue: a shared `DD_ROW_SELECTOR` constant in `DataTableView.vue`) covers every row type (Columns/Sort/Group rows, Filter's left-pane buttons) — the same two markers drive both the roving Up/Down/Home/End nav _and_ focus-on-open, so the two can't drift apart. This lives in `Dropdown.tsx`/`Dropdown.vue` itself (a `useLayoutEffect`/`watch(..., {flush:'post'})` for focus-on-open, an `onKeyDown`/`@keydown` handler for the roving nav) rather than per-dropdown in `DataTableView`, since neither component needs to know which concrete dropdown it's rendering.
- Escape (clear search term first, else close + refocus trigger) is handled per-search-input inline in React (each search `<input>`'s own `onKeyDown`) and via the panel's shared keydown handler in Vue; both close by calling into the `Dropdown` component's own exposed close/open API (Vue: `defineExpose({ open, close, focusTrigger })`; React: the pre-existing controlled `open`/`setOpen` props) rather than vanilla's closure-held `openDropdown` string.
- The Filter dropdown's pane-crossing (Left/Right) and right-pane row nav (including the virtualized checklist's scroll-then-focus dance for Home/End and window-crossing) is its own separate handler bound on the filter panel itself in both adapters (React: `handleFilterPanelKeyDown`; Vue: folded into the same keydown handler via a `.dt__filter-detail` check), since it needs to reach filter-specific DOM the generic `Dropdown` component knows nothing about.
- Focus-follows-selection in the Filter left pane is a plain `onFocus`/`@focus` handler on each column button (guarded against re-selecting the already-active column) — no delegated listener needed, since each button already has its own handler in JSX/template, unlike vanilla's single closure-scoped `container`.
- The Sort/Group activate/remove focus-retention fix (moving a column between the active and addable sections) _is_ still needed in both — neither framework's reconciliation preserves focus across that transition, since the two sections are structurally different list-render blocks, not a reordering of one list. React: a pending-focus-key ref per list (`pendingSortFocusKey`/`pendingGroupFocusKey`) picked up by a `useLayoutEffect` once the state update commits (same "can't focus synchronously across an async update" shape as the existing `pendingFocusTarget`/keyboard-navigation page-boundary handling). Vue: a plain ref map per list (`sortRowRefs`/`addableSortRefs`/etc.) plus `await nextTick()` before refocusing. Toggling a _sort chip's_ direction, by contrast, needs no such fix in either framework — same key/element identity survives the update, so focus just stays for free (see "Active-bar chip click actions").

### Aggregation in group headers

`ColumnDefBase.aggregate` accepts `'sum' | 'count' | 'avg' | 'min' | 'max'` or a custom `(rows: TRow[]) => unknown` function. When any active column defines an aggregate, a secondary `dt__agg-row` / `dt-agg-row` row is rendered below each group header with per-column values. `computeAggregate(col, rows)` in core handles all built-in types; `col.format` is used for display when available, passed `sampleRow` (see "Pagination") rather than `rows[0]` since `rows` can legitimately be empty for a header rendered right at a page boundary. The aggregate row is always visible regardless of collapse state — for a collapsed group `rows` is the full group (backfilled by `paginateVisibleGroups`), for an expanded/split group it's whatever chunk of the group is visible on this page (see "Pagination" for why these differ).

### Visual hierarchy (header / group rows / stripes)

Header, group header rows, aggregate rows, and the odd-row stripe used to all share one `--color-background-secondary` token with no other distinguishing treatment, making them hard to tell apart at a glance. Each now reads as its own tier:

- The table header alone uses a new token, `--color-background-tertiary` (defined in `theme.ts`'s `LIGHT_THEME`/`DARK_THEME` alongside the existing tokens, and picked up automatically by `renderThemeCss()`), plus a heavier `1px` (was `0.5px`) bottom border — the strongest visual anchor, sitting above everything else.
- Group header rows keep `--color-background-secondary` (unchanged) but gain a `3px solid` left accent border and switch their text from `--color-text-secondary` to `--color-text-primary` at `font-weight: 600` (was `500`/secondary) — previously group rows used the same muted styling as the header, which made them read as faded captions instead of bold section dividers. The left border is set on the `<tr>` itself (not a `<td>`) and relies on `border-collapse: collapse` (already set on all three adapters' `<table>`) to render at the table's left edge regardless of which cells happen to be present (checkbox column optional, etc).
- The odd-row stripe now uses `color-mix(in srgb, var(--color-background-secondary) 45%, transparent)` instead of the token at full strength, so plain alternating rows read as a subtle texture rather than competing with group rows for the same gray. Hover (`onRowClick` set) and selection stay at full strength, so they still read as a stronger, more "active" cue than the passive stripe.
- Aggregate rows are intentionally left unchanged (still muted `--color-text-secondary`, `font-weight: 500`) — once the group row above it went bold/primary, the contrast between "section title" and "summary line" falls out for free with no separate change needed.

### i18n

`DataTableLabels` in `packages/core/src/types.ts` defines static string keys and 5 formatting functions (`rowCount(filtered, total)`, `groupCount(n)`, `groupLabel(index)`, `rowsInGroup(n)`, `pageOf(page, total)`). `DEFAULT_LABELS` is English. Both adapters accept a `labels?: Partial<DataTableLabels>` prop/option that is shallow-merged over the defaults.

Built-in locales live in `packages/core/src/locales.ts` and are re-exported from both adapter packages via a `@vates/data-table-core/locales` sub-path export — consumers import from `@vates/data-table-react` or `@vates/data-table-vue` directly. Adding a new locale to `locales.ts` makes it available from both adapters with no further changes.

### View persistence

`TableViewState` in `packages/core/src/view.ts` is a serializable snapshot of everything a user can change through the UI — `visibleCols`, `columnOrder`, `sorts`, `filters`, `rangeFilters`, `groupBy`, `collapsedGroups`, `page`, `pageSize`, `searchQuery` — except `selection`, which is tracked by object identity and isn't meaningful to persist or share. All fields are optional: a partial view (e.g. just a sort) applies on top of whatever defaults are already in place.

`encodeViewState`/`decodeViewState` serialize a view to/from a compact, URL-safe string, kept small by three rules: 1-letter wire keys, tuples instead of objects (`sorts` as `[key, dirFlag]`, `filters` as `[key, values[]]` pairs, `rangeFilters` as `[key, min, max]`), and omitting any field at its natural default (empty array/object/string, `page: 1`, `pageSize: 0`) — most shared/persisted views differ from the defaults in only one or two fields. The string itself is base64url of that compact JSON — hand-rolled (not `btoa`/`TextEncoder`) since core targets ES2020 with no DOM/Node lib and must run identically in browsers, Node (SSR), and the vanilla adapter; base64url is cheaper here than `encodeURIComponent(JSON.stringify(...))` because JSON's punctuation would otherwise be percent-escaped at 3 chars apiece.

Each adapter's `useTableState`/`createDataTable` exposes `getViewState()` (builds a `TableViewState` from current state, omitting `visibleCols` when it equals the full column set) and `setViewState(view)` (applies a partial view, resetting every field absent from it back to its default — so it's idempotent with `getViewState`). `setViewState` falls back to the default visible columns if `view.visibleCols` contains no keys present in the current `columns` (e.g. a stale shared link against a changed column set). The vanilla adapter also exposes `onViewChange(cb)` since it has no reactivity system for external code to hook into; it fires after any UI action that changes the view, but not on selection-only changes.

Actually writing a view to `localStorage` or the URL is opt-in, via separate helpers rather than baked into the main hook (`persistence.ts` in each adapter package):

- `usePersistedView(table, storageKey)` (React/Vue) / `persistViewToLocalStorage(table, storageKey)` (vanilla) — loads on mount/init, saves on every change.
- `useUrlView(table, options?)` (React/Vue) / `syncViewToUrl(table, options?)` (vanilla) — loads from the `view` query param (configurable via `paramName`) on mount/init and on `popstate`, writes back via `history.replaceState` (not `pushState`, so per-change sort/filter/etc. tweaks don't spam browser history).

Both URL helpers only apply state when the param is actually present and decodes successfully — an absent or malformed param leaves whatever state is already there alone rather than forcing a reset to defaults. This matters when composing both helpers (as the demos do): on a plain reload with no `view` param, the URL helper's hydration step must not clobber the localStorage-restored view with an empty one.

### DataTableView — reaching state that `<DataTable>` can't expose (React/Vue)

`usePersistedView`/`useUrlView` (and any other external code wanting imperative selection control, e.g. `table.clearSelection()`) need the actual `useTableState` return value — but `<DataTable>` builds one internally and never exposes it, so nothing outside the component can reach it. Rather than bolt on an escape hatch (a `forwardRef`/`useImperativeHandle` or `defineExpose` handle), the render layer itself was split out: `DataTableView` takes a `table: TableState<TRow>` prop (the `useTableState` return value, type-aliased as `TableState<TRow>` and exported from `useTableState.ts`) instead of calling the hook itself, and `DataTable` is now a thin wrapper — `useTableState(...)` + `<DataTableView table={table} .../>`.

This is fully declarative (no ref timing/SSR concerns) and stays complete automatically as `useTableState` grows — passing the whole object through means every current and future action/derived value is reachable via `table`, with no separate "exposed API" surface to keep in sync by hand. A consumer who needs external control does exactly what the "Custom layout"/headless demos already did, just rendering the built-in UI instead of a hand-rolled one:

```tsx
const table = useTableState(data, columns)
usePersistedView(table, 'my-table-view')
return <DataTableView table={table} data={data} columns={columns} />
```

`DataTableViewProps<TRow>` (in each adapter's `types.ts`) holds every prop `DataTableView` needs beyond `table` — `data` (for the unfiltered row count) and `columns` (for filter/sort/group panels, which list _all_ columns, not just active ones) can't be derived from `table` alone, so they're passed separately, same as `<DataTable>` already required them. `DataTableProps` is `Omit<DataTableViewProps<TRow>, 'table'> & { defaultVisibleColumns?, labels?, defaultPageSize? }` — the three fields that only make sense at `useTableState` construction time.

Vue's split has one extra wrinkle around `onRowClick`/`rowClick` detection (see Row click above): `DataTableView`'s `isRowClickable` check reads its own `vnode.props.onRowClick`, but `DataTable` always forwards the `row-click` emit unconditionally (clicking a row always emits, matching the emit's own semantics, regardless of whether anyone's listening) — so if `DataTableView` self-detected off its incoming listener, it would always see one and always show clickable styling. `DataTable` instead does its own `vnode.props` check (reflecting whether _its_ caller passed a listener) and forwards the result down as an explicit `rowClickable` prop, which `DataTableView` prefers over self-detection when present; `DataTableView` used directly (no wrapper) falls back to self-detection since there's no wrapper to supply the prop.

### Testing

Each package has its own Vitest setup under `src/__tests__/`:

- **`packages/core`** — tests for all pure logic functions (`logic.ts`) and locale pluralization (`locales.ts`).
- **`packages/react`** — tests for `useTableState` via `@testing-library/react`'s `renderHook` + `act`. Runs in jsdom. Important: `vitest.config.ts` must include `resolve.dedupe: ['react', 'react-dom', 'react/jsx-runtime']` to prevent the duplicate-React-instance trap that arises when `react` is also a devDep of the package in a workspace. Behavior that lives in `DataTable.tsx` itself rather than the hook (e.g. `onRowClick`) is tested with `@testing-library/react`'s `render` + `fireEvent` instead.
- **`packages/vue`** — tests for `useTableState` called directly (no component wrapper needed; `ref`/`computed` work outside a component context in Vue 3). Behavior that lives in `DataTable.vue`'s template (e.g. `rowClick`) is tested by mounting the component with `@vue/test-utils`; this requires `vitest.config.ts` to load the `@vitejs/plugin-vue` plugin and set `environment: 'jsdom'`. Since `vue-tsc` can't carry the SFC's `generic="TRow extends object"` parameter through to an externally-imported component, `mount()` needs the component cast (see `DataTable.test.ts`) rather than typed per-test.
- **`packages/vanilla`** — has its own substantial suite despite having no separate hook/component split to test against: `createDataTable.test.ts` drives `createDataTable` end-to-end against real DOM nodes (jsdom) via its returned `{ setData, setColumns, destroy }` handle and delegated event dispatch (`click`/`input`/`change`/`keydown`), and `persistence.test.ts` covers `persistViewToLocalStorage`/`syncViewToUrl`.

### Performance

Given pagination, the DOM only ever renders `pageSize` rows regardless of dataset size — so for huge datasets (100k–1M+ rows), the cost lives entirely in `packages/core`'s pure functions, which run over the _full_ dataset on every relevant state change (sort, filter, search, group), not just the visible page.

- **Benchmarks**: `packages/core/src/__tests__/logic.bench.ts` (`npm run bench -w packages/core`, or `npx vitest bench` from `packages/core`) uses Vitest's built-in `bench()` against synthetic datasets at 10k/100k/500k rows (`bench-utils.ts`: 7 columns — string, number, date, and a 20-value low-cardinality category — generated with a seeded PRNG for stable runs). It covers `processData` (plain/filtered/sorted, per column type), `searchData`, `groupData`/`getVisibleRows`/`paginateVisibleGroups`, `computeStringValues`/`computeStringValueCounts` (all-columns vs. single-column), and `computeDateTree`. There's no CI regression gate on these yet — they're a manual profiling tool, run before/after a perf-sensitive change to check the actual impact rather than guessing.
- **`computeStringValueCounts` was the single biggest cost found**: ~15–17x faster at 500k rows/7 columns when scoped to one column via `targetKeys` instead of every filterable column — see "Filter dropdown" above for the fix (removed `stringValueCounts` from React/Vue's `useTableState` entirely; vanilla scopes it via `filterActiveKey` inside `derive()`).
- **`processData`'s sort** now precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) instead of recomputing them inside the comparator — see "Filter dropdown"'s date-sort note above. ~4x faster sorting a `type: 'date'` column at 500k rows.
- Sorting a plain numeric column is inherently ~1.5–2x costlier than sorting an equivalent string column in V8 for large arrays of objects (reproduced with a bare `(a,b) => a.price - b.price` comparator outside any library code) — this is a JS-runtime characteristic of comparing boxed doubles on objects, not something fixable in library code, so it isn't a benchmark target.
- Global search (`searchData`) and `groupData`/`getVisibleRows` scale linearly and stay well under the cost of a full re-sort even at 500k rows; they weren't found to need optimization for the "pagination keeps the DOM small" scenario this section is scoped to. Revisit if a future use case needs `pageSize: 0` (unpaginated) on a huge dataset, which would shift the bottleneck to DOM size instead.
- **The filter dropdown's checklist is a DOM-rendering cost, not a `packages/core` pure-function one** — the benchmark suite above doesn't exercise it, since it's specific to how many DOM nodes each adapter mounts, not to any core computation. A column with thousands of distinct values (a customer name, an order ID) used to mount one `<label>` per value regardless of scroll position; see "The flat checklist is virtualized" under "Filter dropdown" above for the fix (windowed rendering via `computeVirtualRange`).

### Cross-package resolution in development

Packages and demo apps resolve each other without a build step via:

- **`tsconfig.json` `paths`** — maps `@vates/data-table-core` → `../core/src/index.ts`, `@vates/data-table-core/locales` → `../core/src/locales.ts`, and (vanilla only, the sole consumer) `@vates/data-table-core/theme` → `../core/src/theme.ts` for type checking
- **`vite.config.ts` `resolve.alias`** — maps `@vates/data-table-core` to the `packages/core/src` **directory** (not `index.ts`) so Vite's prefix substitution resolves the bare import and any sub-path (`/locales`, `/theme`) correctly

In production, `npm run build` must run `core` before `react`, `vue`, and `vanilla` since they import from its `dist/`.
