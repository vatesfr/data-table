# Packages

## Core package (`packages/core`)

All stateless logic lives here — but `@vates/data-table-core` is **not a supported public API**. It exists solely so the adapter packages (`@vates/data-table-react`/`-vue`/`-solid`/`-vanilla`) can share implementation code with each other; a consumer of one of those adapters should get everything they need from that adapter directly, never from core. This is enforced by path, not just convention: the main entry point (`@vates/data-table-core`, `src/index.ts`) is a small, deliberate **public** surface — the same set every adapter re-exports identically (see each adapter's own `index.ts`/README props table) — while everything else (the bulk of `logic.ts`'s pure functions/types, `view.ts`'s `encodeViewState`/`decodeViewState`/`buildViewStateSnapshot`/`resolveViewState`, `viewPersistence.ts`'s low-level helpers, `dropdownDomUtils.ts`) lives behind a separate `@vates/data-table-core/internal` sub-path that only the adapter packages' own source imports from. A root `eslint.config.mjs` rule (`no-restricted-imports`, scoped to `demo/**`) fails lint if a demo app — written the same way a real consumer would use these packages — ever imports from core directly, catching a regression back to that pattern (as `demo/react`/`demo/vue` used to, for `renderThemeCss`, before each adapter grew its own `/theme` re-export below). See `packages/core/README.md`'s "Public API surface" section for the authoritative current public list.

- **`types.ts`** — shared interfaces: `ColumnDefBase<TRow>`, `AggregateType`, `SortEntry`, `RangeFilter`, `DataTableLabels`, `DEFAULT_LABELS` (English default strings), plus `DateTreeNode` (internal-only — re-exported from `/internal`, not the public barrel)
- **`logic.ts`** — pure functions: `getColumnValue`, `processData`, `searchData`, `groupData`, `sortWithinGroups`, `computeStringValues`, `computeStringValueCounts`, `computeAggregate`, `paginateData`, `computeTotalPages`, `toggleSort`, `replaceSort`, `appendOrToggleSort`, `cycleFilterValue`, `toggleGroupBy`, `toggleCollapse`, `getOrderedColumns`, `reconcileVisibleColumns`, `reorderColumn`, `moveColumnBy`, `getSortIcon`, `getSortIndex`, `countActiveFilters` — all internal-only (reachable via `/internal`), except the small `groupValue`/`groupFormat` bucketer families (`bucketNumericRange`/`bucketDatePart`/`bucketLogRange` and their `format*`/`*Group` pairs) and `compareMissingLast`, which are public
- **`locales.ts`** — built-in locale objects: `LABELS_EN`, `LABELS_FR`, `LABELS_ES`, `LABELS_DE`, `LABELS_PT` — public, re-exported from core's main barrel and from every adapter's own barrel
- **`theme.ts`** — `LIGHT_THEME`/`DARK_THEME`/`renderThemeCss()`. Not re-exported from core's main `index.ts` barrel or `/internal` — it's a distinct concern from the public/internal logic split (design tokens, not table logic), reachable via its own `@vates/data-table-core/theme` sub-path export, same pattern as `/locales`. Every adapter package (react/vue/solid/vanilla) now re-exports it too via its own `/theme` sub-path (`export * from '@vates/data-table-core/theme'`), so a consumer of any adapter reaches it without ever importing core directly — this matters beyond Solid (which consumes it internally for `styles.ts`'s auto-injected CSS): React/Vue's own demos need the same `--color-*` token values to seed their inline-styled/scoped-CSS components, since neither auto-injects them the way Solid does.
- **`viewPersistence.ts`** — `loadViewFromStorage`/`saveOrClearViewInStorage`/`readViewFromUrlParam`/`writeViewToUrlParam`/`resetView`/`ViewStateApi`/`ResetViewOptions`, the framework-agnostic building blocks behind every adapter's own `persistence.ts` (see [View persistence](view-persistence.md)) — internal-only, reachable via `/internal`.

The internal `asRecord(row: object): Record<string, unknown>` helper exists because the generic constraint is `TRow extends object` (not `Record<string, unknown>`) — TypeScript interfaces lack index signatures so the wider constraint is needed, and `asRecord` lets internal logic access arbitrary keys.

**Sub-path build wiring**: `packages/core/vite.config.ts` builds `index`/`locales`/`theme`/`internal` as parallel `es`+`cjs` entries (core ships no UMD build). React/vue/solid/vanilla each add their own `/theme` re-export the same way — but since those four packages' main entry also ships a `umd`/`iife` build (so each still works as a plain `<script>` global) and Rollup disallows multiple entry points when the output formats include `umd`/`iife`, each of their `/theme` sub-paths is built by a **separate** `vite.theme.config.ts` pass (`es`+`cjs` only), invoked as a second step in that package's own `build` script (`vite build && vite build --config vite.theme.config.ts`) rather than as a second `lib.entry` in the main config.

## React package (`packages/react`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase` with `render?` and `renderFilterLabel?` (render props)
- **`useTableState.ts`** — wraps core logic with `useState`/`useMemo`; signature `useTableState(data, columns, options?)` where `options` is `UseTableStateOptions` (`{ labels?, defaultGroupsCollapsed?, initialViewState?, getRowId? }`) — a single options object rather than 4 positional params, both for parity with Vue's shape below and because a positional-param footgun is exactly the kind of thing this library tries not to have: a consumer must not need to remember argument order, or pass `undefined, undefined, undefined` just to reach the option they actually want. Returns a `TableState<TRow>` namespaced by concern — see [Namespaced TableState](table-state.md#namespaced-tablestate) (React is migrated to this shape; `DataTableView.tsx`'s one destructuring block aliases each namespace's fields back to the same bare local names the rest of the ~2600-line component already used, so nothing past that block needed to change). Also exports `TableState<TRow>` (`ReturnType<typeof useTableState<TRow>>`) and `UseTableStateOptions`.
- **`DataTableView.tsx`** — the actual render layer; takes a `TableState<TRow>` (the `useTableState` return value) as a `table` prop instead of calling the hook itself
- **`DataTable.tsx`** — thin wrapper: calls `useTableState` internally and renders `<DataTableView table={table} .../>`

Cell rendering priority: `col.render(value, row)` → `col.format(value)` → `String(value)`. Group headers use the same `cellValue()` function so custom renders apply there too.

## Vue package (`packages/vue`)

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase` (no render props; customization is via slots)
- **`useTableState.ts`** — same signature shape as React: `useTableState(data, columns, options?)` where `options` is `UseTableStateOptions` (`{ labels?, defaultGroupsCollapsed?, initialViewState?, getRowId? }`); uses `ref`/`computed` and accepts `MaybeRefOrGetter` for reactive inputs. Returns a `TableState<TRow>` namespaced by concern like React/Solid — see [Namespaced TableState](table-state.md#namespaced-tablestate); `DataTableView.vue`'s one destructuring block aliases each namespace's fields back to the same bare local names its script and template already used, so nothing past that block needed to change. Also exports `TableState<TRow>` (`ReturnType<typeof useTableState<TRow>>`) and `UseTableStateOptions`
- **`DataTableView.vue`** — the actual render layer; uses `<script setup lang="ts" generic="TRow extends object">` and takes a `TableState<TRow>` as a `table` prop instead of calling `useTableState` itself
- **`DataTable.vue`** — thin wrapper: calls `useTableState` internally, renders `<DataTableView :table="table" .../>`, and forwards its own slots straight through. Also the one adapter with `v-model` sugar: `page`/`searchQuery` props + matching `update:page`/`update:searchQuery` emits, wired via two `watch` pairs (prop → `table.pagination.setPage`/`table.search.setQuery`, and `table.pagination.page`/`table.search.query` → emit, both `{ immediate: true }` so a bound v-model reflects the real initial value at mount, not just later changes). Scoped to `<DataTable>` only — a direct `useTableState` + `<DataTableView>` consumer already has `table.pagination.page`/`table.search.query` refs to bind however they like. `selection` deliberately has no `v-model:selection` alongside it: `selectionChange`/`onSelectionChange` already covers observing it, and a `v-model` counterpart would just be a second, redundant mechanism for the same event — "set it from outside" is also an awkward fit for a `Set<TRow>`-by-object-identity model (the caller would need to pass the exact same row references already in `data`).
- **`components/Dropdown.vue`** — self-manages open/close state and exposes it to `#trigger` slot

Vue customization uses **scoped slots** instead of render props:

- `#cell-{key}` — custom table cell; slot scope: `{ value: unknown, row: TRow }`
- `#filter-{key}` — custom filter dropdown label; slot scope: `{ value: string }`
- `#group-{key}` — custom group header value; slot scope: `{ value: unknown, row: TRow }`

## Vanilla package (`packages/vanilla`)

**A thin wrapper around `@vates/data-table-solid`** (see that section above for everything about the actual UI/state implementation — `createTableState`, `DataTableView`, every `components/*` file, and the Solid-specific reasoning behind them). This package's own `src/` is now just:

- **`types.ts`** — re-exports `ColumnDef` from `@vates/data-table-solid`, plus `DataTableOptions`/`DataTableInstance` (the imperative wrapper's own option/instance shapes — unchanged from before the split)
- **`index.tsx`** — `createDataTable(container, options)`: builds a `createTableState` (from `@vates/data-table-solid`) inside a `createRoot`, mounts `<DataTableView>` via `solid-js/web`'s `render()`, and returns the public instance object backed by that state (`onViewChange` is a `createEffect`/`on(..., { defer: true })` reading `table.getViewState()`, skipping the initial mount so it only fires from an actual subsequent change)
- **`persistence.ts`** — `persistViewToLocalStorage`/`syncViewToUrl`/`resetView` (see [View persistence](view-persistence.md)); unaffected by the split, since it only ever talked to the imperative `ViewStateApi` shape (`getViewState`/`setViewState`/`onViewChange`), not to Solid internals directly

Both `solid-js` and `@vates/data-table-solid` are bundled into this package's own `dist/` as internal implementation details — see `vite.config.ts`'s `rollupOptions.external` (only `@vates/data-table-core` is external) and `package.json` (both are `devDependencies`, never runtime ones). The public API (`createDataTable(container, options)` returning `{ setData, setColumns, getViewState, setViewState, onViewChange, onSelectionChange, getSelection, setSelection, clearSelection, getProcessedData, focusRow, clearAll, setRowKey, setSelectable, setOnRowClick, setLabels, setDefaultGroupsCollapsed, setGetRowId, destroy }`) is otherwise unchanged by the split — every `createDataTable.*.test.tsx` test still exercises it end-to-end exactly as before, now as a regression check that the wrapper still delegates correctly.

`getProcessedData()` (GitHub issue #22) delegates to Solid's `table.processedData()`, mirroring `getSelection() ↔ selection.all` — a flat method for a value that's already a flat (non-namespaced) `TableState` field, so unlike `getSelection`/`setSelection`/`clearSelection` there's no concept-name renaming involved, the same "no rename needed" precedent as `getViewState() ↔ getViewState`. It returns the current rows after search + filters + sort, before grouping (which can fan a multi-value row out into more than one bucket) or pagination (a display slice, not a reordering) — the linear order a consumer needs for something like prev/next-row navigation, without reaching into `@vates/data-table-core/internal`'s unsupported `processData`/`searchData`.

`clearAll()` delegates to Solid's `table.clearAll()` — the one action-side gap found while auditing vanilla against React/Vue/Solid's full `TableState` for parity (issue #22's own follow-up): every other piece of sort/filter/group/pagination/search state is already fully settable in bulk via `setViewState()` (its `TableViewState` covers all of it) or via the rendered DOM the built-in UI already provides, so no other granular action method was added — only `clearAll` has no equivalent, since `setViewState({})` restores `initialViewState`'s own defaults rather than truly clearing regardless of it. Read-side additions (`getPagedData`/`getGroupedData`/`getNumPages`/`getActiveColumns`/`getOrderedColumns`/`getLabels`/`getVisibleSelection`, mirroring the rest of `TableState`) were considered and deliberately deferred — no concrete consumer need surfaced for any of them yet, the same bar `getProcessedData` had to clear before it was worth adding.

`onSelectionChange(cb): () => void` mirrors `onViewChange`'s subscribe/unsubscribe shape (a `Set` of listeners, seeded with the constructor's `onSelectionChange` option if given) — a listener can now be attached after construction too, not just at construction time.

`rowKey`/`selectable`/`onRowClick`/`labels`/`defaultGroupsCollapsed`/`getRowId` are each backed by their own `createSignal` inside the wrapper, with a matching `setXxx` method to change them after construction — `setRowKey`/`setSelectable`/`setOnRowClick` work because `DataTableView`/`TableBody` already read those props lazily (a signal call passed as a JSX prop stays live, the same mechanism `table={table}` already relies on); `setLabels`/`setDefaultGroupsCollapsed`/`setGetRowId` work because `createTableState` now accepts its whole `options` argument as an Accessor (see [Solid package](solid-package.md)). `data`/`columns` are deliberately **not** threaded through as Accessors, even though `createTableState` supports that for a genuinely reactive source — vanilla's own `options` object is a plain, one-time JS value with no reactivity of its own to feed one from, so `setData`/`setColumns` stay the only way to update them, same as before. `initialViewState` has no setter at all — it's a seed-only constructor value in every adapter (see [Namespaced TableState](table-state.md#namespaced-tablestate)).

## DataTableView — reaching state that `<DataTable>` can't expose (React/Vue; Solid follows the same idea, see [Solid package](solid-package.md) for `DataTable.tsx`/`DataTableProps`)

`usePersistedView`/`useUrlView` (and any other external code wanting imperative selection control, e.g. `table.selection.clear()`) need the actual `useTableState` return value — but `<DataTable>` builds one internally and never exposes it, so nothing outside the component can reach it. Rather than bolt on an escape hatch (a `forwardRef`/`useImperativeHandle` or `defineExpose` handle), the render layer itself was split out: `DataTableView` takes a `table: TableState<TRow>` prop (the `useTableState` return value, type-aliased as `TableState<TRow>` and exported from `useTableState.ts`) instead of calling the hook itself, and `DataTable` is now a thin wrapper — `useTableState(...)` + `<DataTableView table={table} .../>`.

This is fully declarative (no ref timing/SSR concerns) and stays complete automatically as `useTableState` grows — passing the whole object through means every current and future action/derived value is reachable via `table`, with no separate "exposed API" surface to keep in sync by hand. A consumer who needs external control does exactly what the "Custom layout"/headless demos already did, just rendering the built-in UI instead of a hand-rolled one:

```tsx
const table = useTableState(data, columns)
usePersistedView(table, 'my-table-view')
return <DataTableView table={table} data={data} columns={columns} />
```

`DataTableViewProps<TRow>` (in each adapter's `types.ts`) holds every prop `DataTableView` needs beyond `table` — `data` (for the unfiltered row count) and `columns` (for filter/sort/group panels, which list _all_ columns, not just active ones) can't be derived from `table` alone, so they're passed separately, same as `<DataTable>` already required them. `DataTableProps` is `Omit<DataTableViewProps<TRow>, 'table'> & { labels?, defaultGroupsCollapsed?, initialViewState? }` — the fields that only make sense at `useTableState` construction time.

Vue's split has one extra wrinkle around `onRowClick`/`rowClick` detection (see Row click above): `DataTableView`'s `isRowClickable` check reads its own `vnode.props.onRowClick`, but `DataTable` always forwards the `row-click` emit unconditionally (clicking a row always emits, matching the emit's own semantics, regardless of whether anyone's listening) — so if `DataTableView` self-detected off its incoming listener, it would always see one and always show clickable styling. `DataTable` instead does its own `vnode.props` check (reflecting whether _its_ caller passed a listener) and forwards the result down as an explicit `rowClickable` prop, which `DataTableView` prefers over self-detection when present; `DataTableView` used directly (no wrapper) falls back to self-detection since there's no wrapper to supply the prop.
