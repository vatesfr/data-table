# Grouped columns

When a column is added to `groupBy`, `useTableState` removes it from `activeColumns`, so it disappears from the table header and cells automatically. When grouping is cleared, the column reappears. Group header values are rendered with the same `cellValue()` / slot logic as table cells.

**Keeping a grouped column's cells visible (`keepVisibleWhenGrouped`)** — the auto-hide above assumes the group header already shows what the row would, making the row's copy redundant. Two cases break that assumption (GitHub issue #16): a `groupValue`-bucketed column (see below), where the header shows only the bucket label (e.g. `"3–10h"`) and the row's exact value (`"4.3h"`) is otherwise displayed nowhere at all; and a multi-value/array column, where grouping fans one row out into a group per value (a `["Roguelike", "Deckbuilder"]` row appears in both groups), so hiding the column removes the only way to see a row's _other_ values while looking at one particular group's rows. `ColumnDefBase.keepVisibleWhenGrouped?: boolean` (default `false`) opts a column out of the hide for exactly these cases: `activeColumns`' filter (identical in React/Vue/Solid; vanilla inherits it from Solid) is `visibleCols.has(c.key) && (!groupBy.includes(c.key) || c.keepVisibleWhenGrouped === true)`. This is a per-column, explicit opt-in rather than an automatic one — a column's cell values aren't knowable to be bucketed/array-shaped from the column def alone, since `value` is an arbitrary function; whether it _can_ return an array is a fact about actual data, not something safe to infer once and apply everywhere. Rendering itself is unchanged when kept visible: the row's cell goes through the exact same `format`/render/slot pipeline as it would ungrouped (including rendering the full array for a multi-value column) — there's no separate "show only the values other than the one that matched this group" logic; a consumer wanting that presentation can build it with a custom `render`/format function.

**Bucketed grouping (`groupValue`/`groupFormat`)** — grouping buckets rows by a groupBy column's exact value, which is meaningless for a continuous or near-unique column (a percentage, a raw timestamp): every row lands in its own group. `ColumnDefBase.groupValue?: (value: unknown, row: TRow) => unknown` lets a column bucket into a coarser group key instead — e.g. a percentage rounded down to a 10-point range, or a timestamp truncated to its month. It's spliced into `groupData` right where the exact-value key would otherwise be read (`col.groupValue ? col.groupValue(raw, row) : raw`, then through the same `multiValues`/fan-out path unchanged), so it affects grouping _only_ — sort/filter/aggregate/cell rendering keep reading the column's real value via `getColumnValue`, untouched. The bucket key still flows through `keyParts`, so `sortWithinGroups`' existing type-aware group comparison (`comparableFromKeyPart`, keyed off `col.type`) orders bucketed groups correctly for free — a `groupValue` returning a number for a `type: 'number'` column, or a `parseDate`-parseable string for `type: 'date'`, needs no separate sort key. The group header, however, can't just render a sample row's real value through the column's normal `format`/cell pipeline as it does for exact-value grouping — a bucket's representative row's real value (e.g. `47%`) isn't the bucket it's displayed under (`"40–50%"`). `ColumnDefBase.groupFormat?: (keyPart: string) => string` renders the bucket key for the group header instead (falling back to the raw key when omitted); a bucketed column's group header renders `gCol.groupFormat?.(keyParts[gi]) ?? keyParts[gi]` directly, bypassing every other per-column display hook it would otherwise go through (React's `col.render`/`col.format` via `formatValue`; Vue's `#group-{key}` slot, which has no single raw value to hand the slot's scope in the first place — the same reasoning the date filter tree already skips its own per-value slot for a branch node; vanilla's `formatStr`/`col.render`). `bucketNumericRange(step)`/`formatNumericRange(step, unit?)`, `bucketDatePart(part)`/`formatDatePart(part)` (core, `part: 'year' | 'month' | 'day'`), and `bucketLogRange(options?)`/`formatLogRange(options?, unit?)` (log-scale bucketing, for a right-skewed numeric column spanning several orders of magnitude) are ready-made pairs, re-exported from each adapter package (alongside `DEFAULT_LABELS`/locales) since — unlike most other core pure functions, which stay internal to each adapter's own state/render logic — these are meant for direct use in a consumer's column definitions. `numericRangeGroup`/`datePartGroup`/`logRangeGroup` bundle each bucketer with its formatter into one `{ groupValue, groupFormat }` pair from a single set of arguments, spreadable straight into a column def. All three bucketers return `null` for a missing (`null`/`undefined`) value instead of coercing it into a real bucket (e.g. a real `0`) or leaking a raw `"null"`/`"NaN"` group header — see "Ready-made `groupValue` bucketers" in [CLAUDE.md](../CLAUDE.md#ready-made-groupvalue-bucketers-github-issue-18) for the full mechanics of all three (GitHub issue #18). Vue's `DataTableView.vue` renames its own pre-existing group-header helper from `groupValue(group, key, i)` to `groupRawValue(...)` to avoid colliding with the new `ColumnDefBase.groupValue` column property; the bucketed-label path is a separate `groupBucketLabel(group, key, i)` helper.

A `defaultGroupsCollapsed` option/prop (a `UseTableStateOptions`/`DataTableOptions` field in all three adapters) controls whether groups start expanded or collapsed, **defaulting to `true`** (collapsed) — pass `false` to start expanded. Rather than seeding `collapsedGroups` with every group key up front (impossible anyway — group keys are only known once the data is actually grouped, and new keys can appear later as data changes), `collapsedGroups: Set<string>` is reinterpreted as _manual toggles away from the default_ rather than absolute collapsed state: `isGroupCollapsed(collapsedGroups, key, defaultCollapsed)` (core, itself defaulting to `false` as a neutral pure-function default) is `defaultCollapsed ? !collapsedGroups.has(key) : collapsedGroups.has(key)`, used everywhere collapse state is checked (`getVisibleRows`, and each adapter's own render of the header's expand icon/aria-expanded and its rows' visibility) in place of a bare `.has(key)`. This means a never-toggled group — including one that's never been seen before — picks up `defaultCollapsed` for free, with no extra "seed new groups" bookkeeping. `toggleCollapse` itself is unchanged (still a plain Set add/remove); only its interpretation flips.

Vue's `<DataTable>` needs its own explicit `withDefaults(..., { defaultGroupsCollapsed: true, ... })` entry, not just `useTableState`'s own `?? true` fallback — Vue casts an absent boolean prop with no explicit default to `false` (not `undefined`) before it ever reaches `useTableState`'s options object, which would otherwise silently force every `<DataTable>` to the expanded-by-default behavior regardless of `useTableState`'s own default. `useTableState` called directly (no `<DataTable>` wrapper) isn't affected — a plain options object literal has no such casting.

**Sorting within (and of) groups** — `processData` sorts the flat row list _before_ `groupData` fans a multi-value column's row out into one bucket per value (e.g. a row tagged `['Action', 'RPG']` lands in both the 'Action' and 'RPG' groups). That fan-out has no single per-row comparable value to sort by ahead of time, so a multi-value sort key falls back to comparing each row's whole array (`String(array)`) — a comparison unrelated to either bucket a row lands in. This breaks two things downstream: it starves any secondary sort key from ever being reached for row order within a bucket (rarely ties between different rows), and it determines the arbitrary order `groupData` first encounters each value in, so the _groups themselves_ (e.g. which skill's header comes first) end up in no meaningful order either (see GitHub issue #12). `sortWithinGroups(groups, sorts, groupBy, columns)` (core), called right after `groupData` in all three adapters, fixes both by splitting `sorts` into entries matching a `groupBy` column (which reorder the top-level `groups` array — see "Nesting order follows `groupBy`, not `sorts`" below for exactly how) and the rest (which re-sort each group's `rows`, with the groupBy-matching entries excluded — every row in one of that column's buckets already shares its relevant value, so re-comparing it would be a no-op at best or reintroduce the same whole-array comparison at worst; dropping it lets the next sort key become the effective within-group row order, the same outcome a single-value groupBy column already got for free). Sorting by a multi-value column that is _not_ itself a `groupBy` column keeps the incidental whole-array comparison, unchanged — there's no per-bucket context to resolve it against.

## Auto-syncing group order with sort (GitHub issue #17)

Grouping by a column with no matching `sorts` entry used to leave the groups themselves in arbitrary (first-seen) order — `sortWithinGroups`' group-reorder branch only runs at all when at least one entry matches a `groupBy` key. Rather than leave that to chance, or build a separate opt-in helper that has to auto-add _and_ auto-remove sort entries while tracking which ones it "owns" vs. the user's own, each adapter's `group.toggle` add branch inserts a real, ordinary sort entry via `insertGroupSort(sorts, prevGroupBy, key, dir)` (core) — indistinguishable from one the user added by hand, so it shows up as a normal active-bar chip/Sort-dropdown row the user can reverse or remove like any other, with no provenance tracking needed:

- **Position**: the new entry lands after every existing entry for a column already in `groupBy` (so a second/third grouped column defers to the earlier ones, matching `groupBy`'s own append-on-toggle order for nesting) and before every other entry (so an unrelated column the user already sorted by keeps acting as an intra-group tie-breaker, not the primary order). If `key` already had an entry (sorted by hand before grouping), only its position moves — its existing direction is kept.
- **Ungrouping does _not_ remove the entry** — a deliberate scope cut, confirmed with the maintainer rather than assumed. It just becomes an ordinary sort from then on, reversible/removable exactly like any other. This avoids the "is this sort entry the group's or the user's" provenance question entirely, at the cost of a group's order staying pinned even after ungrouping until the user removes it manually.
- **Reordering** an active group (`group.move`/`group.moveBy` — the Group dropdown's drag/Alt+Arrow reorder) calls `reorderGroupSorts(sorts, groupBy)` (core) right after, which re-orders whichever `sorts` entries match a `groupBy` key to follow `groupBy`'s new order (skipping any grouped column with no matching entry), leaving every other entry's relative position untouched — so dragging a group to a new nesting position doesn't leave its sort priority behind at the old position.
- **Header-click sort** (`replaceSort`) gained a 4th `groupBy` param — it exempts any entry whose key is currently grouped from the usual "discard everything else" behavior, since a grouped column normally has no header of its own to reclick, and without this a plain click on some unrelated, still-visible column would silently wipe out every grouped column's sort order.

Each adapter's `group.toggle`/`moveBy`/`move` actions in `useTableState`/`createTableState` wire this (React/Vue/Solid; vanilla gets it for free by wrapping Solid's).

### `groupData`'s `Map`, not a plain object

Found while verifying the above: removing a numeric-bucketed groupBy column's sort entry (e.g. ungrouping-then-resorting a `numericRangeGroup`'d Salary column) still looked "sorted ascending" even with `sortWithinGroups`' reorder branch correctly skipped. The real cause had nothing to do with any of the above — a plain `Record<string, ...>`'s own keys enumerate any canonical non-negative integer string (`'40000'`, or a raw integer groupBy value) in ascending numeric order first, per the JS spec's "array index" key ordering, regardless of insertion order. That made "no matching sort → arbitrary order" quietly mean "always ascending" for a numeric-looking group key and "actually arbitrary" for every other key shape (e.g. a department name) — an inconsistency with nothing to do with `sorts`/`groupBy`, just an accident of using an object as the accumulator. `groupData` was fixed to use a `Map` instead, which preserves true first-seen order for every key shape.

### Nesting order follows `groupBy`, not `sorts`

With multi-level grouping (`groupBy: ['dept', 'role']`), `sortWithinGroups`' nesting comparator used to iterate `groupSorts` in **`sorts`-array order**, not `groupBy`'s own order — so a consumer (or the Sort dropdown's own drag-and-drop, before the fix below) that listed `role` before `dept` in `sorts` got nesting that visually contradicted `groupBy`'s displayed order: two sources of truth that could silently disagree. Fixed: the comparator now iterates `groupBy` directly, looking up each level's `dir` from a matching `sorts` entry (skipping a level with none, falling through to the next) — it never reads `sorts`-array position at all. `insertGroupSort`/`reorderGroupSorts` already kept the two in sync for every reachable path, so this is a pure robustness win with no lost behavior; it just becomes impossible to desync them, full stop.

### Duplicate sort entry via `keepVisibleWhenGrouped`

`replaceSort`'s `groupBy` param originally assumed a grouped column never has a header to plain-click — false for a `keepVisibleWhenGrouped` column, which keeps one. Clicking it called `replaceSort` with `key` itself already inside `groupSorts`, appending a _second_ entry for the same key instead of updating the existing one (two identical chips, both toggling/removing in lockstep). Fixed by special-casing `groupBy.includes(key)` to delegate straight to `toggleSort(sorts, key, defaultDir)` — cycle that one entry's direction in place, touch nothing else. This is also the _correct_ semantics here, not just a dedupe fix: a group column's own direction governs that group's order, and "discard everything else, start fresh" (`replaceSort`'s normal behavior) doesn't make sense for a column that's structurally a group — every other group level still needs its entry to keep its nesting position.

### The Sort dropdown: "Group order" vs. "Active sorts"

The Sort dropdown's active list used to be one flat, draggable, numbered stack mixing two different concerns — entries matching a `groupBy` column (which only ever govern group nesting, never row order across groups) and entries for everything else (the actual tie-break priority stack) — with nothing distinguishing them. That's exactly why dragging a tie-break column above a group column read as a bug rather than a no-op: it visibly "worked" (the row moved) while changing nothing. Fixed by splitting the active list into two sections, in every adapter's Sort dropdown:

- **"Group order"** (`groupOrderSection` label, plus a `groupOrderHint` pointing at the Group dropdown) — entries matching a `groupBy` key, in `groupBy`'s own order, skipping a level with no matching entry. Not draggable, no Alt+↑/↓ reorder (nesting order is never governed by anything here) — direction is still toggleable in place and the entry is still removable, exactly like any other sort.
- **"Active sorts"** (pre-existing `activeSortsSection`) now holds only non-group entries — still fully draggable/Alt+↑/↓-reorderable, but its own Alt+↑/↓ handler had to change too: it now finds its swap neighbor within this _filtered_ non-group list (via `move`/`reorderSort`, by key) instead of the raw `sorts`-array neighbor (`moveSortBy`, by index) — a group entry can sit between two non-group ones in the underlying array, and swapping with it used to silently do nothing visible in this section, the same "looks like a no-op" problem one level down.

### The active bar: one merged chip per grouped-and-sorted column

A grouped column always carries its own sort entry now, so rendering the sort-chip loop and the group-chip loop independently shows two identically-labeled chips for the same column with nothing visually linking them — a guaranteed-every-time visual duplication, easily mistaken for a bug rather than a feature. The active bar instead merges them into one pill (`dt-chip--grouped-sort` / `S.chip` + `chipXMiddle`/`chipGroupMark` / `.dt__chip--grouped-sort`): `[body: icon+label, toggles direction] [× removes the sort] [⊞ mark: opens the Group dropdown] [× removes the group]` — four segments sharing one visually-continuous pill (the same border-sharing trick as the toolbar's grouped-clear buttons), computed purely at render time by checking whether a `sorts` entry's key is also a `groupBy` key — no new state, no provenance tracking. A grouped column with no matching sort entry (removed by hand) still falls back to the old plain single-body group chip. The `⊞` segment's font-size matches its sibling segments' — line-height is relative to font-size, so a smaller font (which seemed reasonable for a bare icon) quietly made that one segment shorter than the rest of the pill.

**Ordering, in both the active bar and the Sort dropdown, and in the toolbar itself: group before non-group.** Group chips/the "Group order" section render before plain sort chips/"Active sorts", and the toolbar's own **Group** button sits before **Sort** (despite "Sort" alphabetically reading first) — grouping is the structural, primary concern (which bucket a row falls into, and in what order the buckets themselves appear) and tie-break sorting is secondary, so everything reads top-to-bottom as cause then effect.
