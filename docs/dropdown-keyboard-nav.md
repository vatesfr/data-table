# Dropdown column search and keyboard navigation

The Columns, Sort, and Group dropdowns' full column lists, and the Filter dropdown's left column pane, each gained a search box plus proper Up/Down/Home/End/Escape navigation — these lists had no way to narrow or arrow-key through them before, relying on plain sequential Tab. The bullets below describe Solid's implementation (`packages/solid/src/components/`); vanilla inherits it unchanged through the wrapper (see [Vanilla package](packages.md#vanilla-package-packagesvanilla)). React/Vue differences follow at the end.

- **Search**: a `.dt-dd-search` input (marked `data-dd-search`) always renders in each list — no column-count threshold gating its visibility — and narrows by case-insensitive match on `col.label` (or its category, via core's `columnMatchesSearch`), backed by a per-dropdown `searchTerm` signal (Filter: `colSearchTerm`). It reuses `L.filterSearchPlaceholder` rather than adding a new label — the global search box and the filter value-checklist search already share that same placeholder text, so a third reuse follows the existing precedent instead of growing `DataTableLabels` (and all 5 locale files) for what would be identical text. For Sort/Group, the search narrows only the "addable" section; the active-sorts/active-groups section above it is never hidden by a search term, since it's a short list with its own priority order and remove controls. The Columns dropdown's search is pinned at the top and narrows both its Visible and Available sections (see [Column categories](columns.md#column-categories)). The Filter dropdown's search sits `position: sticky; top: 0` inside `.dt-filter-cols` (its own scrollable pane) since it isn't a separate section the way Sort/Group's is.
- **Ordering**: the Columns dropdown keeps real table column order (`table.columns.ordered()`) in both sections — Visible doubles as the drag-to-reorder surface (see [Column reordering](column-reordering.md)), and Available deliberately isn't alphabetized either. Sort's and Group's addable lists are alphabetical-by-label (`categorizedAlphabetizedByLabel`, core) — nothing in them is sorted/grouped yet, so their definition order carries no meaning. The Filter dropdown's left pane lists active-filter columns first, then alphabetical (`orderFilterColumnsByActive`/`applyColumnOrderSnapshot`, core) — a snapshot taken when the dropdown opens, not recomputed live — and gives each active-filter column an inline `×` clear button (see [Filter dropdown](filter-dropdown.md)).
- **Keyboard nav**: `.dt-dd` is bounded to `max-height: 420px; overflow-y: auto`. `Dropdown.tsx`'s `handleKeyDown` moves focus on plain (non-Alt) `ArrowDown`/`ArrowUp` between the search input and each row's focusable element — a Columns Visible row (draggable, `×` to hide), an Available row (click to show), a Sort/Group active or addable entry, a Filter left-pane column button — clamped at the first/last row (no wrap), in actual DOM/visual order: a single `ddNavFocusables(panel)` query (core, default `DD_NAV_SELECTOR = 'input[data-dd-search], [data-dd-row]'`), not the search input prepended in front of a separately-queried row list. That distinction matters for Sort/Group specifically: their active-entries section renders _above_ the search box and the addable section renders _below_ it, so concatenating the search input first would reorder the nav to "search → active → addable" regardless of what's on screen. An open `CategorySubmenu`'s rows are excluded (it has its own nav). `Home`/`End` jump to the first/last row, skipping the search input. `Escape` clears a non-empty search term first when focus is in that search box (each dropdown's `onEscapeClearable` prop; Filter's also covers its right-pane value search); pressed again (or with an already-empty term) it closes the dropdown and refocuses its toggle button. It only acts when the focused element is one of its own focusables (`focusables.indexOf(document.activeElement)`), so it never hijacks native key behavior on unrelated controls in the same panel (a range slider thumb, a number/date input in the Filter detail pane). Row-level Alt+↑/↓ reorder and Delete/Backspace remove handlers don't stop propagation; the `e.altKey` guard keeps this handler out of the reorder combo.
- **Focus follows open**: opening a dropdown focuses inside the panel immediately — its search input if it has one, else the first row (e.g. Sort when every column is already sorted, so it has no addable section and therefore no search box). This runs in a `queueMicrotask` from the panel's `ref` callback, not synchronously: the `ref` fires before `props.children` (several component boundaries away) has been appended, so a synchronous lookup found nothing — the same reason the viewport-clamp measurement waits a microtask.
- **Activating/removing a Sort or Group column keeps focus, instead of dropping it to `<body>`**: activating an addable column moves it into the active section — a different element at a different position — and removing an active entry via its `×` does the reverse. `SortDropdown.tsx`/`GroupDropdown.tsx` refocus the equivalent new element directly, synchronously, right after the mutating `table.sort`/`table.group` call (`withPanelRefocus`, `dropdownRowActions.ts`, which resolves the panel _before_ mutating since a removed button can't `.closest()` afterward) — no pending-ref/effect indirection is needed, since Solid's signal writes update the DOM synchronously within the same call stack. `ActiveBar.tsx`'s group/filter chips also jump to the specific entry's row on open (`onOpenGroup(key)`/`onOpenFilter(key)`, wired in `DataTableView.tsx`).
- **Filter dropdown: crossing between the left column pane and the right detail pane**: `FilterDropdown.tsx`'s `handlePanelKeyDown` (bound on `.dt-filter-panel`, inside Dropdown's own panel, so it runs first via bubbling) handles plain `ArrowRight` on a `.dt-filter-col-item` (left pane) by focusing the first value search/checklist/date-tree control in `.dt-filter-detail` (right pane); plain `ArrowLeft` from the right pane returns focus to `.dt-filter-col-item--active`, _except_ when focus is on an editable `text`/`number`/`date`/`range` input, which needs native Left-arrow behavior. Delete/Backspace on a left-pane column with an active filter clears it.
  - **The right pane's own rows get the same Up/Down/Home/End treatment** as every other list here — the value checklist or the date tree, whichever is rendered for the column's type — with only the value-search box (`data-dd-value-search`) joining the vertical chain above the rows (`data-dd-value-row`); the select-all checkbox and sort-order button sit beside the search box on the same row, not above the list, so they're deliberately left out of Up/Down (still reachable via Tab/click) rather than being stepped through in a direction that wouldn't visually correspond to "down". The flat checklist is virtualized in React, Vue, and Solid (see "The flat checklist is virtualized" in [filter-dropdown.md](filter-dropdown.md)) — only a scrolled-into-view window of rows actually exists in the DOM — so crossing out of that window, or `Home`/`End` (which must reach the _logical_ first/last value of the full narrowed list, not just whatever happens to be mounted), first calls `getVirtualScrollTarget(scrollTop, viewportHeight, itemHeight, targetIndex)` (core, shared by all three) to decide the scroll adjustment needed (or `null` if the target's already visible), adjusts the scroll position accordingly (React/Vue patch `filterListScrollTop`/`checklistEl.scrollTop`; Solid sets the list element's `scrollTop` directly, which its `onScroll` mirrors into a signal), and only then focuses the checkbox matching the target value — all synchronously in the keydown handler. The date tree has no such window (every currently-expanded row is already in the DOM), so it falls through to plain DOM-order nav.
  - **The left column pane follows focus like a listbox/radiogroup, rather than needing a separate Enter/Space "activate" step** — the arrow-key nav above only ever calls a plain `.focus()` on a `.dt-filter-col-item`; a delegated `onFocusIn` on `.dt-filter-cols` (`focusin`, unlike `focus`, bubbles) is what actually sets the active column, and it fires for _every_ way focus can land there — arrow-key nav, Tab/Shift+Tab, and a mouse click. Each button's own `onClick` stays alongside it, since Safari doesn't focus a `<button>` on a plain mouse click.

`TableBody`'s row-nav page-boundary crossing (Ctrl/Cmd+Home/End, Arrow-at-an-edge) is covered in "Crossing page boundaries" in [keyboard-navigation.md](keyboard-navigation.md).

**React/Vue** — both fully implement everything in this document, and share the same core design (the same generic panel-level roving-nav handler driven by two DOM markers as Solid):

- A `data-dd-search` attribute marks a dropdown's own column-search `<input>`, and a `data-dd-row`-equivalent selector (React: core's default `DD_NAV_SELECTOR`, via `ddNavFocusables`; Vue: `Dropdown.vue`'s `rowSelector` prop, defaulting to `DEFAULT_ROW_SELECTOR`) covers every row type (Columns/Sort/Group rows, Filter's left-pane buttons) — the same two markers drive both the roving Up/Down/Home/End nav _and_ focus-on-open, so the two can't drift apart. This lives in `Dropdown.tsx`/`Dropdown.vue` itself (a `useLayoutEffect`/`watch(..., {flush:'post'})` for focus-on-open, an `onKeyDown`/`@keydown` handler for the roving nav) rather than per-dropdown in `DataTableView`, since neither component needs to know which concrete dropdown it's rendering.
- Escape (clear search term first, else close + refocus trigger) is handled per-search-input inline in React (each search `<input>`'s own `onKeyDown`) and via the panel's shared keydown handler in Vue; both close by calling into the `Dropdown` component's own exposed close/open API (Vue: `defineExpose({ open, close, focusTrigger })`; React: the pre-existing controlled `open`/`setOpen` props) rather than Solid's shared `openDropdown` signal.
- The Filter dropdown's pane-crossing (Left/Right) and right-pane row nav (including the virtualized checklist's scroll-then-focus dance for Home/End and window-crossing) is its own separate handler bound on the filter panel itself in both adapters (React: `handleFilterPanelKeyDown`; Vue: folded into the same keydown handler via a `.dt__filter-detail` check), since it needs to reach filter-specific DOM the generic `Dropdown` component knows nothing about.
- Focus-follows-selection in the Filter left pane is a plain `onFocus`/`@focus` handler on each column button (guarded against re-selecting the already-active column) — no delegated listener needed, since each button already has its own handler in JSX/template.
- The Sort/Group activate/remove focus-retention fix (moving a column between the active and addable sections) _is_ still needed in both — neither framework's reconciliation preserves focus across that transition, since the two sections are structurally different list-render blocks, not a reordering of one list. React: a pending-focus-key ref per list (`pendingSortFocusKey`/`pendingGroupFocusKey`) picked up by a `useLayoutEffect` once the state update commits (same "can't focus synchronously across an async update" shape as the existing `pendingFocusTarget`/keyboard-navigation page-boundary handling). Vue: a plain ref map per list (`sortRowRefs`/`addableSortRefs`/etc.) plus `await nextTick()` before refocusing. Toggling a _sort chip's_ direction, by contrast, needs no such fix in either framework — same key/element identity survives the update, so focus just stays for free (see [Active-bar chip click actions](toolbar.md#active-bar-chip-click-actions)).
- Alt+ArrowUp/Down reordering an active Columns/Sort/Group row needs the same explicit refocus in Vue and Solid/vanilla — confirmed empirically that both frameworks' keyed reconciliation still drops focus to `<body>` when it repositions a row's DOM node, even though (unlike activate/remove above) the row stays in the _same_ list the whole time. React is the one adapter that doesn't need this: it keeps the same DOM node in place across the reorder with no observable focus loss, so only Vue/Solid gained the fix (Vue reuses its pre-existing `activateAndFocus`/ref-map helper from the activate/remove case above; Solid resolves the panel before the mutating call and refocuses by key afterward via `withPanelRefocus`, same as its remove buttons).
