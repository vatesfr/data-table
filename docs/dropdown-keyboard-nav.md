# Dropdown column search and keyboard navigation

The Columns, Sort, and Group dropdowns' full column lists, and the Filter dropdown's left column pane, each gained a search box plus proper Up/Down/Home/End/Escape navigation — these lists had no way to narrow or arrow-key through them before, relying on plain sequential Tab. The bullets below describe the feature in vanilla's own terms (its identifiers/markup); see the "Vanilla/React/Vue" bullet at the end of this section for how each adapter implements the same behavior.

- **Search**: a `.dt-dd-search` input (`data-action="dd-search"`, `data-dd="cols"|"sort"|"group"|"filter"`) always renders at the top of each list — no column-count threshold gating its visibility, unlike some other conditionally-shown controls in this file — and narrows the list below by case-insensitive substring match on `col.label`, via `ddSearchTerms: Record<string, string>` (ephemeral UI state, same category as `filterSearchTerms`/`filterActiveCol` — keyed by dropdown id rather than by column, since here there's one search per whole dropdown rather than per column). It reuses `L.filterSearchPlaceholder` rather than adding a new label — the global search box and the filter value-checklist search already share that same placeholder text, so a third reuse follows the existing precedent instead of growing `DataTableLabels` (and all 5 locale files) for what would be identical text. For Sort/Group, the search narrows only the "addable" section; the active-sorts/active-groups section above it is never hidden by a search term, since it's a short list with its own priority order and remove controls. The Filter dropdown's search sits `position: sticky; top: 0` inside `.dt-filter-cols` (its own scrollable pane) since it isn't a separate section the way Sort/Group's is.
- **Ordering**: the Columns dropdown keeps listing `orderedColumns` (real table column order) unchanged — it doubles as the drag-to-reorder surface (see "Column reordering"), so alphabetizing it would conflict with that order's own meaning. Sort's and Group's addable lists, and the Filter dropdown's left column pane, switched from raw column-definition order to alphabetical-by-label — none of those three lists had an order that carried any meaning (nothing in them is sorted/grouped/filtered yet), so alphabetizing just makes a long list easier to scan. None of the four pin "active"/visible columns first — Sort/Group already separate active from addable into two sections, and Filter already flags an active column with a dot marker (see "Filter dropdown"), so a third active-first treatment would be redundant.
- **Keyboard nav**: `.dt-dd` itself gained `max-height: 420px; overflow-y: auto` (previously unbounded — a table with many columns could render a dropdown taller than the viewport with no way to scroll it). Plain (non-Alt) `ArrowDown`/`ArrowUp` move focus between the search input and each row's actual focusable element (a row's own `<button>`/`tabindex="0"` div, or — for a Columns row, which carries no tabindex of its own, see "Column reordering" — its checkbox), clamped at the first/last row (no wrap), in actual DOM/visual order — a single combined `querySelectorAll` covering the search input and every row selector together, not the search input prepended in front of a separately-queried row list. That distinction matters for Sort/Group specifically: their active-entries section renders _above_ the search box and the addable section renders _below_ it (active → search → addable, matching what's on screen), so building the search input as its own array and concatenating it first used to silently reorder the nav to "search → active → addable" regardless of what was actually on screen above/below it. `Home`/`End` jump to the first/last row, skipping the search input. `Escape` clears a non-empty search term first (focus stays in the box); pressed again (or with an already-empty term) it closes the dropdown and refocuses its toggle button — this also covers the Filter dropdown's value-search box (`data-action="filter-search"`, clearing `filterSearchTerms` instead of `ddSearchTerms`), checked as a second, independent condition right alongside the column-search one. This is a new, generic `handleKeyDown` block scoped to whichever `.dt-dd` is open, and deliberately runs _before_ the existing sort-row/group-row/column-row handlers (Alt+↑/↓ reorder, Enter/Space toggle — see "Column reordering") since those unconditionally `return` even for a key they don't handle, which would otherwise swallow a plain arrow key before this block ever saw it; it only acts on a key when the currently-focused element is genuinely one of its own (search input or a row's focusable target) — checked via `focusables.indexOf(document.activeElement)` — so it never hijacks native Left/Right/Up/Down/Home/End behavior on unrelated controls sitting in the same `.dt-dd` (a range-filter slider thumb, a plain number/date input) in the Filter dropdown's right-hand detail pane.
- **Focus follows open**: clicking (or Enter/Space-activating) a dropdown's toggle button now focuses inside the panel immediately — its search input if it has one, else the first active row (e.g. the Sort dropdown when every column is already sorted, so it has no addable section and therefore no search box) — via `focusFirstInDropdown(dd)`, called right after `render()` in the `toggle-dd` click handler whenever `openDropdown === dd` (i.e. this click _opened_ it, not closed it). Previously focus stayed on the toggle button, needing an extra Tab before any of the nav above did anything.
- **Activating/removing a Sort or Group column keeps focus, instead of dropping it to `<body>`**: clicking (or Enter/Space-activating) an addable column's button moves it into the active section — a different element (a `sortrow`/`grouprow` div) at a different position — and `render()`'s `innerHTML` rebuild destroys the button that had focus; the reverse (removing an active entry via its `×`) has the same problem in the other direction. Neither element carries the same `data-focus-key` before and after (the addable buttons have none at all — only the active rows and the search inputs do), so the generic focus-key restore at the top of `render()` has nothing to match and focus was silently lost. `toggle-sort`/`toggle-group`/`remove-sort`/`remove-group` each now explicitly refocus the equivalent new element right after the shared `render()` call in `handleClick` — the new active row (by its `sortrow-${key}`/`grouprow-${key}` focus key) when adding, or the now-addable button (by `data-key`) when removing.
- **Filter dropdown: crossing between the left column pane and the right detail pane**: plain `ArrowRight` on a `.dt-filter-col-item` (left pane) focuses the first focusable control in `.dt-filter-detail` (right pane) — whatever that is for the column's type (the select-all checkbox for a string column, a range-min input for number/date); plain `ArrowLeft` from anywhere in the right pane returns focus to `.dt-filter-col-item--active`, _except_ when focus is on an actual editable control (`filter-search`, `range-min`, `range-max`, `range-slider`) — those need native Left-arrow cursor/value behavior, so `ArrowLeft` is left untouched there. This pane-crossing check runs first, ahead of the column-list `ddPanel` block above (same "runs before, so it isn't swallowed" reasoning), keyed off `.dt-filter-col-item`/`.dt-filter-detail` rather than `.dt-dd` generally.
  - **The right pane's own rows get the same Up/Down/Home/End treatment** as every other list here — the value checklist (`.dt-dd-item` inside `.dt-filter-list`) or the date tree (`.dt-date-tree-item` inside `.dt-date-tree-wrap`), whichever is rendered for the column's type — with only the value-search box (`filter-search`) joining the vertical chain above the rows; the select-all checkbox and sort-order button sit beside the search box on the same row (`.dt-filter-search-row`), not above the list, so they're deliberately left out of Up/Down (still reachable via Tab/click) rather than being stepped through in a direction that wouldn't visually correspond to "down". The flat checklist is virtualized (see "The flat checklist is virtualized" above) — only a scrolled-into-view window of rows actually exists in the DOM — so crossing out of that window, or `Home`/`End` (which must reach the _logical_ first/last value of the full narrowed list, not just whatever happens to be mounted), first computes the target row's pixel offset and adjusts `filterListScrollTop`/`checklistEl.scrollTop`, patches `.dt-filter-list`'s `innerHTML` via the same `buildFilterListInnerHtml` the scroll handler already uses (see "Vanilla" under "The flat checklist is virtualized"), and only then focuses the checkbox matching the target value — all synchronously in the keydown handler, not routed through the scroll listener's own `requestAnimationFrame` throttling. The date tree has no such window (every currently-expanded row is already in the DOM, same as any other dropdown list), so it falls through to the same plain DOM-order nav the column lists use.
  - **The left column pane follows focus like a listbox/radiogroup, rather than needing a separate Enter/Space "activate" step** — the arrow-key nav above only ever calls a plain `.focus()` on a `.dt-filter-col-item`; a delegated `focusin` listener (`handleFilterColFocus`, registered on `container` since `focusin`, unlike `focus`, bubbles) is what actually updates `filterActiveCol`/resets `filterListScrollTop`/re-renders/refocuses the equivalent new button, and it fires for _every_ way focus can land there — arrow-key nav, Tab/Shift+Tab, and a mouse click (which focuses the button natively before the click handler's own `select-filter-col` case even runs). It's guarded by comparing the focused button's key against the _resolved_ active key (`resolveFilterActiveKey`, the same fallback-to-first-filterable-column logic the render side already uses) rather than the raw `filterActiveCol` — so focusing the already-effectively-active column (e.g. on initial mount) is a no-op — and that same guard is what stops the handler from looping: refocusing the new node after `render()` fires another `focusin`, but by then `filterActiveCol` already matches so the second call returns immediately.

**Vanilla** — everything above is this adapter's own implementation (`ddSearchTerms`, the generic `handleKeyDown` block scoped to whichever `.dt-dd` is open, `handleFilterColFocus`).
**React/Vue** — both share the same core design (a generic panel-level roving-nav handler driven by two DOM markers rather than vanilla's per-dropdown string building) instead of duplicating vanilla's exact mechanics one-for-one:

- A `data-dd-search` attribute marks a dropdown's own column-search `<input>`, and a `data-dd-row`-equivalent selector (React: a shared `DD_NAV_SELECTOR` constant in `Dropdown.tsx`; Vue: a shared `DD_ROW_SELECTOR` constant in `DataTableView.vue`) covers every row type (Columns/Sort/Group rows, Filter's left-pane buttons) — the same two markers drive both the roving Up/Down/Home/End nav _and_ focus-on-open, so the two can't drift apart. This lives in `Dropdown.tsx`/`Dropdown.vue` itself (a `useLayoutEffect`/`watch(..., {flush:'post'})` for focus-on-open, an `onKeyDown`/`@keydown` handler for the roving nav) rather than per-dropdown in `DataTableView`, since neither component needs to know which concrete dropdown it's rendering.
- Escape (clear search term first, else close + refocus trigger) is handled per-search-input inline in React (each search `<input>`'s own `onKeyDown`) and via the panel's shared keydown handler in Vue; both close by calling into the `Dropdown` component's own exposed close/open API (Vue: `defineExpose({ open, close, focusTrigger })`; React: the pre-existing controlled `open`/`setOpen` props) rather than vanilla's closure-held `openDropdown` string.
- The Filter dropdown's pane-crossing (Left/Right) and right-pane row nav (including the virtualized checklist's scroll-then-focus dance for Home/End and window-crossing) is its own separate handler bound on the filter panel itself in both adapters (React: `handleFilterPanelKeyDown`; Vue: folded into the same keydown handler via a `.dt__filter-detail` check), since it needs to reach filter-specific DOM the generic `Dropdown` component knows nothing about.
- Focus-follows-selection in the Filter left pane is a plain `onFocus`/`@focus` handler on each column button (guarded against re-selecting the already-active column) — no delegated listener needed, since each button already has its own handler in JSX/template, unlike vanilla's single closure-scoped `container`.
- The Sort/Group activate/remove focus-retention fix (moving a column between the active and addable sections) _is_ still needed in both — neither framework's reconciliation preserves focus across that transition, since the two sections are structurally different list-render blocks, not a reordering of one list. React: a pending-focus-key ref per list (`pendingSortFocusKey`/`pendingGroupFocusKey`) picked up by a `useLayoutEffect` once the state update commits (same "can't focus synchronously across an async update" shape as the existing `pendingFocusTarget`/keyboard-navigation page-boundary handling). Vue: a plain ref map per list (`sortRowRefs`/`addableSortRefs`/etc.) plus `await nextTick()` before refocusing. Toggling a _sort chip's_ direction, by contrast, needs no such fix in either framework — same key/element identity survives the update, so focus just stays for free (see "Active-bar chip click actions").
