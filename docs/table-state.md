# TableState

## Namespaced TableState

`useTableState`/`createTableState`'s returned object used to be one flat ~45-field object — every raw state signal, every derived value, and every action as a sibling top-level property, with no grouping. That was hard to scan (autocomplete on `table.` is a wall of ~45 entries) and made related concerns (e.g. `sorts`/`toggleSort`/`replaceSort`/`moveSortBy`/`getSortIcon`, all "sort") look unrelated to each other purely because they didn't share a prefix consistently.

The shape is now namespaced by concern — one sub-object per feature area, each holding that area's own state and actions with the redundant prefix dropped (`toggleSort` → `sort.toggle`, `moveGroupBy` → `group.moveBy`):

- **`columns`** — `{ visible, active, ordered, toggleVisibility, move, moveBy }`, plus Solid-only `list`/`set` (the raw full column array/setter — React/Vue never had this on `TableState` at all, since they get fresh `columns` as a constructor argument instead)
- **`sort`** — `{ entries, toggle, replace, appendOrToggle, remove, toggleDir, move, moveBy, clear, icon, index }`
- **`filter`** — `{ include, exclude, ranges, activeCount, valueMap, toggleAll, setValues, cycleValue, clearExcludeValues, setRange, clearColumn, clear }`
- **`group`** — `{ by, collapsed, defaultCollapsed, toggle, remove, move, moveBy, toggleCollapse, clear }`
- **`selection`** — `{ all, rows, toggle, toggleAll, clear }`, plus Solid/vanilla-only `setAll` (was `setSelectionRows` — replaces the selection outright by reference, backing vanilla's imperative `setSelection(rows)`, which has no reactive value of its own to mutate directly)
- **`pagination`** — `{ page, pageSize, numPages, setPage, setPageSize }`. `page` is always the already-clamped value (`Math.min(rawPage, numPages)`) — `numPages` can shrink (a group collapsing, data changing) without any `setPage` call, and exposing the raw, pre-clamp state would leave the page label/prev/first-page button state stale until the next explicit navigation. `setPage` still clamps against `numPages` at set time the same as before; only what's read back changed. All three of React/Vue/Solid derive `page` this way (`clampedPage` was already computed internally for `pagedData`/`groupedData` in every adapter — only the public field was still the raw one). Solid's `Pagination.tsx` used to re-derive this itself locally since the underlying fix lived only in the component, not `createTableState`; that workaround is gone now that the table-level `page` is already clamped.
- **`search`** — `{ query, setQuery }`
- **`focus`** — `{ target, row, setTarget, moveTo }` (GitHub issue #24) — the roving-tabindex "current" item, lifted here from the render layer (React/Vue's `DataTableView`, Solid's `TableBody`) so it's reachable/settable from outside the rendered table, e.g. a lightbox with its own prev/next syncing which row the table highlights. `target: VisibleItem<TRow> | null` is the raw value (a row or a group header); `row` is the common-case derived accessor (`target.kind === 'row' ? target.row : null`); `setTarget` is the low-level setter the built-in keyboard nav itself uses. `moveTo(row, options?: { focus?: boolean })` is the one meant for external callers: it force-expands whichever group(s) `row` belongs to if collapsed, jumps to the page containing it, and sets it as the focus target — but never moves real DOM focus itself by default (only an actual keyboard interaction does that), so it can't steal focus from whatever else on the page currently owns it, unless `{ focus: true }` opts into that too (a typed option added deliberately instead of documenting an internal DOM class name/attribute as public API — see the doc link below). See [docs/keyboard-navigation.md](keyboard-navigation.md)'s "External row focus". Vanilla has no reactive state to expose `focus` through, so it gets a flat `focusRow(row, options?)` method instead (delegates to Solid's `table.focus.moveTo`), matching its usual flattened-namespace convention.

Stays top-level — these are the pipeline's actual output, not a "concern" of their own, and nesting the single most commonly accessed values under one more property hop would hurt the common case for no benefit: `data`/`setData` (Solid only), `processedData`, `pagedData`, `groupedData`, `visibleItems`, `labels` (was `L`), `getViewState`/`setViewState` (cross-cutting; `persistence.ts` in every adapter reaches these and nothing else, so this split leaves it completely untouched), `clearAll` (also cross-cutting).

`filter` keeps all six of its mutators despite the temptation to trim it further (e.g. one `setColumn(key, patch)` replacing all six) — `clearExcludeValues` looked like it was purely `toggleAll`'s own internal helper for clearing stale exclusions before a "select all", but `FilterDropdown`'s shift-click checklist range-select calls it directly too, so it's genuinely part of the built-in UI's own needs, not just an implementation detail safe to fold away.

This reduces top-level members from ~45 to 15 (7 namespace objects + 8 top-level entries), a real cut in perceived surface area, at the cost of being a breaking change — every field/action moved. Pre-1.0 (core is at 0.8.0, Solid at 0.1.0), so this shipped as a hard cut with no flat-property compatibility shim, rather than a getter-based deprecation bridge that would add real runtime complexity for a temporary bridge undermining the entire point of the change. **All three of Solid, React, and Vue are migrated to this shape** (see their own package sections above) — `TableState<TRow>` is consistent across every adapter (only `@vates/data-table-vanilla`'s own `DataTableInstance` differs, since it always had its own distinct public method names rather than exposing `TableState` directly, and needed no changes here). `focus` (see above) was added later, as an 8th namespace, for the same reasons.

## Reconciling `visibleCols` against a replaced column set

`table.columns.visible` (`visibleCols` internally) is normally seeded once (from `initialViewState.visibleCols`, or every initial column — see "Column definition") and otherwise only ever mutated by `table.columns.toggleVisibility`. Every adapter's `table.columns.active` is filtered by it, so if a table's whole `columns` can be swapped for a differently-keyed set without a fresh mount — a consumer keeping the same `<DataTable>`/`TableState` but changing what kind of data it shows, e.g. `xapi-data-table`'s `ObjectsView` switching between XAPI object types — an unreconciled `visibleCols` would still hold the _old_ keys, none of which exist in the new `columns`, and every column would filter out as "not visible": the table would silently render with none at all.

`reconcileVisibleColumns(prevColumns, nextColumns, visibleCols)` (core) fixes this: a column present in both keeps whatever visibility choice it had; a column only in `nextColumns` (genuinely new) starts visible by default, the same default used when no `initialViewState.visibleCols` override is given at construction. This also covers a fully disjoint replacement for free — with nothing carried over to preserve, every column in `nextColumns` counts as "new" and ends up visible.

Each adapter reaches this from a different trigger, matching how each already owns `columns`:

- **Solid** — `createTableState.columns.set` (its own explicit setter, exposed publicly and also used internally by the accessor-tracking effect) calls it directly: `setVisibleCols((prevVisible) => reconcileVisibleColumns(prevColumns, cols, prevVisible))`, where `prevColumns` is `columns()` read just before the signal is updated.
- **React** — `useTableState` gets fresh `columns` on every render (no explicit setter of its own), so the reconciliation runs inline during render, comparing against the previous render's column keys — the same "adjust state when a prop changes" pattern already used for `filterListScrollTop` in `DataTableView.tsx` (a plain `if` calling `setState` synchronously during render, not inside an effect, which both avoids an extra render and sidesteps the `react-hooks/set-state-in-effect` lint error). A `sameKeySet` guard (order-insensitive) prevents this from re-running every render when `columns` is a fresh array with the identical key set — without it, the state update on every render would defeat the whole "only reconcile on a genuine key-set change" point.
- **Vue** — a `watch(columns, (nextColumns, prevColumns) => { visibleCols.value = reconcileVisibleColumns(...) })`, since `useTableState` (like Solid's `createTableState`) is only called once per component instance, unlike React's re-invocation-per-render — `watch` is Vue's equivalent mechanism for reacting to a later change. `watch` is lazy by default (no `immediate`), so it never runs against the very same `columns.value` that already seeded `visibleCols` above it.
