# Keyboard navigation

Rows use a **roving tabindex**: exactly one item — a data row _or a group header row_ — is a Tab stop at a time (`tabIndex`/`tabindex` `0`, the rest `-1`), arrow keys move it. This only covers the table body; toolbar buttons, dropdowns, and filter checkboxes are already native focusable elements and needed no changes.

- **`getVisibleRows(groups, collapsedGroups, defaultCollapsed)`** (core) flattens `groupData`'s result into a `VisibleItem<TRow>[]` sequence — `{ kind: 'row', row, groupKey }` or `{ kind: 'group', key }` — in display order: a group header for every group (even a collapsed one, so it stays reachable to re-expand), followed by its rows unless it's collapsed. This is the Up/Down/Home/End order: a collapsed group's rows are not valid arrow-key targets, but its header always is, and expanding/collapsing a group changes what else is reachable. Called with the _full_ grouped data (see "Pagination"), not just the current page's slice. `isSameVisibleItem(a, b)` (core) compares two items — rows by object identity, groups by key — and `indexOfVisibleItem(items, target)` finds `target`'s index (or `-1`), used everywhere a stored focus target needs to be relocated inside a freshly-computed sequence.
- Each adapter derives `navigableItems` from `getVisibleRows`'s result by filtering out row items when the table isn't otherwise interactive: `items.filter(item => item.kind === 'group' || rowNavEnabled)` where `rowNavEnabled = selectable || !!onRowClick`. Group headers are **never** filtered out this way — collapsing a group is already a plain click away regardless of `selectable`/`onRowClick`, so a header is always a valid Tab stop whenever grouping is active, even in an otherwise display-only table.
- The currently-tabbable item is tracked as `focusTarget: VisibleItem<TRow> | null` — ephemeral UI state, same category as `selectionAnchor`/`hoveredRow`, not part of `TableViewState`. Each render derives `effectiveFocusTarget = focusTarget && indexOfVisibleItem(navigableItems, focusTarget) !== -1 ? focusTarget : navigableItems[0]`, the same "stale state still renders something sane" fallback used for `filterActiveKey`/`visibleCols` — so a focused item that scrolls out of view (sorted/filtered/grouped away, or its group collapsed) self-heals to the first navigable item instead of leaving no tab stop at all.
- **Key bindings**, handled on the row/header itself: `ArrowUp`/`ArrowDown` move focus one item (row or group header, whichever is next in `navigableItems`); when pagination is active, moving past the current page's first/last item crosses into the previous/next page instead of clamping there (see "Crossing page boundaries" below) — **React and Vue only**, see the per-adapter Solid bullet below for why Solid stops at the page edge instead. `Home`/`End` jump to the first/last navigable item _of the current page_; `Ctrl+Home`/`Ctrl+End` (or `Cmd+Home`/`Cmd+End` on Mac) jump to the true first/last item across _all_ pages, matching the spreadsheet/ARIA-grid convention — again React/Vue only; Solid's `Home`/`End` only ever jump within the current page, with no `Ctrl`/`Cmd` variant at all. On a **data row**: `Space` calls `toggleRowSelection(row, shiftKey)` (only when `selectable`); `Enter` fires `onRowClick`/`rowClick` (only when it's set), reusing the exact same handler the row's click already calls. On a **group header**: `Enter` always toggles that group's collapse state — unconditionally, mirroring the header's own `onClick`, since collapsing has never depended on `selectable`/`onRowClick` — and `Space` toggles the group's own select-all checkbox (only when `selectable`), mirroring a data row's `Space`. `Shift+ArrowUp/Down/Home/End` (and `Shift+Ctrl+Home/End`) additionally call `toggleRowSelection(target, true)` before moving focus, but only when the target is a row — landing on a group header via a shift-key press just moves focus, since a header isn't a rangeable selection unit at the row level. This composes for free with the existing anchor/`selectRange` logic (see "Row selection" above) with no new core primitive; it also means a shift-crossing selection already spans a page boundary correctly, since `toggleRowSelection`'s range computation runs over `processedData` (the full order), not the current page's slice.
- The row checkbox gets `tabIndex={-1}` / `tabindex="-1"` unconditionally when `selectable` — with row-level keyboard interaction (`Space`/`Shift+Arrow`) covering selection, a separately-tabbable checkbox would just be a redundant second Tab stop per row. Clicking it with a mouse is unaffected; only its presence in sequential Tab order changes. The group header's own select-all checkbox is left natively tabbable (no `tabIndex` override) since, unlike a data row, a header wasn't already part of a "roving" single-stop model before this feature — it wouldn't be a _redundant_ stop.
- `onRowClick` (React/vanilla) and the `rowClick` emit (Vue) are typed to accept `MouseEvent | KeyboardEvent` (`React.KeyboardEvent<HTMLTableRowElement>` in React) instead of just a click event, since `Enter` now fires the same callback with the keyboard event instead of a mouse event. Consumers that only read the row argument are unaffected; ones that read `event.shiftKey` or call `stopPropagation()` still work since both event types share those.
- Selected rows get `aria-selected` (`selectable` only) so the selection state is announced, matching native listbox/grid conventions, without adopting a full ARIA grid (`role="grid"`, per-cell focus) — this table's interactions are all row-level (selection, click, range), never per-cell, so a lighter row-level model was chosen over the heavier grid pattern. Group headers get `aria-expanded` (always, whenever grouping is active) reflecting their collapsed state, matching the standard disclosure-widget ARIA pattern now that they're keyboard-operable.

**Crossing page boundaries** (React/Vue only — see the Solid bullet below): `navigableItems` covers only the _current_ page — `paginateVisibleItems(visibleItems, page, pageSize)` (core), filtered by the same `rowNavEnabled` rule. `visibleItems` (exposed from `useTableState`/`derive()`) already covers the _full_ filtered/grouped dataset (see "Pagination"), so reaching an item on another page (an ArrowUp/ArrowDown at the edge, or Ctrl+Home/Ctrl+End) is just re-slicing that same array for a different page — no re-grouping needed (a meaningful simplification over the old paginate-then-group pipeline, which had to re-run `groupData`+`getVisibleRows` from scratch for every arbitrary page). `Ctrl`/`Cmd+Home` targets page `1`, `Ctrl`/`Cmd+End` targets `numPages`, taking the first/last item returned; a boundary ArrowDown targets `page + 1`'s first item, ArrowUp targets `page - 1`'s last item. `getCrossPageFocusTarget(visibleItems, page, numPages, pageSize, mode, rowNavEnabled)` (core) is this decision logic itself — given either `{ kind: 'edge', delta: 1 | -1 }` (the Arrow-at-an-edge case) or `{ kind: 'jump', toEnd }` (the Ctrl/Cmd+Home/End case), it returns `{ targetPage, item }` or `null` if there's nowhere to go. Extracted here specifically because it was previously duplicated near-verbatim between React's and Vue's own `DataTableView` (each with its own inline `visibleItemsForPage` helper) — this is the one core function shared by every adapter that implements page-boundary crossing at all, rather than each reimplementing the same page-slicing arithmetic.

Per-adapter wiring:

- **React** — `focusTarget` (`useState`) plus a `rowRefs = useRef(new Map<TRow | string, HTMLTableRowElement>())` populated via each row/header's callback `ref` (rows keyed by object identity, headers by their group key string — a plain `Map` allows both key types with no collision risk). Moving focus calls `.focus()` on the target's ref synchronously inside the key handler (not via an effect) — the item is already mounted, so this is simpler than waiting a render cycle. `onFocus` (bubbling in React, unlike the native `focus` event) keeps `focusTarget` in sync when focus lands on an item via Tab or via a mouse click on its (now `tabIndex={-1}`) checkbox. Crossing a page boundary calls `setPage`, whose state update re-renders asynchronously — the item to focus can't be reached via a ref until that render commits, so it's stashed in a `pendingFocusTarget` ref and a `useEffect` keyed on `[page]` calls `focusItem` once the effect fires (i.e. after the new page's items are mounted).
- **Vue** — the same shape: `focusTarget` (`shallowRef` — not `ref`, since `VisibleItem<TRow>` embeds a `TRow` field and Vue's deep-unwrap conflicts with the generic constraint here the same way it does for `selection`, see "Row selection"), a plain (non-reactive) `rowRefs` `Map<TRow | string, HTMLTableRowElement>` populated via a function `:ref`, and `@focusin` (which, unlike `@focus`, bubbles natively) instead of React's auto-bubbling `onFocus`. Crossing a page boundary mirrors React's `pendingFocusTarget` + effect approach, but as a plain closure variable plus `watch(page, ..., { flush: 'post' })` — `flush: 'post'` (rather than the default `'pre'`) is what makes the callback run after the DOM actually updates, so `rowRefs` already holds the new page's items by the time it fires.
- **Solid** — `TableBody.tsx` owns this directly; it's the one adapter package with a real, standalone keyboard-nav implementation of its own (see CLAUDE.md's "Solid package" — a real Solid+TSX adapter, not a hand-rolled `innerHTML`-rebuilding one). `focusTarget` is a `createSignal<VisibleItem<TRow> | null>`; `rowRefs` is a plain `Map<TRow | string, HTMLElement>` (rows keyed by object identity, group headers by a `` `group:${key}` `` string) populated and pruned by a `trackRowRef` helper called from each row/header's own `ref` callback, with a matching `onCleanup` so a long-lived table that periodically calls `setData` with fresh row objects doesn't accumulate one stale `Map` entry (pinning a detached DOM node) per row ever seen. `effectiveFocusTarget` is a `createMemo` doing the same self-heal-to-first-navigable-item fallback described above; `moveFocus`/`jumpFocus` compute the next item from `navigableItems` and call `setFocusTarget` plus `.focus()` on the matching ref synchronously in the keydown handler — no pending-ref/effect indirection is needed for a same-page move, since the target is already mounted. Solid does **not** implement crossing a page boundary at all: `Home`/`End` only jump to the first/last item of the _current_ page, and there is no `Ctrl`/`Cmd+Home`/`End` equivalent — a deliberate, documented simplification (see CLAUDE.md's "Known, deliberate simplifications vs. React/Vue"), not an oversight; the file's own comment calls out the async pending-focus-target mechanism React/Vue need for this as "the single most involved piece of the original keyboard-nav design," flagged as a follow-up rather than built now. The row/group list itself renders via `<Index each={table.groupedData()}>` rather than `<For>`: `groupedData()` (from `paginateVisibleGroups`) returns fresh `PagedGroup` object references on every recompute — even when only a group's collapsed state changed — which would make a reference-keyed `<For>` remount every group's header/rows (dropping focus to `<body>`) on a plain collapse toggle; `<Index>` tracks by array position instead, reusing the same row/header component instance whenever the group count/order is unchanged.
- **Vanilla** — inherits Solid's `TableBody` keyboard-nav behavior wholesale through `@vates/data-table-vanilla`'s thin wrapper (see CLAUDE.md's "Vanilla package"): `createDataTable` mounts Solid's `DataTableView`/`TableBody` via `solid-js/web`'s `render()` and has no keyboard-navigation wiring of its own anymore — no closure-held `focusTarget`, no delegated `keydown` container listener resolving `.dt-tr[data-proc-idx]`/`.dt-group-row[data-gkey]` ancestors, no `innerHTML`-rebuild focus-restore step. That hand-rolled mechanism (previously described here) no longer exists in `packages/vanilla/src/` — it moved to, and was rewritten as, the Solid-native implementation in the bullet above when `packages/solid` was split out of `packages/vanilla`.
