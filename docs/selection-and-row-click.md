# Row selection and row click

## Row selection

Selection lives in `useTableState` in both adapters. Key design notes:

- Selection is tracked as `Set<TRow>` by **object identity** — no `rowKey` dependency. Row references must be stable (the same object in memory) across re-renders for selection to persist through sort/filter changes. `rowKey`'s own JSDoc (all three adapters' `types.ts`) and each README's props table now spell this out explicitly — it's a rendering-identity hint only (React `key`/Vue `:key`/vanilla DOM key), not a selection identifier the way "row key" reads in most other table libraries (TanStack Table, AG Grid, MUI); this was previously undocumented and easy to assume otherwise.
- **`getRowId?: (row: TRow) => string | number`** (all four adapters' options, alongside `initialViewState`/`labels`/etc.) is the opt-in escape hatch for the identity limitation just above: a refetch or re-map of `data` that produces new row objects (even with identical content) silently drops object-identity selection, since a `Set` can only ever match by reference. Supplying it switches selection to match by id instead, surviving that kind of refresh. Built entirely in core (`logic.ts`'s "Selection identity" section) as a handful of `getRowId?`-parameterized functions that are a no-op passthrough to today's exact object-identity behavior when omitted, so this is purely additive — nothing changes for a consumer who doesn't set it:
  - `isRowSelected(selection, row, getRowId?)` / `getSelectedRows(rows, selection, getRowId?)` — the membership check and its array-filter form (the latter backs `selectedRows`), matching by id (linear scan / one id-`Set` built up front) instead of `Set.has` when `getRowId` is given.
  - `toggleRowInSelection(selection, row, getRowId?)` / `toggleAllInSelection(selection, rows, getRowId?)` — replace each adapter's own inline `Set` add/delete logic in `toggleRowSelection`/`toggleSelectAll`; with `getRowId`, "toggle" finds and removes whichever existing entry shares the row's id (not necessarily the exact reference passed in) rather than requiring an exact match.
  - `reconcileSelection(nextData, selection, getRowId?)` — run whenever `data` changes, remaps each selected id to its fresh object reference in `nextData` and drops ids no longer present. React does this inline during render (the same `data !== prevData` "adjust state when a prop changes" pattern as the `visibleCols`/`columnKeys` reconciliation); Vue via a `watch(data, ...)`; Solid inside a wrapped `setData` (mirroring `setColumns`'s own `visibleCols` reconciliation wrapper); vanilla gets it for free through Solid's `setData`.
  - Shift-click range selection (`selectRange`) is **not** id-aware — the anchor/target still match by reference within `processedData`, so a data refresh between a plain click and a later shift-click can fall back to selecting just the target, the same pre-existing fallback that already applies when the anchor is sorted/filtered away. Not fixed here; considered acceptable given the anchor is always re-set to the exact just-clicked row on every non-shift click, so this only bites a shift-click whose anchor click and target click straddle a data refresh.
- React uses `useState<Set<TRow>>` (always assigns a new Set on mutation). Vue uses `shallowRef<Set<TRow>>` — `ref` would cause `UnwrapRefSimple<TRow>` type errors because Vue's deep-unwrap conflicts with generic constraints.
- Vanilla's imperative selection methods don't share names 1:1 with `TableState.selection`: `clearSelection()` ↔ `selection.clear()`, `getSelection()` ↔ `selection.all`, `setSelection(rows)` ↔ `selection.setAll(rows)` (the latter exists on Solid's `TableState` specifically to back this vanilla method — React/Vue have no `setAll` of their own). Worth checking this mapping by hand rather than assuming a name carries over, since vanilla intentionally flattens every namespaced group into its own distinct flat method names (see [Vanilla package](packages.md#vanilla-package-packagesvanilla)).
- `table.selection.rows` is `processedData.filter(r => selection.has(r))` — rows removed by filtering disappear from `selection.rows` but stay in `selection.all` and reappear if the filter is cleared.
- `table.selection.toggleAll(rows: TRow[])` takes an explicit row array — the caller decides what to pass (typically `processedData`, not just the current page). It deselects all if any are currently selected (so an indeterminate _or_ fully-checked state clears on click, matching Gmail's select-all-checkbox convention), and only selects all when none are selected.
- Vue uses a local `vIndeterminate` directive (mounted + updated hooks) to set `el.indeterminate` reactively; React uses inline callback refs (re-run on every render because they are arrow functions).
- **Shift-click range selection**: `table.selection.toggle(row, shiftKey?)` takes an optional second argument. A plain click toggles just that row and remembers it as the anchor (an internal `selectionAnchor` closure/state var — not part of the public `TableState`, since nothing outside needs to read it). A shift-click computes the contiguous run between the anchor and the clicked row via core's `selectRange(items, anchor, target)` (an inclusive slice by `indexOf`, falling back to `[target]` alone if the anchor isn't in `items` anymore — e.g. sorted/filtered away) over `processedData` (the full filtered/sorted order, not just the current page, so a range can span a page boundary the same way it would in a scrollable list). The direction (select vs deselect) mirrors what a plain click on the _target_ row would do — i.e. it's based on the target's own checked state before the click — so shift-click can both extend and shrink a selection with the same modifier. Row checkboxes read the modifier off `onClick`/`@click` (a `MouseEvent`), not `onChange`/`@change`, since `change` events on checkboxes don't carry `shiftKey`; React additionally marks the checkbox `readOnly` to suppress its controlled-input-without-`onChange` warning.
- **Vanilla's imperative selection API**: React/Vue/Solid expose selection reactively (`table.selection.all`/`.rows`/`.clear`/`.toggleAll`/`.toggle`, readable and callable anytime). Vanilla has no reactive state to read directly, so `DataTableInstance` gained matching methods — `getSelection()` (mirrors `selection.all`, not `selection.rows`: it returns every selected row including ones currently hidden by a filter, so `setSelection(getSelection())` round-trips predictably regardless of what's filtered), `setSelection(rows)`, and `clearSelection()` — so a consumer can wire an external "Clear selection" button or pre-select rows on load, the same things React/Vue/Solid could already do by calling `table.selection.clear()`/`table.selection.toggle(row)` directly outside the component. `setSelection`/`clearSelection` just delegate straight to `table.selection.setAll(rows)`/`table.selection.clear()` — post-split, there's no `render()` call for them to make: Solid's own reactivity re-renders the mounted `DataTableView` off the mutated `selection` signal, and a `createEffect(on(table.selection.rows, ...))` (deferred, so it never fires for the initial value) fires `onSelectionChange` with the current `_processedData`-filtered view, consistent with how every other selection change already notifies it.

## Row click

`onRowClick` (React/vanilla prop) / `rowClick` (Vue emit) fires when a data row is clicked, receiving the full row object and the native click event — no `rowKey` lookup needed. Group header rows, the aggregate row, and the selection checkbox cell never trigger it:

- **React** — the checkbox `<td>` already calls `e.stopPropagation()`, which is what keeps checkbox clicks from bubbling to the row's `onClick`. A `cursor: 'pointer'` inline style is applied to the row only when `onRowClick` is set. Since rows are styled with inline `style` objects (no stylesheet to hold a `:hover` rule), the hover highlight is JS-driven: `onMouseEnter`/`onMouseLeave` track a single `hoveredRow` state value, which the row's background ternary checks ahead of the stripe/selected fallback.
- **Vue** — the checkbox `<td>` uses `@click.stop` for the same reason. Since `rowClick` is a declared emit, Vue strips any `onRowClick` listener out of `$attrs` before it reaches the component, so presence can't be detected via `useAttrs()`; `getCurrentInstance()?.vnode.props?.onRowClick` reads the raw incoming listener instead, and drives the `dt__tr--clickable` class (which sets the pointer cursor and a `:hover` background rule — real CSS pseudo-classes work here because rows are styled via classes, not inline styles). `.dt__tr--selected` uses `!important` so a selected row's highlight always wins over the hover background.
- **Vanilla** — the row `<tr>` carries `data-action="row-click"` and `data-proc-idx`; the checkbox `<td>` carries `data-no-row-click`, which the `row-click` case in `handleClick` checks via `target.closest('[data-no-row-click]')` before invoking the callback (same guard pattern as `data-no-collapse` for group-row checkboxes). The `dt-tr--clickable` class is added whenever `onRowClick` is set; its `:hover` rule is declared in `styles.ts` _before_ `.dt-tr--selected .dt-td` so a selected+hovered row keeps the selected color on the equal-specificity tie. Firing the callback returns early without calling `render()` itself — it does update `focusedRow` (see [Keyboard navigation](keyboard-navigation.md)), but that's picked up by whichever render happens next rather than forcing one here.

Custom cell renders (React `render`, Vue `#cell-*` slots) that put clickable elements (buttons, links) inside a cell are responsible for calling `stopPropagation()` themselves if they don't want the click to also reach `onRowClick`.
