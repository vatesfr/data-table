# Toolbar, active bar and layout

## Toolbar layout (shape/find clusters, active state bar)

The toolbar reads as two purposeful clusters instead of one undifferentiated row of buttons: **Columns · Group · Sort** (what's shown and in what order — "shape" the view) then a vertical divider then **Search · Filter** (which rows are shown at all — "narrow" the view), with the toolbar-level "Clear all" button pinned alone at the far right (`margin-left: auto`). Group moved out of its old position (after Filter) to sit with Sort as a fellow "shape" control; Search moved out of its own separate search-specific div to sit next to Filter as a fellow "find" control. **Group sits before Sort** (not after, despite "Sort" reading first alphabetically) — grouping is the structural, primary concern (data is grouped first) and sorting within/across groups is secondary, the same ordering already used by the Sort dropdown's own "Group order" section coming before "Active sorts" and the active bar's group-chips-before-sort-chips order (see "Auto-syncing group order with sort" below). The divider (`dt-toolbar-divider`/`S.toolbarDivider`/`.dt__toolbar-divider`) is a plain 1px-wide, 22px-tall vertical bar in `--color-border-secondary` (not the fainter `--color-border-tertiary` the toolbar's own bottom border uses — that token is too close to the background to read as a divider at this size).

Below the toolbar sits a second row, the **active state bar**, always rendered — even with nothing active — rather than only appearing once a filter is set. This gives the row-count stats a single stable home instead of bouncing between "end of the toolbar row" (its old position) and nowhere, and means toggling a sort/filter/group never changes the toolbar's height or shifts anything above it. It shows one chip per active sort entry, group column, and filter column, each independently removable (`remove-sort`/`remove-group`/`clear-filter-key`, all pre-existing actions — no new core primitives needed), followed by the row-count/group-count stats pinned at the far right of _this_ row instead of the toolbar row.

This replaces the old asymmetry where filter chips got a dedicated summary row (because the Filter button only ever showed a column _count_, with no view of which values were selected) while sort/group got only a bare count badge on their own toolbar button (`sorts.length`/`groupBy.length` in a small pill) — on the theory that the dropdown's own active-entries list already showed the detail, so a second copy would be pure duplication. In practice this meant sort/group state was strictly less visible than filter state despite being the same _category_ of thing (something the user did to shape/narrow the view), and you couldn't tell _which_ columns were sorted/grouped without opening the dropdown. The count badges are gone from all three toolbar buttons now (the active bar carries that detail instead); sort/group chips reuse the plain neutral chip look the badges used, while filter chips keep their existing blue tint (`dt-chip--filter`/`S.chipFilter`/`.dt__chip--info`) — the one deliberate color accent in this bar, since filters already carried that "narrowing your view" meaning before sort/group chips existed alongside them.

- **Vanilla** — the toolbar's outer `<div class="dt-toolbar">` now wraps only `.dt-toolbar-actions`; the active bar (`.dt-active-bar`) is a sibling `<div>` rendered after it (same nesting level `.dt-chips` used to have), built in the same `render()` pass right after the toolbar markup.
- **React** — `S.toolbar` dropped its own flex properties (it now just wraps `S.toolbarActions`, no longer lays out children directly); `S.toolbarSearch` was deleted entirely (the search `<span>` moved to be a plain sibling inside `S.toolbarActions`); the active bar is `S.activeBar`, a sibling `<div>` after the toolbar's closing tag.
- **Vue** — mirrors React exactly: `.dt__toolbar` lost its flex properties, `.dt__toolbar-search` was deleted, `.dt__chips` was renamed `.dt__active-bar` (kept as a sibling of `.dt__toolbar`, unchanged position) and is no longer gated behind `v-if="activeFilterCount > 0"`.
- Test gotcha for React specifically: the global search input and the Filter dropdown's own per-column search input share the exact same default placeholder text (`L.search` and `L.filterSearchPlaceholder` are both `'Search…'`). Tests that grab the filter's own search box via `getAllByPlaceholderText('Search…')` must now take the _last_ match, not the first — Search moved from after Filter (in DOM order) to before it, so the global box is now the earlier of the two matches. Vue's equivalent tests were never affected, since they disambiguate by CSS class (`.dt__search-input` vs `.dt__dd-search`) rather than by placeholder text.

## Toolbar clear buttons (Sort/Group/Filter)

The Sort/Group/Filter dropdowns used to render their own "Clear sorts"/"Clear groups"/"Clear filters" row in a `dd-footer` at the bottom of the panel — clearing that state required opening the dropdown first. Each toolbar button now instead grows an adjoining × button (visible only when that state is non-empty, i.e. `sorts.length > 0`/`groupBy.length > 0`/`activeFilterCount > 0`) that clears without opening the dropdown at all — same idea as the search input's own `×` clear button (`dt-search-clear`/`.dt__search-clear`), which the new button matches in color/size (muted `--color-text-tertiary`, `font-size: 14px`). The Columns dropdown is unaffected — it never had a clear concept. The toolbar-level "Clear all" button (`clear-all`) is also unaffected; it coexists with these per-dropdown ones.

A `<button>` can't contain another interactive element, so the × can't nest inside the toggle button itself — it's a sibling, and the two are visually merged into one pill via a shared border (toggle button gets its right corners squared off and its right border dropped; the × button gets the matching left treatment and rounds off the outer right corners).

- **Vanilla** — the trigger markup passed to `buildDd` becomes `<span class="dt-btn-group">` wrapping both `<button class="dt-btn dt-btn--grouped">` (only when active — plain `.dt-btn` otherwise) and the sibling `<button class="dt-btn-clear" data-action="clear-sorts">×</button>`. Since both buttons already live inside the same `.dt-dd-wrap` as before, no changes were needed to the existing "close dropdown on outside click" logic (which checks `.closest('.dt-dd-wrap')`) or to drag-and-drop resolution (which already treats the whole `.dt-dd-wrap` as one region).
- **React/Vue** — the × can't just be placed in the `trigger` prop/slot, because `Dropdown`'s trigger area itself carries the open/close click handler (an ancestor `<div onClick>` in React, `<div @click>` in Vue) — nesting the × there would make clicking it also toggle the dropdown. Both `Dropdown` components instead gained a second slot for this: React's `extraTrigger?: ReactNode` prop and Vue's `#extra-trigger` slot are rendered as a sibling of the trigger's own click-handling wrapper, but still inside the same outer container that the "click outside closes the dropdown" listener checks (`ref.current.contains(...)` in React, `containerRef.value.contains(...)` in Vue) — so clicking × neither toggles the dropdown open/closed via the trigger's own handler, nor spuriously closes an already-open dropdown via the outside-click listener treating it as "outside". That container's `display` changed from `inline-block` to `inline-flex` so the trigger and the extra × sit side by side. `ToolbarBtn` gained a `grouped`/`:grouped` prop (mirroring vanilla's `dt-btn--grouped`) for the same squared-off-right-edge treatment, applied only when that dropdown's state is non-empty.
- The × buttons reuse the existing `L.clearSorts`/`L.clearGroups`/`L.clearFilters` labels for their `title`/`aria-label` rather than as visible button text (the visible glyph is a literal `×`, matching `clearSearch`'s convention). Those three labels no longer carry a `'× Clear sorts'`-style leading `×` in `locales.ts` (across all five locales) — it made sense back when the string _was_ visible footer text, but reads redundantly once it's tooltip/aria-label-only text sitting next to a button that already shows its own `×` glyph, the same reasoning `clearSearch` (never prefixed) was already built around. `clearAll` is the one label that correctly keeps its `× ` prefix, since its button still renders the label as real visible text.

## Hiding toolbar controls that have nothing to act on (GitHub issue #25)

The Group and Filter toolbar buttons already hide themselves entirely when no column qualifies (`groupableCols.length > 0`/`filterableCols.length > 0` guards) rather than rendering a dropdown with nothing addable inside it. The Sort button follows the same convention (`sortableCols.length > 0`, i.e. `columns.some(c => c.sortable !== false)`) — it used to be the one outlier, always rendered even when every column had `sortable: false`. Solid's own `filterableCols.length > 0` guard on `FilterDropdown` was missing until a follow-up fix (vanilla inherited the gap through it) — React/Vue already had it; Solid/vanilla now match.

Search can't auto-hide this way — every column is searchable by default, so there's no column-derived signal for "the consumer doesn't want this." **`showSearch?: boolean`** (default `true`, on `DataTableViewProps`/`DataTableProps` — all four adapters) is the explicit opt-out for it, e.g. when a page already has its own search input elsewhere and the toolbar's own box would just duplicate it.

The Columns dropdown has no per-column "nothing to act on" signal either — showing/hiding a column is a table-level preference, not something any single column's flags express — so it gets the same explicit-opt-out treatment as Search rather than an auto-hide rule bolted onto column definitions: **`showColumns?: boolean`** (default `true`, all four adapters). Unlike Search, it _also_ auto-hides once `columns.length < 2` — toggling/reordering the visibility of a single column has nothing meaningful to act on, so this one case doesn't need the opt-out to be useless. Each adapter combines both checks at the same render site the Sort/Group/Filter guards live (`showColumns !== false && columns.length >= 2`, or Vue's already-coerced-to-boolean `showColumns && columns.length >= 2`).

Together, showSearch + showColumns + the Sort/Filter fixes above fully close the original ask: a minimal table (every column `sortable`/`filterable`/`groupable: false`, one column, `showSearch: false`) now renders a genuinely empty toolbar with no CSS workaround needed — no blanket `toolbar={false}` or a `showSort`/`showGroup`/`showFilter` trio was added, since that would have duplicated logic that already exists (or needed to exist) for those three.

- **Vue-specific gotcha**: Vue casts an absent boolean prop with no explicit `withDefaults` default to `false`, not `undefined` — both `DataTable.vue` and `DataTableView.vue` need `showSearch: true` spelled out in their own `withDefaults` call (same reasoning as `defaultGroupsCollapsed`'s existing comment), or an omitted `showSearch` silently hides the search box instead of showing it.
- **React/Solid**: `DataTable.tsx` must explicitly forward `showSearch` through to `<DataTableView>` — it isn't covered by a prop spread, so a new `DataTableViewProps` field needs a matching line added at each `<DataTable>` wrapper's own call site (a gap this feature's own tests caught: forgetting this bullet left `showSearch` silently inert through `<DataTable>` while still working through `<DataTableView>` directly).
- **Vanilla**: `showSearch` is backed by its own `createSignal` (`options.showSearch ?? true`) mirroring `selectable`, with a matching `setShowSearch(value: boolean)` on `DataTableInstance`.

## Active-bar chip click actions

Previously a chip's body (the label/icon text) was inert — only its `×` did anything. Each chip's body is now a real, focusable `<button>` (a sibling of the `×` button rather than nested inside it — a `<button>` can't contain another interactive element, the same reasoning already used for the toolbar's grouped clear buttons) that does something specific to that chip's own kind of active state, so tweaking an already-active sort/group/filter no longer requires reopening its dropdown and re-navigating to the same entry:

- **Sort chip** → toggles that column's direction in place (the same action the dropdown's own active-sort row already does) — no dropdown needed for the single most common tweak.
- **Group chip** → opens the Group dropdown and focuses that entry's row. There's no single obvious inline toggle for a group entry the way direction is for sort, so getting straight to it (ready to reorder/remove) is the most useful available action.
- **Filter chip** (both the checklist-values chip and the range chip) → opens the Filter dropdown, sets the active filter column to that key _before_ the panel first renders (so the right pane already shows the right thing on the very first paint, rather than waiting for focus to land and the "focus follows selection" mechanism below to catch up), and focuses that column's button in the left pane.
- Styling: a chip is no longer one bordered/padded pill-shaped element — the border/background/padding moved onto the body and `×` individually, each keeping only its own outer corner rounded and sharing a border between them (mirroring the toolbar's grouped-clear-button seam trick), so the pair still reads as one pill. This also makes chips keyboard-reachable for the first time (real `<button>`s are native Tab stops) — previously the whole chip was a plain, inert element apart from its `×`.

**Vanilla** (this bullet describes the pre-Solid-extraction hand-rolled implementation; see below for what `packages/solid`/vanilla's current inherited behavior actually is) — reused the pre-existing `toggle-sort-dir` action as-is for the sort chip; two small, structurally identical click-handler cases, `open-group-entry`/`open-filter-col`, did the rest — no new core logic needed, since each one only set pre-existing state (`openDropdown`, `filterActiveCol`, `filterListScrollTop`) the same way the equivalent dropdown-open/column-select interactions already did. The sort chip's button carried a stable `data-focus-key="chip-sort-${key}"` so the existing generic focus-key restore at the top of `render()` (see [Keyboard navigation](keyboard-navigation.md)) kept it focused across the re-render for free; Group/Filter's buttons got an explicit post-render focus lookup instead (by `grouprow-${key}`'s focus key, or by `.dt-filter-col-item`'s own `data-key`), since a _newly opened_ dropdown's row isn't the thing that had focus before this render, so the generic restore didn't apply there. `.dt-chip` dropped its own padding/background/border in favor of `.dt-chip-body`/`.dt-chip-x` (`12px 0 0 12px` / `0 12px 12px 0` corner rounding).

**Solid/vanilla today**: the sort chip's direction toggle works the same as always (no focus concern — same button/key across the update). The group chip's ⊞ mark jumps to that entry's row on open (`ActiveBar.tsx`'s `onOpenGroup(key)`, wired in `DataTableView.tsx` to call `.focus()` synchronously right after opening the dropdown — see [Dropdown column search and keyboard navigation](dropdown-keyboard-nav.md)'s Solid bullet). The filter chip's jump-to-column behavior is implemented too, at parity with React/Vue: `onOpenFilter(key)` forwards the key through to `FilterDropdown`'s `openKey` prop, which sets the active column and focuses its left-pane button.

- **React** — the sort chip's button keeps the same key/identity across the toggle, so it stays focused for free with no explicit refocus needed. Group/Filter route through the same pending-ref + `useLayoutEffect` pattern already used for the Sort/Group activate/remove focus-retention fix below (`pendingGroupFocusKey`/`pendingFilterColFocusKey`), since clicking either opens a dropdown panel that doesn't exist in the DOM yet at click time. `S.chip` lost its own padding/background/border in favor of new `S.chipBody`/`S.chipX` style objects.
- **Vue** — same reasoning as React: the sort chip needs no refocus code (Vue's reconciliation keeps its `<button>` in place across the reactive update); Group/Filter open their dropdown via a new `open()` method `Dropdown.vue` exposes via `defineExpose` (alongside the existing `close()`), then focus the target row/column button via the same ref maps used by the Sort/Group activate/remove fix, after an `await nextTick()`. `.dt__chip`'s own padding/background/border moved onto new `.dt__chip-body`/`.dt__chip-remove` classes.

## Dropdown viewport clamping and toolbar wrapping

Every dropdown panel (Columns/Sort/Group/Filter) is absolutely positioned off its trigger and would otherwise render partly or fully off-screen — most visibly the ~460px-wide filter panel opened near the right edge of a narrow viewport. Each adapter measures the freshly-opened panel's `getBoundingClientRect()` and, if it overflows the viewport, applies a `transform: translateX(...)` horizontal offset (rather than flipping the anchor side, `left:0` → `right:0` — the overflow is relative to the _viewport_, not the trigger, so flipping the anchor on a trigger near the toolbar's left edge would just push a wide panel off the opposite side instead) and flips the panel above the trigger when it would overflow the bottom edge (`top`/`margin-top` swapped for `bottom`/`margin-bottom` in React/Vue; a `dt-dd--up` CSS class in vanilla). React (`Dropdown.tsx`) and Vue (`Dropdown.vue`) do this in a `useLayoutEffect`/`watch(..., { flush: 'post' })` right after the panel mounts (each open is a fresh, unclamped DOM node, since the panel unmounts entirely when closed); vanilla does it inline in `render()` after `container.innerHTML` is set, via a plain `container.querySelector('.dt-dd')` lookup. All three mutate the node's `style`/`classList` directly rather than through reactive state, to avoid a synchronous re-render-triggering-render loop.

Separately, the toolbar search input is `flex: 1` capped at a `max-width` of 280px instead of a fixed ~160px box, so it grows to use available toolbar space on wide viewports while still shrinking gracefully on narrow ones — a CSS-only responsiveness fix, not a behavioral change. (An earlier iteration also wrapped the toolbar's buttons and the search/clear-all pair into two separate flex sub-containers so they'd wrap as units on narrow viewports; [Toolbar layout](#toolbar-layout-shapefind-clusters-active-state-bar)'s shape/find redesign flattened both back into the single `dt-toolbar-actions`/`S.toolbarActions`/`.dt__toolbar-actions` container, so each control now wraps individually again.)

## Visual hierarchy (header / group rows / stripes)

Header, group header rows, aggregate rows, and the odd-row stripe used to all share one `--color-background-secondary` token with no other distinguishing treatment, making them hard to tell apart at a glance. Each now reads as its own tier:

- The table header alone uses a new token, `--color-background-tertiary` (defined in `theme.ts`'s `LIGHT_THEME`/`DARK_THEME` alongside the existing tokens, and picked up automatically by `renderThemeCss()`), plus a heavier `1px` (was `0.5px`) bottom border — the strongest visual anchor, sitting above everything else.
- Group header rows keep `--color-background-secondary` (unchanged) but gain a `3px solid` left accent border and switch their text from `--color-text-secondary` to `--color-text-primary` at `font-weight: 600` (was `500`/secondary) — previously group rows used the same muted styling as the header, which made them read as faded captions instead of bold section dividers. The left border is set on the `<tr>` itself (not a `<td>`) and relies on `border-collapse: collapse` (already set on all three adapters' `<table>`) to render at the table's left edge regardless of which cells happen to be present (checkbox column optional, etc).
- The odd-row stripe now uses `color-mix(in srgb, var(--color-background-secondary) 45%, transparent)` instead of the token at full strength, so plain alternating rows read as a subtle texture rather than competing with group rows for the same gray. Hover (`onRowClick` set) and selection stay at full strength, so they still read as a stronger, more "active" cue than the passive stripe.
- Aggregate rows are intentionally left unchanged (still muted `--color-text-secondary`, `font-weight: 500`) — once the group row above it went bold/primary, the contrast between "section title" and "summary line" falls out for free with no separate change needed.
