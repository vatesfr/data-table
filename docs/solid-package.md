# Solid package (`packages/solid`)

**A real, standalone Solid adapter** — `solid-js` is a `peerDependency` here (never bundled), so a project already using Solid shares its own `solid-js` instance instead of a second, non-interoperable copy: Solid's dependency tracking is module-scoped, so a signal created by one bundled copy is invisible to a computation running under a different copy (see `vite.config.ts`'s `rollupOptions.external`, which excludes `solid-js` the same way `packages/react` excludes `react`). This package was split out of `packages/vanilla` (see that section below) — before the split, this exact code (`createTableState`, `DataTableView`, every file under `components/`) lived directly inside `packages/vanilla` with `solid-js` bundled as an internal implementation detail; the code itself, and the reasoning below for how it's built, is unchanged by the split.

Rationale for building this adapter with Solid + TSX in the first place (rather than a hand-rolled `innerHTML`-string-rebuilding implementation with manual event delegation, which is how `packages/vanilla` originally implemented its own UI before this package existed): Solid's setup-once + fine-grained-signal execution model matches a closure-based architecture more closely than React/Preact's re-render-the-world model would, and it structurally eliminates whole categories of hand-maintained code a full-string-rebuild-per-update model needs to work around — manual focus/selection/scroll restore, a `col.render()` placeholder-and-patch mechanism (`pendingRenders`/`data-render-slot`, no longer needed at all — Solid renders an arbitrary DOM `Node` as a JSX child directly), and the range-slider's `input`-vs-`change` event split (needed only to avoid a full-rebuild aborting a native drag mid-gesture).

- **`types.ts`** — `ColumnDef<TRow>` extends `ColumnDefBase<TRow>` with `render?: (value, row) => Node` and `renderFilterLabel?: (value: string) => Node`
- **`styles.ts`** — the CSS string, plus `injectStyles()`, which injects it once into `<head>` via a `<style data-dt-styles>` tag; imports `renderThemeCss` from `@vates/data-table-core/theme` (not the main package entry — see "Core package"). Called from `DataTableView` itself (not left to each caller), so a table renders styled whether it's mounted directly here or through `@vates/data-table-vanilla`'s `createDataTable` wrapper, with no separate CSS import to remember either way.
- **`createTableState.ts`** — internal state/action logic is a field-for-field Solid port of react/vue's own `useTableState` (`createSignal` instead of `useState`/`ref`, `createMemo` instead of `useMemo`/`computed` — no dependency arrays, Solid tracks reads automatically), but the _returned object_ is namespaced (`table.sort.*`, `table.filter.*`, `table.group.*`, `table.selection.*`, `table.pagination.*`, `table.search.*`, `table.columns.*`, plus a handful of top-level entries) rather than the ~45-field flat shape react/vue still return — see CLAUDE.md's "Namespaced TableState" for the full design and why, and note that Solid is the first adapter migrated to it. One structural difference from React/Vue: `data`/`columns` are themselves signals with public `setData`/`columns.set` setters — a consumer (this package's own user, or `@vates/data-table-vanilla`'s `createDataTable` factory, called once) has no render loop re-invoking `createTableState` with fresh arguments the way React re-invokes `useTableState` on every render, so keeping `data`/`columns` in sync with a reactive prop needs some other mechanism. Also exports `TableState<TRow>` and `CreateTableStateOptions`. Ephemeral, UI-only state that React/Vue keep out of `useTableState` (`openDropdown`, `filterActiveCol`/`filterActiveKey`, search terms, drag state, focus target, etc.) is deliberately not here either — it lives in the view components below, matching the same split.
  - **`initialData`/`initialColumns` each accept a plain value _or_ an `Accessor`** (mirroring Vue's own `MaybeRefOrGetter` support for the same inputs) via a small internal `access()` helper (`typeof value === 'function'` discriminates the two, since neither `TRow[]` nor `ColumnDef<TRow>[]` can themselves be a function). A plain array is a one-time initial value only — exactly the pre-existing behavior, fully decoupled after construction, changed only via `setData`/`columns.set`. An accessor instead seeds the same way but also gets a `createRenderEffect(() => setData(accessor()))` (data) / `setColumns(accessor())` (columns — the internal wrapper function is still named `setColumns`, only its exposed key changed to `columns.set`) wired up internally, tracking it for the table's whole lifetime, removing the need for a direct `createTableState`+`DataTableView` consumer to write that effect by hand. `createRenderEffect` specifically, not `createEffect`: both are scheduled identically for a plain re-run (this Solid version defers both equally when triggered while already nested inside another update transaction — a real, if narrow, consideration for the test suite, see `createTableState.test.ts`'s "accessor inputs" describe block), but only `createRenderEffect` is guaranteed to run ahead of "user" effects and is never itself deferred by an ambient `<Suspense>` boundary, which matters here since keeping the table's own state in sync is a rendering concern, not user-effect timing. Calling `setData`/`columns.set` manually on an accessor-backed table still works, but is only a temporary override — the next time the accessor's own source changes, the internal effect re-applies it, the same "controlled input" trade-off Vue's `computed` already has.
  - **`columns.set` reconciles `columns.visible` against the new key set instead of being the raw signal setter** — see "Reconciling `visibleCols` against a replaced column set" below (React and Vue need the identical reconciliation too, just reached via a different trigger).
- **`DataTableView.tsx`** — composes the toolbar (`ColumnsDropdown`/`SortDropdown`/`GroupDropdown`/divider/`SearchBox`/`FilterDropdown`/"Clear all"), `ActiveBar`, `TableBody`, and `Pagination`; takes a `table: TableState<TRow>` prop instead of calling `createTableState` itself, mirroring React/Vue's own `DataTableView` split (see "DataTableView — reaching state that `<DataTable>` can't expose") — here that split also means a consumer using this package directly builds a `table` and can hand it to `usePersistedView`/`usePersistence` (see `persistence.ts` below), exactly as `createDataTable` already does internally. Unlike React/Vue's `DataTableViewProps` (whose `TableState` doesn't carry raw `data`/`columns` at all), this one takes only `table` — no separate `data`/`columns` props — since `createTableState`'s own `table.data()`/`table.columns()` accessors already are that value; passing them again as plain-array props alongside `table` would be pure redundancy with nothing enforcing the two stayed in sync, which is exactly what an earlier version of this file did before that redundancy was removed.
- **`components/`** — `Dropdown.tsx` (shared open/close/outside-click/Escape/viewport-clamping shell used by all four toolbar dropdowns), `SearchBox.tsx`, `ColumnsDropdown.tsx`, `SortDropdown.tsx`, `GroupDropdown.tsx`, `FilterDropdown.tsx` (the master-detail panel — checklist/range+slider/date-tree), `RangeSlider.tsx`, `formatRangeBound.ts` (converts a numeric/date bound back into the string shape `RangeFilter.min`/`.max` expects, shared by `RangeSlider.tsx`'s thumb-commit and `FilterDropdown.tsx`'s plain min/max inputs so the two stay in sync), `DateTreeItem.tsx` (self-importing recursive tree node, same pattern as Vue's own), `ActiveBar.tsx`, `TableBody.tsx` (header + group/data rows + aggregation + keyboard nav), `Pagination.tsx`, `dragReorder.ts` (shared cursor-position-based drop-row resolution for Sort/Group/Columns drag-and-drop and `TableBody`'s header drag, reusing the same helper via a horizontal variant), `checkboxSync.ts` (see below).
- **`DataTable.tsx`** — thin convenience wrapper mirroring React's/Vue's own `<DataTable>`: builds a `createTableState` internally (passing `data`/`columns` through as accessors — `() => props.data` — so no manual `createEffect` is needed here the way every other adapter's equivalent wrapper needs one) and renders `<DataTableView>`. `DataTableProps<TRow>` is `Omit<DataTableViewProps<TRow>, 'table'>` plus its own `data`/`columns` (needed here even though `DataTableViewProps` doesn't have them — `<DataTable>` still has to feed them into `createTableState` itself) plus the same four construction-only fields (`defaultVisibleColumns`, `labels`, `defaultPageSize`, `defaultGroupsCollapsed`) React/Vue's own `DataTableProps` add, plus `onSelectionChange?: (rows: TRow[]) => void` — the one prop `DataTableViewProps` doesn't otherwise have, needed here specifically because `<DataTable>` never hands `table` back to its caller the way the split does, so there's no other way to observe a selection change (same reason `@vates/data-table-vanilla`'s `createDataTable` has its own `onSelectionChange` option). Wired via `createEffect(on(table.selection.rows, ..., { defer: true }))`, the same pattern vanilla's `index.tsx` already uses.
- **`persistence.ts`** — `usePersistedView`/`useUrlView`/`resetView`/`usePersistence`, a straight promotion of the hand-rolled `createEffect`-based implementation that used to live only in `demo/solid/src/persistence.ts` (that file is gone now that the real thing exists here) — same behavior and naming as React/Vue's own hooks (see "View persistence" below), including the empty-view-removes-the-`localStorage`-key fix and the combined `usePersistence` helper that came later.
- **`index.ts`** — re-exports `createTableState`/`TableState`/`CreateTableStateOptions`, `DataTableView`/`DataTableViewProps`, `DataTable`/`DataTableProps`, `ColumnDef`, `usePersistedView`/`useUrlView`/`resetView`/`usePersistence` and their option types, and (mirroring every other adapter) core's locales, `DataTableLabels`/`TableViewState`/`GetRowId`/`DatePart`/`LogRangeOptions`, and the `bucketNumericRange`/`formatNumericRange`/`numericRangeGroup`/`bucketDatePart`/`formatDatePart`/`datePartGroup`/`bucketLogRange`/`formatLogRange`/`logRangeGroup`/`compareMissingLast` helpers. `injectStyles` is deliberately **not** re-exported here — `DataTableView` already calls it automatically on mount, so a normal consumer never needs it, and there's no documented reason (e.g. SSR pre-injection) to justify the extra public surface. It's still exported from `./styles` itself for `DataTableView`'s own internal import.

**Known simplifications vs. the fuller documented behavior below** (deliberately deferred, not silently dropped — each is noted in its own component's doc comment too): the flat filter checklist is not virtualized/windowed (`computeVirtualRange` exists in core for this, layerable later — a pure rendering-cost optimization, not a behavior change); the generic roving Up/Down/Home/End keyboard nav _inside an open dropdown_ (beyond native Tab order), dropdown focus-on-open, and Sort/Group's activate/remove focus-retention are not implemented; the Filter dropdown's Left/Right pane-crossing keyboard nav is not implemented; `TableBody`'s Home/End jump to the first/last item of the _current page only_ — crossing a page boundary (arrow keys, or Ctrl+Home/Ctrl+End across all pages) is deferred. None of this affects mouse/touch interaction or the underlying state/behavior — every one of these is purely about keyboard-only navigation shortcuts layered on top of already-working mouse interactions, native Tab order, and (where relevant) already-working same-page keyboard nav.

Because this package's UI was originally built as part of `packages/vanilla`'s own Solid migration, most of the "vanilla"-labeled implementation asides in the sections below (`data-action` dispatch, `data-focus-key` restore, the `pendingRenders` placeholder mechanism, the `input`/`change` slider split, and — after this split — every mention of `createTableState.ts`/`DataTableView.tsx`/`components/*` by name) actually describe code that now lives in **`packages/solid`**, not `packages/vanilla` itself; `packages/vanilla` today is only the thin wrapper described in its own section below. Some of those asides also describe the **pre-Solid-migration** implementation and no longer apply to either package — Solid's diffing (reusing the same DOM node across updates by construction) makes most of that category of special-casing unnecessary. They're left in place because the _behavior_ they describe is still current for React/Vue, and in most cases still current for the Solid/vanilla pairing too, just achieved differently (a real DOM node instead of a placeholder-and-patch string trick; the browser's own focus/scroll persistence instead of manual save/restore). Read "vanilla does X via `data-action`/`data-focus-key`/etc." as "`packages/solid`'s components achieve the same X, now via Solid reactivity, and `packages/vanilla` gets it for free by wrapping them" unless a specific behavior is called out above as changed or deferred.

Cell customization: `col.format(value, row) → string` for plain text, or `col.render(value, row) → Node` for arbitrary DOM (images, links, badges — see GitHub issue #3) — `render` takes priority over `format` when both are set, mirroring React's `render`/`format` priority. Implemented by a shared `cellValue(col, row)` helper (`TableBody.tsx`) used for data cells, group header cells (`renderGroupCellValue`), and aggregate cells (`aggValue`) alike — the same column-reuse pattern as React's `cellValue()` — since `col.render`'s return value is a real DOM `Node`, Solid renders it as a JSX child directly with no placeholder/patch step.

**`checkboxSync.ts`** exists for one specific, non-obvious Solid + native-checkbox interaction: a tri-state checkbox (the filter checklist's include/exclude cycling, the date tree's checked/unchecked/indeterminate rollup) must call `e.preventDefault()` in its `click` handler to stay fully controlled — a plain native toggle can't express a 3-state cycle. Solid's own reactive `checked`/`indeterminate` bindings write to the DOM synchronously as part of that same handler call, but a checkbox's native "canceled activation steps" (triggered specifically because `preventDefault()` was called) run _after_ the whole click finishes dispatching — i.e. after Solid's write — silently reverting `.checked` back to its pre-click value a moment later, on exactly the element that was clicked. `applyCheckboxState` is the plain synchronous setter (correct for every update _except_ this one race — used from each component's general reactive effect); `deferCheckboxCorrection`, called from the click handler itself right after the state-changing action, re-applies the settled-correct state from a microtask, guaranteed to run after the native revert. Deferring unconditionally in the general effect instead would "fix" the race at the cost of a one-tick-late DOM read for every other update path too (a different checkbox changing, `setViewState`, initial render) — so the fix is scoped to exactly the element that was clicked.
