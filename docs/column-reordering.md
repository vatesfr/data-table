# Column reordering

`columnOrder: string[]` is a separate piece of state from `visibleCols` — it lists _all_ column keys (visible and hidden) in display order, not just the visible ones, so hiding a column and showing it again doesn't lose its position. It starts as `[]` (natural order, i.e. `columns` as passed in) and is only materialized on the first reorder.

`getOrderedColumns(columns, order)` in core sorts the full column list per `order`, appending any column missing from it (added later, or `order` still `[]`) at the end in its original relative position — the same "stale/partial state still renders something sane" pattern used for `visibleCols` in `setViewState`. `activeColumns` in each adapter is `getOrderedColumns(columns, columnOrder).filter(visible && !grouped)`; a second derived value, `orderedColumns`, is the unfiltered version — all columns in display order, visible or not — used to render the Columns panel with its own drag/order controls.

Two interactions both write to `columnOrder`, backed by two core primitives:

- **Drag-and-drop on headers** — native HTML5 Drag and Drop API (`draggable`, `dragstart`/`dragover`/`drop`), not a pointer-events implementation, to keep the per-adapter diff small and avoid a dependency. `reorderColumn(order, dragKey, targetKey)` moves `dragKey` to just before `targetKey`; dropping doesn't distinguish drop-before vs drop-after halves of the target header, it always inserts before — a deliberate simplification.
- **Drag-and-drop, or Alt+ArrowUp/Alt+ArrowDown, on rows in the Columns panel** — replaces the old ▲▼ buttons entirely. Dragging a row uses the same mechanism as the Sort/Group dropdowns' own active-entry lists (see "Drag-and-drop reordering inside the Sort/Group/Columns dropdown lists" below); `moveColumnBy(order, key, delta)` swaps `key` with its neighbor `delta` positions away (`-1`/`+1`) and is a no-op past either boundary, now fired via `Alt+ArrowUp`/`Alt+ArrowDown` on the row's own visibility checkbox rather than a dedicated button.

Both actions materialize `columnOrder` from `columns.map(c => c.key)` before calling the core primitive if it's still `[]`, so the first reorder always operates on a complete key list rather than an empty one.

Per-adapter drag wiring:

- **React/Vue** — `dragColKey`/`dragOverColKey` local state (React `useState`, Vue `ref`) drives inline opacity/box-shadow feedback on the dragged and hovered-over headers; both are cleared on `dragend` as well as `drop`, since a drag cancelled outside a valid target (e.g. dropped off the table) still fires `dragend` but not `drop`.
- **Solid** (`packages/solid/src/components/TableBody.tsx`) — `dragColKey`/`dragOverColKey` signals drive a `dt-dd-item--drag-over` class on the hovered-over header `<th>`, cleared on both `dragend` and `drop` for the same reason as React/Vue. Unlike vanilla's old hand-rolled version (see below), Solid's controlled JSX reconciles the same `<th>` DOM node in place rather than rebuilding it via `innerHTML`, so there's no risk of a mid-drag render aborting the native drag operation — `handleHeaderDragOver`/`handleHeaderDrop` can mutate signal state directly on every event, with no need to defer state writes to `drop` alone the way vanilla's old `innerHTML`-rebuilding implementation had to. Header dragging resolves its target column by `clientX` against each header cell's `getBoundingClientRect()` via a small horizontal-only helper, `resolveDropRowHorizontal(clientX, cells)` (local to `TableBody.tsx`, not in `dragReorder.ts` — see below), always inserting before the hit column (the same deliberate "insert-before-only" simplification described above); `table.columns.move(from, hit, false)` applies it.
- **Vanilla** — has no drag wiring of its own anymore; it inherits header drag-and-drop entirely through `@vates/data-table-solid`'s `TableBody`/`DataTableView` (see CLAUDE.md's "Vanilla package"). The `dragColKey`/`dragOverColKey` state and the `render()`/`innerHTML`-avoidance dance described in earlier revisions of this doc no longer exist in `packages/vanilla/src/` — that hand-rolled implementation was superseded by the Solid extraction.

`TableViewState.columnOrder?: string[]` persists/shares the order the same way as every other field in `view.ts` — omitted when empty (natural order), wire key `o`.

**Drag-and-drop reordering inside the Sort/Group/Columns dropdown lists** (the active-entries list in each, plus the Columns panel's row list) is a separate interaction from header dragging above, but shares the same core primitives — `reorderColumn`/`reorderSort` (core) both take a 4th `after = false` param: `false` splices the dragged entry just before the target (the header-drag behavior, unchanged), `true` splices it just after. Unlike header dragging (which deliberately stays insert-before-only, see above), these three lists resolve `after` from where the cursor is within the hovered row's own bounds (top half vs bottom half via `getBoundingClientRect()`/`clientY`) — without that, a row could only ever be a valid "insert before" target, so the _last_ row in a list could never actually become non-last (dropping onto it could only ever push it to second-to-last). When the cursor isn't over any row at all (dead space below the last row, e.g. the "add" section) it snaps to the nearest edge row instead of rejecting the drop — a plain `closest()`-on-target-row-only design would `return` before calling `preventDefault()` there, and the browser treats a `dragover` that never calls `preventDefault()` as an invalid drop target, silently swallowing the subsequent `drop`.

- **Solid** — `resolveDropRow(clientY, rows)` (`packages/solid/src/components/dragReorder.ts`, shared by `ColumnsDropdown.tsx`/`SortDropdown.tsx`/`GroupDropdown.tsx`) takes the drag event's `clientY` and the list's candidate rows (each `{ key: string; el: HTMLElement }`, gathered via a `querySelectorAll`-style lookup at drag time rather than a persistent ref map) and returns `{ key, after } | null` — `after` resolved from whether `clientY` falls in the top or bottom half of the hit row's own `getBoundingClientRect()`, or the first/last row snapped to an edge when the cursor isn't over any row at all (dead space below the list). Each dropdown component keeps `dragKey`/`dragOverKey`/`dragOverAfter` signals; `dt-dd-item--drag-over-after` (bottom inset line, mirroring the existing top-inset `dt-dd-item--drag-over`) renders the after-case's insertion point. Vanilla inherits all of this via the Solid wrapper — no drag-and-drop code of its own remains in `packages/vanilla/src/`. (The header-drag mechanism described just above uses its own separate horizontal helper, `resolveDropRowHorizontal`, local to `TableBody.tsx` rather than `dragReorder.ts` — it isn't a variant of `resolveDropRow` itself, since a header row has no "rows" to snap against, only column cells laid out left-to-right.)
- **React/Vue** — the per-row `dragover`/`drop` handlers were removed; instead `<Dropdown>` itself accepts `onDragOver`/`onDrop` (React: new optional props forwarded onto the panel `<div>`; Vue: `Dropdown.vue` sets `inheritAttrs: false` and binds `v-bind="$attrs"` on the menu panel div instead of its own root, so a consumer's `@dragover`/`@drop` land on the panel rather than falling through to the outer wrapper) — bound once per dropdown rather than once per row, so hovering _past_ the last row (still inside the panel) reaches a handler at all. `resolveDropdownDragRow(root, e, attr)` (React: module-level function; Vue: a plain function in `<script setup>`) is the same row-query-and-snap logic as Solid's `resolveDropRow`, scoped via the panel element (`e.currentTarget`) instead of a closure-held container. A second boolean ref/state (`dragOverSortAfter`/`dragOverGroupAfter`/`dragOverColRowAfter`) alongside the existing `dragOverXKey` picks which inset (`inset 0 2px 0` vs `inset 0 -2px 0`) the hovered row renders.
- `table.columns.move`/`table.sort.move`/`table.group.move` (post-namespacing — see CLAUDE.md's "Namespaced TableState"; these were flat `moveColumn`/`moveSort`/`moveGroup` members on React/Vue's `useTableState` return value before that reshape) each take an optional 3rd `after` param (default `false`), threaded straight through to the corresponding core `reorderColumn`/`reorderSort` call. React's `DataTableView.tsx` and Vue's `DataTableView.vue` each alias the namespaced field back to the same bare local name (`moveColumn`, etc.) their code used before the reshape, in the one destructuring block CLAUDE.md's "Namespaced TableState" section describes, so nothing past that block needed to change; Solid's own `TableState` was namespaced from the start (it was built after the reshape), so `packages/solid/src/components/*.tsx` call `table.columns.move`/`table.sort.move`/`table.group.move` directly with no aliasing step, and vanilla — itself just a wrapper around Solid — never had flat names to alias either.

### Touch/mobile

Every drag-and-drop reorder path described above — header dragging and the Sort/Group/Columns dropdown lists, across all four adapters — is native HTML5 Drag and Drop (`draggable`, `dragstart`/`dragover`/`drop`), chosen specifically to avoid a pointer-events reimplementation and its own dependency (see "Drag-and-drop on headers" above). This API has no real touch-device support: most mobile browsers never fire these events from a touch gesture without an explicit polyfill, which this library doesn't include. **There is currently no way to reorder columns, sorts, or groups on a touch-only device** — not a deliberate scope cut stated anywhere before now, just an unstated consequence of the native-DnD choice.

The Columns/Sort/Group dropdowns' own Alt+ArrowUp/Alt+ArrowDown keyboard reorder (see above) is not a real touch fallback either — it needs a physical keyboard, which a touch-primary device typically doesn't have alongside it. Contrast this with `RangeSlider.tsx` (the Filter dropdown's numeric range control — see `docs/filter-dropdown.md`), which deliberately uses a dual-thumb `<input type="range">` specifically because that gets touch support for free; drag-and-drop reordering never had an equivalent touch-conscious design pass.

Closing this gap for real would mean a pointer-events-based reorder implementation (or a touch-and-mouse-unifying library) alongside — or instead of — the native HTML5 DnD used today; that's a real, currently-unscoped project, not a quick fix.
