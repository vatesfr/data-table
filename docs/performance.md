# Performance

Given pagination, the DOM only ever renders `pageSize` rows regardless of dataset size — so for huge datasets (100k–1M+ rows), the cost lives entirely in `packages/core`'s pure functions, which run over the _full_ dataset on every relevant state change (sort, filter, search, group), not just the visible page.

- **Benchmarks**: `packages/core/src/__tests__/logic.bench.ts` (`npm run bench -w packages/core`, or `npx vitest bench --reporter=verbose` from `packages/core` — the default reporter prints no results table) uses Vitest's `bench` test fixture against synthetic datasets at 10k/100k/500k rows (`bench-utils.ts`: 7 columns — string, number, date, and a 20-value low-cardinality category — generated with a seeded PRNG for stable runs). It covers `filterData`/`sortData` (plain/filtered/sorted, per column type), `buildSearchIndex`/`searchData`, `groupData`/`getVisibleRows`/`paginateVisibleGroups`, `computeStringValues`/`computeStringValueCounts`, and `computeDateTree`. There's no CI regression gate on these yet — they're a manual profiling tool, run before/after a perf-sensitive change to check the actual impact rather than guessing.
- **Load-independent and browser measurements**: `scripts/perf-core.mjs` (instructions and bytes per core call) and `scripts/perf-browser.mjs` (interaction timings and leak loop on the demos' production builds), driven by the `perf-review` skill.
- **`computeStringValueCounts` was the single biggest cost found**: ~15–17x faster at 500k rows/7 columns when computed for the open column only instead of every filterable column (it now takes a single column) — see [Filter dropdown](filter-dropdown.md) for the fix (removed `stringValueCounts` from React/Vue's `useTableState` entirely; Solid scopes it to `activeCol()` inside `FilterDropdown.tsx`'s `stringValueCounts` memo, and vanilla inherits that).
- **`computeStringValues` runs per column, where a checklist is shown**: the open filter pane computes its column's values, and an exclusion chip computes its column's (memoized on `exclusionValueKeys`, so ticking a box doesn't rescan rows). It used to run for every filterable column on every `data` change (Solid `createMemo`, React `useMemo`), with no pane open. Rows in a Solid store make each value read a tracked proxy read: 1,197 synthetic rows × 16 string/array columns took 7 ms as plain objects and ~141 ms per rerun from a store (Node with `--conditions=browser`, solid-js 1.9.17, a store read inside a memo); a write to a field no filterable column reads doesn't rerun it.
- **`sortData`'s sort** now precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) instead of recomputing them inside the comparator — see [Filter dropdown](filter-dropdown.md)'s date-sort note above. ~4x faster sorting a `type: 'date'` column at 500k rows.
- A bare `(a,b) => a.price - b.price` sort over a large array of objects is itself costly in V8 (boxed doubles on objects), which library code can't fix; the library's own overhead on top of it can be (see Open leads). An earlier note found numeric sorts ~1.5–2x costlier than string ones, but the bench's string column was nearly pre-sorted then.
- **Search runs after the sort, in its own memo**: `searchData` used to run inside the `processData` memo, so every keystroke re-filtered and re-sorted the whole dataset. Filtering keeps the (stable) sort order, so each adapter now runs `searchData` on the sorted rows in its own memo (see "Sorting is off the search/filter path" below for the full pipeline); a keystroke re-runs only the search. Guarded by each adapter's `recompute.test.ts` (0 `sortData` calls per keystroke).
- **Search reads a per-row index**: `searchData` used to format and normalize every searchable cell of every row on each keystroke (at 200k rows: ~2,400 M instructions and ~147 MB of garbage per keystroke, measured with `perf stat -e instructions:u` and heap deltas). `buildSearchIndex` now does that once, on the first keystroke (~1,700 M instructions), and each later keystroke is a substring check per row (~115 M instructions, ~0.4 MB). The index is rebuilt when `data` or `columns` change, dropped when the query is cleared, and holds ~25 MB at 200k rows while searching. It is built inside each adapter's memo, so Vue/Solid track the cells it reads: a row edited in place or a `value` reading a signal rebuilds it (guarded by "an active search sees reactive changes" in their state tests).
- **React persistence writes only when the view changes**: `usePersistedView`/`useUrlView`'s save effects had no dependency array, so every render (a focus move, a selection click, a parent re-render) wrote `localStorage` and called `history.replaceState`. They're now keyed on the encoded view (`getViewState()` returns a new object each render, and inline `columns`/`initialViewState` would defeat a memoized one). Guarded by `persistence.test.ts`'s "persistence writes".
- **A Solid group toggle groups once**: `group.toggle` set `sorts` from inside `setGroupBy`'s updater, so grouping (`groupData`, `getVisibleRows`) and persistence ran once per signal; both now change in one `batch`. React's equivalent nested `setSorts` regroups twice only when another update is already pending in the same event (React then runs the updater at render time); the huge-dataset demo groups in the same time as Vue's, so it's left as is. Guarded by `recompute.test.ts`.
- **`groupData` has a fast path for scalar rows**: it used to build per-row combo arrays (`flatMap`, spread, `join`) even for one plain group-by value. A row whose group-by values are all non-arrays now goes straight to its bucket key, and `keyParts` is built only for a new group; array values keep the fan-out path. At 200k rows grouped by one column: 746 M → ~190 M instructions, 185 → 45 MB allocated.
- `groupData`/`getVisibleRows` scale linearly. Revisit if a future use case needs `pageSize: 0` (unpaginated) on a huge dataset, which would shift the bottleneck to DOM size instead.
- **The filter dropdown's checklist is a DOM-rendering cost, not a `packages/core` pure-function one** — the benchmark suite above doesn't exercise it, since it's specific to how many DOM nodes each adapter mounts, not to any core computation. A column with thousands of distinct values (a customer name, an order ID) used to mount one `<label>` per value regardless of scroll position; see "The flat checklist is virtualized" under [Filter dropdown](filter-dropdown.md) for the fix (windowed rendering via `computeVirtualRange`).
- **`filterData`'s include/exclude filter passes used to be O(rows × filter-set size × row-values length)**: each row's own filter check spread the column's `filters`/`excludeFilters` `Set` to an array and called `.includes()` on it against the row's (usually length-1) values, instead of the other way around. Correct, but invisible at the small filter-set sizes an include/exclude checklist realistically reached under the old tri-state model (a handful of manually-clicked values) — until Solid's checked-by-default checklist (see [Filter dropdown](filter-dropdown.md)) made a multi-thousand-value `excludeFilters` entry a single click away (select-all, or "Others," on a column with thousands of distinct values). Reproduced on the huge-dataset demo: a select-all click on a ~2,000-value column took **~1000ms** end to end (found by profiling with `console.time` around `toggleExcludeAll`'s state update, `computeStringValueCounts`, and the checklist's own memos — all fast; the cost was the _reactive_ `processedData` recompute the state change triggered). Fixed by flipping the iteration to walk the row's own (small) values array and do an O(1) `Set.has` against the filter set, dropping the same click to ~100ms. Guarded by correctness tests in `logic.test.ts` (large include/exclude/"and"-mode sets) and a `logic.bench.ts` case (`large exclude/include set (2,000 values) on a high-cardinality column`) rather than a timing assertion in the regular suite, which would be flaky in CI.
- **`normalizeForSearch` skips NFD + regex for printable ASCII** (just `toLowerCase`): `searchData` over 500k rows ~1.7x faster (3 queries: 1579 → 949 ms, plain-Node A/B). A per-row `WeakMap` cache of the normalized text measured ~3.5–5x faster once warm, but rejected: a row mutated in place (Vue/Solid reactive data) would keep matching its old text. The search index above avoids that by living in the adapter's memo instead of across calls.
- **Sorting is off the search/filter path**: every adapter sorts the full data in its own memo (`sortData`), then searches and filters the sorted rows (`filterData`), and `sortWithinGroups` skips the ungrouped case, which used to re-sort every row a second time. One search keystroke with a sort active, 500k rows, plain-Node A/B: 1751 → 477 ms (number sort), 1914 → 300 ms (string sort), same rows in the same order — but for a query matching every row (`cate` on `Category N`): the old pipeline searched first, so once a query narrows it only sorted the few matching rows (see the browser measurements below). Trade-off: a sort or data change sorts all rows, not just the filtered ones (see Open leads).
- **Filter value lists as lazy getters, superseded** by the per-column `computeStringValues` above: a getter per column in `filter.valueMap` gave the same mount saving (371 → ~0 ms at 500k rows, `npm run bench:ab`), at the cost of a read-only map in the public state and an adapter memo per column.
- **Browser measurements of the two changes above**, taken before the search index and per-pane value lists replaced parts of them (2026-10-30, 200k-row `#huge-dataset`, demos built for production and served with `vite preview`, `ad32721` vs `d82d348` interleaved over 3 rounds through `scripts/ux-step.mjs --run`; event → next frame, ms):

  | Interaction                                | React       | Vue         | Solid       |
  | ------------------------------------------ | ----------- | ----------- | ----------- |
  | Mount (scroll into view → rows)            | 322 → 227   | 368 → 336   | 472 → 375   |
  | Keystroke `e` (matches most rows), sorted  | 243 → 213   | 220 → 87    | 289 → 113   |
  | Keystrokes `em`…`emma` (narrowing), sorted | ~160 → ~140 | ~155 → ~135 | ~175 → ~145 |
  | Sort click, no filter                      | ~195 → ~157 | ~198 → ~140 | ~203 → ~154 |
  | Sort click, narrow filter (`Emma Smith`)   | ~17 → ~185  | 16 → ~136   | ~16 → ~146  |
  | Open the Customer pane (~2,000 values)     | 18 → 40     | 98 → 37     | 25 → 49     |

  The method (a synthetic `input` event, timed to the next frame) suits before/after comparisons, not absolute numbers or comparing adapters: timed with real keystrokes and the Event Timing API (what INP uses), all three adapters take ~100 ms for `e` and ~150 ms per narrowing keystroke once warm, the narrowing ones costing more because `searchData` then checks every searchable cell of every row.

- **Search has its own memo**, between `sortData` and `filterData`: with a query active, a filter click no longer re-runs `searchData` over every row, saving one search pass (at 500k rows in `npm run bench:ab`'s `search` scenario: ~180 ms before the search index, ~50 ms with it; not measured in the browser).
- **Incremental search while typing, rejected**: when the new normalized query contains the previous one, searching only the previous matches is exact. Before the search index, it would have stopped reading the other rows' cells, so Vue/Solid would no longer see a row edited in place start matching, and a React-only version breaks adapter parity. With the index, a keystroke is already one substring check per row (~115 M instructions at 200k rows), so the remaining gain doesn't pay for the extra state.
- **Vitest bench is too noisy above 100k rows for a < 2x change**: the ASCII fast path above showed as slower at 500k in it. Use `npm run bench:ab -- [ref]` instead (`scripts/bench-ab.mjs`): it imports `logic.ts` at `ref` (default `HEAD`) and in the working tree into one Node process, checks both return the same result, and times them interleaved over the scenarios in `packages/core/src/__tests__/ab.scenarios.ts` (median and min–max). An A/A run (no changes) at 500k rows stays within ±2%.

## Open leads

Measured 2026-10-30 at 500k bench rows in plain Node (`npm run bench:ab`; Vitest bench inflates absolute times ~2.5x). Delete an entry once fixed.

- **Grouped mode still re-sorts per keystroke**: with `groupBy` and a non-group sort active, `sortWithinGroups` re-sorts every group's rows on each `processedData` change (~160 ms of a ~550 ms keystroke at 500k), though they arrive in order. The cost is `sortRows`' decorate pass, not the sort (TimSort is linear on sorted input): an "already in order?" check after decorating only gained 5% (554 → 527 ms). Skipping the decorate pass needs a proof that every row in a bucket ties on the groupBy keys' sort entries, and bucket keys (`String(value)`) don't imply that: a `type: 'number'` column buckets `null` (0) with `undefined` (NaN), and a custom `compare` can split equal strings.
- **A sort or data change with a narrow filter now sorts the full data** (the trade-off above): 23 → 755 ms per sort click with a ~1% filter. Same for each `data` update (polling, `setData`) and, in React, each render with an inline `columns` array.
- **`setViewState` always passes a fresh `sorts` array**, so restoring a view that only changes a filter still re-sorts the full data. Keep the previous array when its entries are equal.
- **String sort is the slowest sort**: ~700 ms at 500k random names (`npm run bench:ab`), from `defaultCompare`'s `localeCompare` per comparison. A shared `Intl.Collator`'s `compare` is _slower_ (1052 vs 698 ms on Node 24): V8 already caches the default collator and has a one-byte fast path in `localeCompare`.
- **Numeric/date `sortRows` is ~2x a bare sort**: 480 ms vs 250 ms for `(a, b) => a.price - b.price` on the same rows, 130 ms for an index array sorted against a `Float64Array`. Overhead: a `values` array per decorated row, `compareFns[i]` + `applyDir` per comparison.
- **Unpaginated (`pageSize: 0`) huge datasets** shift the cost to DOM size: rows aren't virtualized. Unmeasured.

From a 2026-10 review: the huge-dataset demos (200k rows, production builds) driven by Playwright with Event Timing, core functions measured with `perf stat -e instructions:u` and heap deltas, and recompute counts from spied core functions.

- **Identity churn reruns the pipeline**: React's `columns` argument, Vue's options object and Solid's options accessor are memo dependencies (Vue/Solid through the labels object rebuilt from options). A consumer passing them inline (a new array/object on each parent render) reruns filter + sort + grouping on every parent update, ~one sort's cost (210–310 ms at 200k rows). Solid reruns even when the accessor returns the same object.
- **Number and date sorts cost more than string sorts on the demo data** (unlike the random names above): at 200k rows, a number or date sort is 1,350–1,590 M instructions and ~90 MB allocated, against ~320 M and 32 MB for a string sort.
- **Reactive row data slows the pipeline**: sorting 50k rows held in a Vue deep `ref` took ~2.4× as long as from a `shallowRef`, and from a Solid store ~3.6× as long as plain objects (one same-process timing ratio each).
- **Opening a high-cardinality checklist is slower in Solid**: opening the Customer values (~2,000 distinct) takes ~104 ms in Solid and vanilla against ~40 ms in React and Vue.
- **Solid and vanilla trail React and Vue by 10–40%** on sort, search and grouping, and hold ~4 MB more heap after mounting the 200k-row table (38 against 34 MB).
- No leak found: 40 dropdown open/close cycles and 20 remount and data-replacement cycles grow neither DOM nodes nor listeners; the remaining heap growth is V8 compiled code (heap snapshot diff).
