# Performance

Given pagination, the DOM only ever renders `pageSize` rows regardless of dataset size — so for huge datasets (100k–1M+ rows), the cost lives entirely in `packages/core`'s pure functions, which run over the _full_ dataset on every relevant state change (sort, filter, search, group), not just the visible page.

- **Benchmarks**: `packages/core/src/__tests__/logic.bench.ts` (`npm run bench -w packages/core`, or `npx vitest bench --reporter=verbose` from `packages/core` — the default reporter prints no results table) uses Vitest's `bench` test fixture against synthetic datasets at 10k/100k/500k rows (`bench-utils.ts`: 7 columns — string, number, date, and a 20-value low-cardinality category — generated with a seeded PRNG for stable runs). It covers `filterData`/`sortData` (plain/filtered/sorted, per column type), `searchData`, `groupData`/`getVisibleRows`/`paginateVisibleGroups`, `computeStringValues`/`computeStringValueCounts` (all-columns vs. single-column), and `computeDateTree`. There's no CI regression gate on these yet — they're a manual profiling tool, run before/after a perf-sensitive change to check the actual impact rather than guessing.
- **`computeStringValueCounts` was the single biggest cost found**: ~15–17x faster at 500k rows/7 columns when scoped to one column via `targetKeys` instead of every filterable column — see [Filter dropdown](filter-dropdown.md) for the fix (removed `stringValueCounts` from React/Vue's `useTableState` entirely; Solid scopes it to `activeCol()` inside `FilterDropdown.tsx`'s `stringValueCounts` memo, and vanilla inherits that).
- **`sortData`'s sort** now precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) instead of recomputing them inside the comparator — see [Filter dropdown](filter-dropdown.md)'s date-sort note above. ~4x faster sorting a `type: 'date'` column at 500k rows.
- A bare `(a,b) => a.price - b.price` sort over a large array of objects is itself costly in V8 (boxed doubles on objects), which library code can't fix; the library's own overhead on top of it can be (see Open leads). An earlier note found numeric sorts ~1.5–2x costlier than string ones, but the bench's string column was nearly pre-sorted then.
- `groupData`/`getVisibleRows` scale linearly and stay well under the cost of a full re-sort even at 500k rows. Global search (`searchData`) does not: see Open leads.
- **The filter dropdown's checklist is a DOM-rendering cost, not a `packages/core` pure-function one** — the benchmark suite above doesn't exercise it, since it's specific to how many DOM nodes each adapter mounts, not to any core computation. A column with thousands of distinct values (a customer name, an order ID) used to mount one `<label>` per value regardless of scroll position; see "The flat checklist is virtualized" under [Filter dropdown](filter-dropdown.md) for the fix (windowed rendering via `computeVirtualRange`).
- **`filterData`'s include/exclude filter passes used to be O(rows × filter-set size × row-values length)**: each row's own filter check spread the column's `filters`/`excludeFilters` `Set` to an array and called `.includes()` on it against the row's (usually length-1) values, instead of the other way around. Correct, but invisible at the small filter-set sizes an include/exclude checklist realistically reached under the old tri-state model (a handful of manually-clicked values) — until Solid's checked-by-default checklist (see [Filter dropdown](filter-dropdown.md)) made a multi-thousand-value `excludeFilters` entry a single click away (select-all, or "Others," on a column with thousands of distinct values). Reproduced on the huge-dataset demo: a select-all click on a ~2,000-value column took **~1000ms** end to end (found by profiling with `console.time` around `toggleExcludeAll`'s state update, `computeStringValueCounts`, and the checklist's own memos — all fast; the cost was the _reactive_ `processedData` recompute the state change triggered). Fixed by flipping the iteration to walk the row's own (small) values array and do an O(1) `Set.has` against the filter set, dropping the same click to ~100ms. Guarded by correctness tests in `logic.test.ts` (large include/exclude/"and"-mode sets) and a `logic.bench.ts` case (`large exclude/include set (2,000 values) on a high-cardinality column`) rather than a timing assertion in the regular suite, which would be flaky in CI.
- **`normalizeForSearch` skips NFD + regex for printable ASCII** (just `toLowerCase`): `searchData` over 500k rows ~1.7x faster (3 queries: 1579 → 949 ms, plain-Node A/B). A per-row `WeakMap` cache of the normalized text measured ~3.5–5x faster once warm, but rejected: a row mutated in place (Vue/Solid reactive data) would keep matching its old text.
- **Sorting is off the search/filter path**: every adapter sorts the full data in its own memo (`sortData`), then searches and filters the sorted rows (`filterData`), and `sortWithinGroups` skips the ungrouped case, which used to re-sort every row a second time. One search keystroke with a sort active, 500k rows, plain-Node A/B: 1751 → 477 ms (number sort), 1914 → 300 ms (string sort), same rows in the same order — but for a query matching every row (`cate` on `Category N`): the old pipeline searched first, so once a query narrows it only sorted the few matching rows (see the browser measurements below). Trade-off: a sort or data change sorts all rows, not just the filtered ones (see Open leads).
- **Filter value lists are computed per column on first read**: `computeStringValues` returns getters, so mounting a table or replacing its data no longer builds every filterable column's sorted distinct values (React/Solid did it eagerly, Vue on first pane open): 371 → ~0 ms at 500k rows (`npm run bench:ab`), and reading every column costs the same as before (370 ms). Opening a pane now pays for its column (see the browser measurements below). Vue/Solid wrap each column in their own `computed`/`createMemo`, so a column still tracks what its `value` reads.
- **Browser measurements of the two changes above** (2026-10-30, 200k-row `#huge-dataset`, demos built for production and served with `vite preview`, `ad32721` vs `d82d348` interleaved over 3 rounds through `scripts/ux-step.mjs --run`; event → next frame, ms):

  | Interaction                                | React       | Vue         | Solid       |
  | ------------------------------------------ | ----------- | ----------- | ----------- |
  | Mount (scroll into view → rows)            | 322 → 227   | 368 → 336   | 472 → 375   |
  | Keystroke `e` (matches most rows), sorted  | 243 → 213   | 220 → 87    | 289 → 113   |
  | Keystrokes `em`…`emma` (narrowing), sorted | ~160 → ~140 | ~155 → ~135 | ~175 → ~145 |
  | Sort click, no filter                      | ~195 → ~157 | ~198 → ~140 | ~203 → ~154 |
  | Sort click, narrow filter (`Emma Smith`)   | ~17 → ~185  | 16 → ~136   | ~16 → ~146  |
  | Open the Customer pane (~2,000 values)     | 18 → 40     | 98 → 37     | 25 → 49     |

  The method (a synthetic `input` event, timed to the next frame) suits before/after comparisons, not absolute numbers or comparing adapters: timed with real keystrokes and the Event Timing API (what INP uses), all three adapters take ~100 ms for `e` and ~150 ms per narrowing keystroke once warm, the narrowing ones costing more because `searchData` then checks every searchable cell of every row.

- **Search has its own memo**, between `sortData` and `filterData`: with a query active, a filter click no longer re-runs `searchData` over every row, saving one full search pass (~180 ms at 500k rows in `npm run bench:ab`'s `search` scenarios; not measured in the browser).
- **Incremental search while typing, rejected**: when the new normalized query contains the previous one, searching only the previous matches is exact, and would cut the ~150 ms narrowing keystroke. But it stops reading the other rows, so Vue/Solid would no longer see a row edited in place (deep-reactive rows, a `value`/`format` reading a signal) start matching, the same reason as the per-row cache above; only React could take it safely, and a React-only optimization breaks adapter parity for a modest gain.
- **Vitest bench is too noisy above 100k rows for a < 2x change**: the ASCII fast path above showed as slower at 500k in it. Use `npm run bench:ab -- [ref]` instead (`scripts/bench-ab.mjs`): it imports `logic.ts` at `ref` (default `HEAD`) and in the working tree into one Node process, checks both return the same result, and times them interleaved over the scenarios in `packages/core/src/__tests__/ab.scenarios.ts` (median and min–max). An A/A run (no changes) at 500k rows stays within ±2%.

## Open leads

Measured 2026-10-30 at 500k bench rows in plain Node (`npm run bench:ab`; Vitest bench inflates absolute times ~2.5x). Delete an entry once fixed.

- **Grouped mode still re-sorts per keystroke**: with `groupBy` and a non-group sort active, `sortWithinGroups` re-sorts every group's rows on each `processedData` change (~160 ms of a ~550 ms keystroke at 500k), though they arrive in order. The cost is `sortRows`' decorate pass, not the sort (TimSort is linear on sorted input): an "already in order?" check after decorating only gained 5% (554 → 527 ms). Skipping the decorate pass needs a proof that every row in a bucket ties on the groupBy keys' sort entries, and bucket keys (`String(value)`) don't imply that: a `type: 'number'` column buckets `null` (0) with `undefined` (NaN), and a custom `compare` can split equal strings.
- **A sort or data change with a narrow filter now sorts the full data** (the trade-off above): 23 → 755 ms per sort click with a ~1% filter. Same for each `data` update (polling, `setData`) and, in React, each render with an inline `columns` array.
- **`setViewState` always passes a fresh `sorts` array**, so restoring a view that only changes a filter still re-sorts the full data. Keep the previous array when its entries are equal.
- **String sort is the slowest sort**: ~700 ms at 500k random names (`npm run bench:ab`), from `defaultCompare`'s `localeCompare` per comparison. A shared `Intl.Collator`'s `compare` is _slower_ (1052 vs 698 ms on Node 24): V8 already caches the default collator and has a one-byte fast path in `localeCompare`.
- **Numeric/date `sortRows` is ~2x a bare sort**: 480 ms vs 250 ms for `(a, b) => a.price - b.price` on the same rows, 130 ms for an index array sorted against a `Float64Array`. Overhead: a `values` array per decorated row, `compareFns[i]` + `applyDir` per comparison.
- **Unpaginated (`pageSize: 0`) huge datasets** shift the cost to DOM size: rows aren't virtualized. Unmeasured.
