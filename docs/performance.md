# Performance

Given pagination, the DOM only ever renders `pageSize` rows regardless of dataset size — so for huge datasets (100k–1M+ rows), the cost lives entirely in `packages/core`'s pure functions, which run over the _full_ dataset on every relevant state change (sort, filter, search, group), not just the visible page.

- **Benchmarks**: `packages/core/src/__tests__/logic.bench.ts` (`npm run bench -w packages/core`, or `npx vitest bench --reporter=verbose` from `packages/core` — the default reporter prints no results table) uses Vitest's `bench` test fixture against synthetic datasets at 10k/100k/500k rows (`bench-utils.ts`: 7 columns — string, number, date, and a 20-value low-cardinality category — generated with a seeded PRNG for stable runs). It covers `processData` (plain/filtered/sorted, per column type), `searchData`, `groupData`/`getVisibleRows`/`paginateVisibleGroups`, `computeStringValues`/`computeStringValueCounts` (all-columns vs. single-column), and `computeDateTree`. There's no CI regression gate on these yet — they're a manual profiling tool, run before/after a perf-sensitive change to check the actual impact rather than guessing.
- **`computeStringValueCounts` was the single biggest cost found**: ~15–17x faster at 500k rows/7 columns when scoped to one column via `targetKeys` instead of every filterable column — see [Filter dropdown](filter-dropdown.md) for the fix (removed `stringValueCounts` from React/Vue's `useTableState` entirely; Solid scopes it to `activeCol()` inside `FilterDropdown.tsx`'s `stringValueCounts` memo, and vanilla inherits that).
- **`computeStringValues` runs per column, where a checklist is shown**: the open filter pane computes its column's values, and an exclusion chip computes its column's (memoized on `exclusionValueKeys`, so ticking a box doesn't rescan rows). It used to run for every filterable column on every `data` change (Solid `createMemo`, React `useMemo`), with no pane open. Rows in a Solid store make each value read a tracked proxy read: 1,197 synthetic rows × 16 string/array columns took 7 ms as plain objects and ~141 ms per rerun from a store (Node with `--conditions=browser`, solid-js 1.9.17, a store read inside a memo); a write to a field no filterable column reads doesn't rerun it.
- **`processData`'s sort** now precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) instead of recomputing them inside the comparator — see [Filter dropdown](filter-dropdown.md)'s date-sort note above. ~4x faster sorting a `type: 'date'` column at 500k rows.
- Sorting a plain numeric column is inherently ~1.5–2x costlier than sorting an equivalent string column in V8 for large arrays of objects (reproduced with a bare `(a,b) => a.price - b.price` comparator outside any library code) — this is a JS-runtime characteristic of comparing boxed doubles on objects, not something fixable in library code, so it isn't a benchmark target.
- **Search runs after the sort, in its own memo**: `searchData` used to run inside the `processData` memo, so every keystroke re-filtered and re-sorted the whole dataset. Filtering keeps the (stable) sort order, so each adapter now memoizes `processData` (filters + sort) separately and runs `searchData` on its output; a keystroke re-runs only the search. Guarded by each adapter's `recompute.test.ts` (0 `processData` calls per keystroke).
- `groupData`/`getVisibleRows` scale linearly. Revisit if a future use case needs `pageSize: 0` (unpaginated) on a huge dataset, which would shift the bottleneck to DOM size instead.
- **The filter dropdown's checklist is a DOM-rendering cost, not a `packages/core` pure-function one** — the benchmark suite above doesn't exercise it, since it's specific to how many DOM nodes each adapter mounts, not to any core computation. A column with thousands of distinct values (a customer name, an order ID) used to mount one `<label>` per value regardless of scroll position; see "The flat checklist is virtualized" under [Filter dropdown](filter-dropdown.md) for the fix (windowed rendering via `computeVirtualRange`).
- **`processData`'s include/exclude filter passes used to be O(rows × filter-set size × row-values length)**: each row's own filter check spread the column's `filters`/`excludeFilters` `Set` to an array and called `.includes()` on it against the row's (usually length-1) values, instead of the other way around. Correct, but invisible at the small filter-set sizes an include/exclude checklist realistically reached under the old tri-state model (a handful of manually-clicked values) — until Solid's checked-by-default checklist (see [Filter dropdown](filter-dropdown.md)) made a multi-thousand-value `excludeFilters` entry a single click away (select-all, or "Others," on a column with thousands of distinct values). Reproduced on the huge-dataset demo: a select-all click on a ~2,000-value column took **~1000ms** end to end (found by profiling with `console.time` around `toggleExcludeAll`'s state update, `computeStringValueCounts`, and the checklist's own memos — all fast; the cost was the _reactive_ `processData` recompute the state change triggered). Fixed by flipping the iteration to walk the row's own (small) values array and do an O(1) `Set.has` against the filter set, dropping the same click to ~100ms. Guarded by correctness tests in `logic.test.ts` (large include/exclude/"and"-mode sets) and a `logic.bench.ts` case (`large exclude/include set (2,000 values) on a high-cardinality column`) rather than a timing assertion in the regular suite, which would be flaky in CI.
