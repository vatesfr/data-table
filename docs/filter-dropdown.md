# Filter dropdown

Originally a flat list — one section header + checkbox list per string column, stacked in a single scrolling box — which became unusable for high-cardinality columns (hundreds of checkboxes; see GitHub issue #8). Now a master-detail layout:

- **Left pane** lists every filterable column, string/numeric/date unified: `filterableCols = columns.filter(c => c.filterable !== false)`, in column order. A dot indicator marks a column with an active filter.
- **Right pane** shows the selected column's controls — a search input + checklist for string columns, min/max range inputs for numeric columns, a Year › Month › Day tree for date columns (see below). Selected column defaults to the first filterable column (`filterActiveKey` falls back to `filterableCols[0]?.key`) so the detail pane is never empty on open.
- `filterActiveCol` (selected column) and `filterSearchTerms` (per-column search term) are local, ephemeral UI state — `useState`/`ref` in React/Vue, `createSignal`s in Solid (`activeKey`/`searchTerms` in `packages/solid/src/components/FilterDropdown.tsx`, vanilla inheriting them through the Solid wrapper) — same category as `openDropdown`/`dragColKey`: never touches `filters`/`TableViewState`, not persisted or shared.
- `filterValuesBySearch(values, term)` (core) narrows a checklist by case-insensitive substring, called with the active column's `stringValueMap[col.key]` and its search term. No count threshold gates the search input's visibility — because only one column's checklist is shown at a time (not all of them stacked, as before), showing it unconditionally isn't visual noise the way it would've been in the old flat layout.
- A **select-all checkbox** sits on the same row as the search input — no visible label (to save vertical space in an already dense dropdown), accessible via `title`/`aria-label` (`L.selectAll`) instead. It toggles every value _currently listed_, i.e. post-search-narrowing, not the column's full value set: `toggleFilterAll(filters, key, values)` (core) deselects all given values if any is selected, else selects all of them — same clear-if-any-selected convention as row selection's `toggleSelectAll`. Indeterminate when some but not all listed values are selected.
- **Exclude filters** let a checklist value mean "rows without this" instead of just "rows with this" — the only way to narrow a multi-value column (tags) down to rows _lacking_ a value, since a plain include-only checklist can only ever narrow toward a value, never away from one. `filters: Record<string, Set<string>>` stays include-only and unchanged; a parallel `excludeFilters: Record<string, Set<string>>` (same shape, one Set per column) tracks exclusions, kept mutually exclusive with `filters` (a value is never in both at once). A plain click on a checklist value cycles it neutral → include → exclude → neutral via `cycleFilterValue(filters, excludeFilters, key, value)` (core), rendered as a native tri-state checkbox: unchecked, checked, or `indeterminate` (the browser's dash glyph, reused as the "not this" indicator with no extra markup). `processData`'s optional trailing `excludeFilters` param drops a row as soon as it carries _any_ excluded value — a NOR, independent of `col.multiMode` (which only ever governs the include side: "not tagged Action" must exclude the row the moment Action shows up, regardless of how includes combine). `computeStringValueCounts`'s facet counts and `countActiveFilters`'s badge count both take the same optional trailing param, mirroring how they already treat `filters`. Two batch include actions — select-all (`toggleFilterAll`) and shift-range select (`setFilterValues`) — stay include-only and unaware of `excludeFilters` by design (extending shift-range to exclude adds a second direction with no obviously-right UX); a caller that also tracks exclusion calls `clearExcludeValues(excludeFilters, key, values)` (core) alongside them to preserve the mutual-exclusion invariant when values move into `filters`.
  - **The master select-all checkbox** only ever calls `clearExcludeValues` on the "select all ON" branch, where it's unavoidable (every listed value is about to become included, and the invariant means a value can't land in both sets) — the "deselect all" branch calls only `toggleFilterAll` and leaves `excludeFilters` completely alone, since the checkbox's own checked/indeterminate render already reflects `filters` only (no visual concept of exclusion at all) and shouldn't silently clear state it never displayed. This wasn't the original wiring in any adapter — each first called `clearExcludeValues` unconditionally on both branches, which meant clicking an indeterminate select-all checkbox (some values included, unrelated to any excluded ones) silently cleared _every_ listed value's exclusion too, not just the included ones the checkbox was actually showing as selected — the same "action tied to one piece of state silently mutates an unrelated one" shape as the chip bug below.
  - **Each active-bar chip's × clears only the state that chip represents.** A column's include set, exclude set, and range filter (a date column can carry all three) each get their _own_ chip; React/Vue's `clearColumnFilter(key, kind)` takes `kind` (`'include' | 'exclude' | 'range'`, defaulting to `'include'`) as an explicit parameter, and Solid's `table.filter.clearColumn(key, kind)` (`packages/solid/src/createTableState.ts`, called directly from each chip's own `onClick` in `components/ActiveBar.tsx` — one call site per kind, no `data-kind` attribute involved) takes the same shape; vanilla inherits this through the wrapper. This wasn't the original design: the per-column clear action first did an unconditional "full per-column reset regardless of which kind of filter is actually active" (so a date column's range chip and its checklist-tree chip cleared each other too), which read as an acceptable simplification when a column could carry at most an include set _or_ a range filter as alternatives — but once includes and excludes became two states a column can hold at once, clearing one silently dropping the other stopped reading as a reset and started reading as a bug (a real one a user hit — removing a negative filter chip removed the positive filter on the same column, and vice versa).
  - An exclude filter gets its own active-bar chip (`dt-chip--exclude` Solid/vanilla, `chipExclude` React, `.dt__chip--danger` Vue — all backed by the same new `--color-*-danger` theme tokens), distinguished by a "≠" prefix rather than a translated word — the same reasoning the sort/value-sort icons already use symbols instead of growing every locale file. `TableViewState.excludeFilters` persists/shares the same way as `filters` (wire key `x`).
- **Any/all match mode** lets the _user_ flip a multi-value column's checklist between union ("any" of the selected values, the default) and intersection ("all" of them) at runtime — the interactive counterpart to the developer-set `col.multiMode` default (see "Grouped columns"/`ColumnDefBase.multiMode` in the core README), which only ever picks a column's starting mode and has no UI of its own. `filterModes: Record<string, 'and' | 'or'>` (core, alongside `filters`/`excludeFilters`) tracks a per-column runtime override; `setFilterMode(filterModes, key, mode)` sets it directly. `processData`'s optional 8th `filterModes` param resolves each column's mode as `filterModes[key] ?? col?.multiMode ?? 'or'`, so a caller that never passes it gets today's exact `col.multiMode`-only behavior — purely additive. Deliberately per-column, not a single table-wide setting: different multi-value columns (e.g. "Tags" vs "Categories") often want different modes at once, and this mirrors `multiMode` already being a per-column concept.
  - **Only shown for a column whose values are actually array-shaped in the data** — `isMultiValueColumn(data, col, key)` (core) checks whether at least one row's resolved value is an array. A plain scalar column has no meaningful "all" mode (a row can only ever carry one value, so "match all selected values" could never match more than one at a time), so the control is omitted entirely for one rather than rendered disabled.
  - **Rendered as a 2-button segmented "Any"/"All" control, not a single button cycling between them.** A first pass used one button whose label/behavior changed with the current mode (click "Any" to switch to "All", the button then reading "All" and clicking it switches back) — this reads wrong for a genuine two-option choice: only the non-default "All" state ever got a visible "engaged" treatment, which implies "Any" is a passive non-state (nothing selected yet) rather than an equally-real option that merely happens to be the default. Showing both options side by side, with whichever is currently in effect visually engaged (bold + secondary background, same convention as the toolbar's own `.dt-btn--active`) and the other left neutral, reads correctly regardless of which one is active — the same reasoning a two-way segmented control/radio-group always uses over a single toggle button once _both_ sides are meaningful, named states (contrast with the neighboring sort-order button's single-button 4-state cycle, which is fine as a cycle precisely because its states aren't a symmetric either/or choice). `setFilterMode(filterModes, key, mode)` (core) backs this directly — each button's own click handler already knows which mode it wants, so there's no need for a single flip-whatever's-current action the way a cycling button would need. `aria-pressed` on each button reflects whether that particular option is the active one.
  - **Implemented in Solid, React, and Vue** (vanilla gets it for free through the Solid wrapper — see "Vanilla package" in CLAUDE.md), each following the same shape: a `filter.modes`/`filter.setMode(key, mode)` pair alongside `filter.include`/`filter.exclude` in `TableState` (Solid: `createTableState.ts`; React/Vue: `useTableState.ts`), wired into `processData` and `computeStringValueCounts`'s trailing `filterModes` param, and reset by `filter.clear()`/`clearAll()` back to `{}` (a fresh column reverts to its own `col.multiMode` default) the same way `filters`/`excludeFilters` already are. `TableViewState.filterModes` persists/shares the same way as `filters` (wire key `m`, tuples of `[key, andFlag]`). Labels: `L.filterMatchAny`/`L.filterMatchAll` (each button's own visible text and `title`/`aria-label`, matching `col.multiMode`'s own two-word vocabulary rather than inventing new symbols). The two buttons render next to the sort-order toggle — Solid: `.dt-filter-match-mode-group` in `components/FilterDropdown.tsx`'s `FilterSearchRow`; React: a plain `<div>` in `DataTableView.tsx`'s inline JSX (styled via `S.filterMatchMode*`, composed at the call site since `S`'s own object literal can't reference its own other entries); Vue: `.dt__filter-match-mode-group` in `DataTableView.vue`'s single shared search-row template block (gated on `isMultiValueFilterCol`, since that block is reused for both the string checklist and the date tree, unlike Solid/React's dedicated string-only render path) — shown only for the string checklist, never the date tree, which has no array-valued use case today.
    - **`computeStringValueCounts` also takes the optional trailing `filterModes` param**, threaded straight through to its own internal `processData` call — a column's facet counts are computed by narrowing rows via every _other_ active filter (see below), so if one of those other columns is in "all" mode, that must be honored when deciding which rows count toward _this_ column's totals. Missing this initially was a real bug caught during review: toggling some other column to "All" silently left every column's displayed counts computed as if that column were still in its default "any" mode, since nothing had wired the override through.
    - **The sort-order toggle shares `.dt-value-sort-btn` with the match-mode buttons** (an `--active` modifier layered on top for whichever match-mode option is engaged) rather than its own separate style block, so all the buttons in this row sit at identical height/padding/radius. Adding the match-mode control surfaced a latent, unrelated bug where the sort-order button had never actually had `.dt-value-sort-btn` (a real, already-defined class) applied to it at all, leaving it an unstyled default `<button>` that visibly clashed once a properly-styled control sat right next to it. Fixed alongside this feature since it was directly adjacent and made the whole row look broken; also gave that button the `title`/`aria-label={L.sortValues}` React and Vue already set on their own equivalent (Solid's had neither).
  - **Per-adapter wiring quirks, some surfaced by moving from a 2-state toggle to a 3-state cycle:**
    - **React** combines `filters`/`excludeFilters` into one `useState` atom (an object holding both, instead of two independent `useState` calls) — `cycleFilterValue` and the exclude-aware branch of `toggleFilterAll` both need to read _and_ write both maps together to decide the next state, and two independent setters each read from that render's own closure; two such actions called synchronously before a re-render (e.g. back-to-back in the same handler, or in a test's single `act()`) would each compute from the same stale pair otherwise. One atom means one functional updater always sees the latest committed value of both, the same guarantee `toggleFilter`/`setFilterValues` already got for free by only ever touching `filters` alone.
    - **Vue's plain `:checked` binding (no `v-model`) only rewrites the DOM property when the _bound value itself_ changes between renders** — unlike React, which force-syncs a controlled `checked` prop on every commit regardless of whether it changed. The old boolean toggle always flipped `checked` on every click, so this never mattered; but `cycleFilterValue`'s exclude→neutral transition changes `indeterminate` while `checked` stays `false` across both renders, so Vue would skip rewriting `.checked` and leave whatever the browser's own native click-toggle left in the DOM — a real bug hit in testing (a value cycled to neutral kept rendering as checked). `onFilterValueClick` now calls `event.preventDefault()` so the checkbox's visible state is exclusively driven by Vue's own binding, never by the native default action.
    - **Solid** (`packages/solid/src/components/FilterDropdown.tsx`) hits the same race React/Vue each work around, but from a different angle: a tri-state checkbox's click handler calls `e.preventDefault()` to stay controlled, yet a checkbox's native "canceled activation steps" run _after_ the click finishes dispatching, silently reverting `.checked` a moment after Solid's own synchronous write. `applyCheckboxState`/`deferCheckboxCorrection` (`components/checkboxSync.ts`, see CLAUDE.md's "Solid package") solve this generically — a `createEffect` applies the correct `checked`/`indeterminate` pair on every state change, and the click handler additionally calls `deferCheckboxCorrection` right after mutating state to re-apply it from a microtask, scoped to just the clicked element. Vanilla inherits this wiring via the Solid wrapper — the `data-exclude`-attribute-plus-post-render-`indeterminate`-pass and `buildFilterListInnerHtml` described in earlier revisions of this doc no longer exist in `packages/vanilla/src/`; that hand-rolled `innerHTML`-patching implementation was superseded by the Solid extraction.
- The `numericRanges` label was removed — it only existed for the old layout's "Numeric ranges" section header, which the per-column detail pane has no equivalent of.
- Each checklist item shows a row count (see GitHub issue #9), computed by `computeStringValueCounts(data, filters, rangeFilters, columns, emptyLabel, targetKeys?)` (core). It's a _facet_: for a given column, counts are computed over rows narrowed by every _other_ active filter but not that column's own — so ticking a box in one checklist updates the counts shown in another, while a column's own displayed counts stay stable as its own boxes are ticked (unticking one value should never make the others look like they'd match fewer rows than they actually would once unticked). Implemented by re-running `processData` per column with that column's own filter entry deleted from `filters`, then tallying `getColumnValue`/`multiValues` per row. Rendered as a muted, right-aligned `<span>` after the value label (`.dt-filter-count` Solid/vanilla, `.dt__filter-count` Vue, inline style in React) — `aria-hidden` in React since it's a supplementary visual cue, not part of the checkbox's accessible name.
  - Since the master-detail layout only ever renders one column's checklist at a time (`filterDetailCol`/`activeCol`), computing counts for every filterable column on every filter/search change is O(filterableColumns × rows) for O(rows) of actual use — measured as the single largest cost in the library on large datasets (see "Performance" below; ~15–17x at 500k rows/7 columns). `targetKeys` (optional 6th param) restricts which columns counts are actually computed for; `columns` must still be the _full_ list even when narrowing via `targetKeys`, since it's also used to resolve each _other_ active filter's own accessor. Solid's `FilterDropdown.tsx` passes `[col.key]` directly inside a `stringValueCounts` memo (`col` being `activeCol()`, the currently-selected left-pane column, already local to the same component), since it's the one adapter where `filterActiveCol`-equivalent state and the counts computation already live in the same scope; vanilla gets this for free through the Solid wrapper. React/Vue can't do this inside `useTableState` — `filterActiveCol` is UI-only state living in `DataTableView`/`DataTableView.vue`, not in `useTableState` — so `stringValueCounts` was removed from `useTableState`/`TableState<TRow>` entirely and is instead computed via a `useMemo`/`computed` inside the view layer, scoped to `filterDetailCol`, right next to where that state already lives.
- Values with a facet count of 0 are dropped from the checklist entirely, via `filterValuesByCount(values, counts, selected)` (core) — there's no point listing a value that can't currently match any row. The one exception: a value the user already has _selected_ stays listed even at 0, so a filter combination that's narrowed a value out of existence can still be found and unticked from the checklist itself, not just via "Clear filters". `filterValuesByCount` composes with `filterValuesBySearch` at each adapter's single `filterDetailValues`/`filteredValuesFor`/`_filterDetailValues` computation point, so select-all/indeterminate logic (which already operates on "currently listed values") automatically respects the same visibility rule with no separate wiring.
- `type: 'date'` columns get a spreadsheet-style (LibreOffice/Excel autofilter) Year › Month › Day tree instead of a min/max range (see GitHub issue #7) — deliberately chosen over a range so it reuses the exact-match `filters: Record<string, Set<string>>` checklist model rather than adding a second filter-state shape: a date column is simply never excluded from `computeStringValues`/`computeStringValueCounts` (previously gated out alongside `number`), and its checklist values (raw stringified dates, e.g. `"2023-05-14"`) are the tree's leaves. `computeDateTree(values, emptyLabel, dir, parseDate)` (core) parses each value with `parseDate` (default `(v) => new Date(v).getTime()`, overridable via `col.parseDate` — see below) and groups into nodes keyed by 4-digit year / 0-padded month / 0-padded day, ordering years/months/days ascending or descending per `dir` (default `'asc'`); values that don't parse land under a single trailing `emptyLabel` leaf instead of being dropped (always last, regardless of `dir`). Each node's `values: string[]` is every raw leaf value underneath it (a day node's own values if multiple raw values share a calendar day, rolled up through month/year) — so **no new toggle primitive is needed**: checking/unchecking any node (leaf or branch) is just `toggleFilterAll(filters, key, node.values)`, identical to the existing select-all-currently-listed action. `getDateTreeNodeState(node, selected)` (core) derives checked/unchecked/indeterminate from how many of `node.values` are selected, and `sumDateTreeNodeCount(node, counts)` (core) rolls up issue #9's per-value facet counts the same way. The tree is built from the column's already search/count-narrowed flat value list (`filterValuesByCount(filterValuesBySearch(...))`, same pipeline as the flat checklist) rather than the full unfiltered value set — so search and the 0-count-hides-the-value rule prune whole branches for free, with no separate tree-search function. Expand/collapse (`expandedDateNodes`, keyed by column then node `path`) is local ephemeral UI state, same category as `filterActiveCol`; a node with an active search term for its column is force-expanded regardless of click history, since the already-narrowed list is small enough to show in full. Each of React, Vue, and Solid renders the tree recursively — React: a local recursive function (no hooks inside, so no new component needed); Vue: `components/DateTreeItem.vue`, self-importing itself for recursion (safer across build setups than relying on filename-based self-reference) and duplicating the small set of scoped-CSS classes it needs, since a child SFC's `<style scoped>` doesn't inherit the parent's scope id; Solid: `packages/solid/src/components/DateTreeItem.tsx`, likewise self-importing for recursion (mirroring Vue's own reasoning), calling `props.onToggleNode`/`props.onToggleExpand` callbacks up to `FilterDropdown.tsx` (which owns `findDateTreeNode(nodes, path)` (core) and the anchor/expanded state) rather than reading `data-path` off a DOM event the way vanilla's old hand-rolled `render()`-based string-building implementation did — that vanilla code predates the Solid extraction and no longer exists in `packages/vanilla/src/`, which now inherits `DateTreeItem.tsx` through the Solid wrapper. The expand arrow sits inside the same `<label>` as the node's checkbox in all three of React/Vue/Solid; toggling it calls `preventDefault()`/stops propagation before the click reaches the label, otherwise the browser's native label→control forwarding would also fire the checkbox's own toggle. React's/Solid's `renderFilterLabel` and Vue's `#filter-{key}` slot (custom per-value label rendering; vanilla gets `renderFilterLabel` for free since it renders through Solid's same `FilterDropdown.tsx`) are **not** applied to date-tree nodes — both are built around one raw checklist value, but a tree branch's label (a year/month) isn't a raw value at all, and even a day leaf's `values` can bundle more than one. Selecting many leaves at once (e.g. a whole year in one click) can put far more values into `filters[key]` than a user manually ticking checkboxes ever would, so the toolbar's active-filters chip caps its value list at 3 (`FILTER_CHIP_MAX`, one per adapter) and appends `L.moreValues(n)` for the rest — otherwise a fully-selected year would dump ~365 comma-joined ISO dates into one chip.
- **Sorting a `type: 'date'` column** (clicking its header, not the filter tree's own sort-order toggle below) parses values the same way as the filter tree instead of comparing them as plain strings (see GitHub issue #10) — `processData`'s sort calls the same `parseDate` (default/override) used by `computeDateTree`/`selectDateRange`, falling back to string comparison if either side fails to parse. `ColumnDefBase.parseDate?: (value: string) => number` lets a column override the default `(v) => new Date(v).getTime()` for formats `new Date` guesses wrong (e.g. `DD/MM` read as `MM/DD`); it's the single source of truth threaded through all three date-aware functions so the header sort and the filter tree never disagree on chronological order for the same column again. `processData`'s sort precomputes each row's comparable value(s) once before sorting (decorate-sort-undecorate) rather than calling `getComparableValue` from inside the comparator — a comparator re-derives both sides on every comparison, so without this a `type: 'date'` column reparses the same row's date string O(n log n) times during a large sort instead of O(n); benchmarked at ~4x faster for a date-sorted 500k-row column (see "Performance" below).
- The same bug shape existed for `type: 'number'` columns: sort only compared numerically when the raw value was already a JS `number` (`typeof va === 'number'`), so a numeric _string_ (e.g. `"1200"`, common with CSV/JSON-sourced data) silently fell back to alphabetical comparison — while the range filter (`Number(rangeValue(r))`) and `computeAggregate` (`Number(getColumnValue(col, r))`) already coerced correctly, so sort alone disagreed. Fixed by a shared `getComparableValue(col, row)` (core, not exported) that centralizes "what does this column's value mean as a comparable" in one place instead of every call site re-guessing from the raw value's runtime type: `'date'` → `parseDate`, `'number'` → `Number`, anything else (untyped/computed columns) → the raw value unchanged, so a plain numeric column with no `type` set still sorts correctly off its already-numeric raw value. `processData`'s sort is now a single branch (`typeof va === 'number' && !isNaN(va) && ...` → numeric, else string), used for both `'number'` and `'date'` alike. `computeAggregate`'s existing `Number(...)` coercion was deliberately left as-is rather than routed through `getComparableValue` — it already coerces unconditionally regardless of `col.type` (so numeric aggregates were never actually buggy), and routing a `'date'` column through `getComparableValue` there would return a raw epoch number instead of `NaN`, changing `min`/`max` to return a number that a `col.format` written for the original string date wouldn't expect — a behavior change nobody asked for, not a fix.
- A **sort-order toggle** sits next to the search input (string/date columns only — numeric columns have no checklist to sort). For string columns it cycles a `ValueSort` (core type: `{ by: 'alpha' | 'count', dir: SortDir }`) through alpha-asc → alpha-desc → count-desc → count-asc → alpha-asc via `cycleValueSort` (core); `sortFilterValues(values, counts, sort)` (core) applies it as the last step of each adapter's `filterDetailValues`/`filteredValuesFor`/`_filterDetailValues` pipeline, after search/count-narrowing. For date columns the same button only toggles chronological direction via `toggleSortDir` (core), passed straight through as `computeDateTree`'s `dir` param — there's no count-based order for a tree of grouped branches, so `by` never applies there. `getValueSortIcon`/`getDateSortIcon` (core) render the button's compact label (e.g. `"ABC ↑"`, `"# ↓"`, or a bare `"↑"`/`"↓"` for dates). Per-column sort mode (`filterValueSort: Record<string, ValueSort>`) is ephemeral UI state, same category as `filterActiveCol`/`filterSearchTerms` — not part of `filters`/`TableViewState`, defaulting to `{ by: 'alpha', dir: 'asc' }` (matching `computeStringValues`'s existing default order) whenever a column has no entry yet — overridable per column via `ColumnDefBase.defaultValueSort?: ValueSort` (e.g. `{ by: 'count', dir: 'desc' }` for a high-cardinality tag column that reads better "most common first", or `{ dir: 'desc' }` for a date column's tree to open most-recent-year-first). `cycleValueSort` itself needs no change — it's a fixed 4-state rotation, not asymmetric like `toggleSort`'s 3-state one (see "Header click sorting"'s `defaultSortDir`), so a custom starting point still advances through all 4 states the same way. Each adapter's single `valueSortFor`/`findCol`-equivalent fallback point (`filterValueSort[key] ?? DEFAULT_VALUE_SORT`) becomes `filterValueSort[key] ?? columns.find(c => c.key === key)?.defaultValueSort ?? DEFAULT_VALUE_SORT` — the only call site that needed to change in each of the three adapters.
- **Shift-click range selection** works the same way as table rows (see "Row selection" above), for both the flat checklist and the date tree. Each adapter keeps a per-column anchor (`filterSelectionAnchor: Record<string, string>`, ephemeral UI state living alongside `filterActiveCol`/`filterSearchTerms` — the same dict serves both checklist values and date-tree node `path`s, since a column is never both types at once) and, on shift-click, applies `selectRange(filterDetailValues, anchor, value)` (core) against the column's already search/count/sort-narrowed value list. Unlike `toggleFilterAll`'s clear-if-any-selected convention, the direction here always mirrors what a plain click on the target value would do, so it needs its own core primitive: `setFilterValues(filters, key, values, selected)` sets `values` to `selected` unconditionally rather than deriving the direction from the whole group's state. Filter checkboxes read the modifier off `onClick`/`@click` (React/Vue), the same event Solid's `handleValueClick`/`handleDateNodeToggle` read `(e as MouseEvent).shiftKey` from in their own `onClick` handlers, with vanilla inheriting Solid's wiring — never `onChange`/`@change`, same reasoning as row selection.
- **Date tree range selection** is a chronological interval, not a sweep over rendered tree rows — the year/month/day grouping is purely a _display_ concern, layered on top of the same flat-list range-selection idea used elsewhere, just re-expressed in terms of dates instead of list positions. A rendered-row sweep (ranging across whatever's visually between the anchor and target, like the row/checklist cases) would be wrong here: a branch node's own `values` already roll up _every_ descendant date, so merely crossing an expanded year's row would pull in that whole year — including dates chronologically after the target (e.g. ranging `2023-02` → `2024-06` must never select `2024-07`, even though the `2024` year row sits "between" them once expanded). `selectDateRange(allValues, anchorNode, targetNode, parseDate)` (core) instead spans the earliest-to-latest raw value across both nodes' own `values` (parsed via the same `parseDate`, default/override shared with `computeDateTree`) and returns every value in the column's flat `allValues` list that parses into that interval — regardless of which branch it's grouped under, and independent of expand/collapse state entirely. `anchorNode`/`targetNode` can each be a leaf (day) or a branch (year/month): a branch endpoint's own min/max simply widens the interval to that whole unit (e.g. anchoring on a year spans its earliest to latest date). The anchor is still tracked as a `path` string (in the same per-column `filterSelectionAnchor` dict as the flat checklist), re-resolved to a node via `findDateTreeNode` on the next click, since node objects themselves are recreated every render. The select-vs-deselect direction mirrors what a plain click on the _target_ node would do — `getDateTreeNodeState(node, selected) !== 'checked'` — the same "clicked node's own new state" rule used for the flat checklist and for rows. Vue wires this by having `DateTreeItem.vue` emit `toggleNode: [node, event]` (rather than just `values: string[]`) so the parent `DataTableView.vue` (which alone holds `filterSelectionAnchor`) can decide plain-toggle vs range; Solid's `DateTreeItem.tsx` takes the same shape as a plain callback prop instead of an emit (`onToggleNode: (node: DateTreeNode, shiftKey: boolean) => void`), since it's a separate component from `FilterDropdown.tsx` (which alone holds the anchor signals) the same way Vue's is separate from `DataTableView.vue` — architecturally the same reasoning as Vue's emit, just Solid's own idiom for a child-to-parent callback. React already had direct access to both from within the same render/handler scope (its date-tree renderer is a local recursive function, not a separate component — see above), so no signature change was needed there; vanilla inherits Solid's callback-prop wiring through the wrapper.
- **The flat checklist is virtualized in React and Vue** (windowed rendering) — a column with thousands of distinct values (e.g. a customer name) would otherwise mount one `<label>`/`<input>` per value regardless of how many are actually scrolled into view, which is a real perf cliff distinct from (and on top of) the facet-count cost above. `computeVirtualRange(scrollTop, viewportHeight, itemHeight, totalCount, overscan?)` (core) is pure, fixed-row-height windowing math — given how far a list is scrolled, it returns which item indices should actually be mounted (`startIndex`/`endIndex`, padded by `overscan` rows each side to avoid a blank flash on fast scroll), the pixel `offsetY` to position that window at, and the `totalHeight` so the real scrollbar still reports the full list's size. React/Vue render the checklist as a scrollable container — a spacer `<div>` sized to `totalHeight`, and an absolutely-positioned inner `<div>` at `offsetY` holding only `values.slice(startIndex, endIndex)` — each row given an explicit `FILTER_LIST_ITEM_HEIGHT` (32px) inline/bound height so it matches what the math assumes exactly, rather than relying on the existing checklist item style's padding + line-height to happen to add up right. This is scoped to the flat checklist only — the date tree (see above) is naturally already "virtualized" in spirit by being collapsed/hierarchical by default, so it was left alone. Select-all, indeterminate, and shift-range selection all continue to operate on the _full_ (unwindowed) `filterDetailValues`/`filteredValuesFor` array — virtualization only changes what's mounted, never what's considered "currently listed" for those operations, so a fully-selected 50,000-value column still shows as `50000 / 50000 rows` even though only ~20 checkboxes were ever in the DOM.
  - **Solid's flat checklist is virtualized too**, at parity with React/Vue (vanilla inherits it through the Solid wrapper): `FilterDropdown.tsx` has its own `scrollTop` signal (updated on `.dt-filter-list`'s `onScroll`, reset to 0 via an effect keyed on the active column/search term, same trigger React/Vue use) and a `filterListVirtualRange` memo wrapping the same `computeVirtualRange` — a spacer `<div>` sized to `totalHeight`, an absolutely-positioned inner `<div>` at `offsetY`, and `<For each={filterDetailValues().slice(startIndex, endIndex)}>` for the actual rows, each given an explicit `FILTER_LIST_ITEM_HEIGHT` inline height like React's own. The scroll-then-focus dance for Up/Down/Home/End (`focusChecklistIndex`) calls core's `getVirtualScrollTarget` (see "Row-nav page-boundary crossing" and the shared-helpers note in `docs/keyboard-navigation.md` — the same function React/Vue's own equivalent logic was refactored onto) to decide the scroll adjustment, then sets `scrollTop`/focuses the target value **synchronously**, with no pending-ref/effect indirection — Solid's signal writes update the DOM (including the new window's rows) within the same call stack, unlike React's `useLayoutEffect`/Vue's `nextTick`. Select-all/indeterminate/shift-range selection are unaffected, since they already operate on the full `filterDetailValues()` array regardless of what's mounted.
  - **The checklist/date-tree viewport fills the panel's real height instead of a hardcoded constant** (GitHub issues #13/#14) — `.dt-filter-cols` (the column list on the left) and `.dt-filter-detail` (the checklist/date-tree side) are flex row siblings in `.dt-filter-panel`, so a `.dt-filter-cols` taller than the old 260px default stretches `.dt-filter-detail` with it via the flex row's cross-axis stretch; a checklist left at a hardcoded height then left dead space below it (#13), and the date tree — which had no height/scroll bound of its own at all — instead overflowed past the panel onto the page (#14). `.dt-filter-panel` also gained `overflow:hidden` in React, Vue, and Solid as a safety net regardless, since `max-height` alone doesn't clip (vanilla inherits Solid's `.dt-filter-panel` rule as-is).
    - **React/Vue/Solid all fill it via CSS flex** — `filterDetail`/`.dt__filter-detail`/`.dt-filter-detail` became a flex column (`flex:1` on the pane itself, plus `flex-direction:column`) with the checklist and a date-tree wrapper both set to `flex:1; min-height:0; overflow-y:auto` instead of a hardcoded height — so both fill whatever room the detail pane is actually stretched to, with no JS measurement needed in any of the three. For React/Vue specifically, `computeVirtualRange`'s viewport-height argument still passes the `FILTER_LIST_VIEWPORT_HEIGHT` constant (260) unchanged rather than a real measured number — safe here specifically because `.dt-filter-panel`'s own `max-height:380px` bounds how much taller the checklist can ever actually grow past that default (at most ~60-80px, once the search row/padding above it are accounted for), which is comfortably inside the 5-row/160px overscan `computeVirtualRange` already renders on each side — so the virtualized window always has enough pre-rendered rows to cover the real visible box. React additionally has a second reason it didn't need a JS-measured height: React Compiler's lint rules (`react-hooks/set-state-in-effect`, `react-hooks/refs`, both `error` in `eslint.config.mjs`) rule out the two obvious ways to feed a `useLayoutEffect`-measured height back into a render — calling `setState` from inside the effect, or reading a ref's value during render. Vue has no such restriction but uses the identical CSS approach anyway, for consistency between the two framework adapters. Solid's own version of this reasoning doesn't apply at all, since Solid's checklist isn't virtualized in the first place (see above) — there's no `computeVirtualRange` call whose viewport-height argument could need justifying.
  - **React**: scroll position is tracked as `filterListScrollTop` state, updated via a `requestAnimationFrame`-throttled `onScroll` handler that reads the live `scrollTop` from `filterListRef.current` at rAF-fire time (not a value captured back in the triggering scroll event — several scroll events can fire before the callback runs, and only the latest position matters). Reset to 0 whenever the checklist's values change identity (switching column, or narrowing by search) — done inline during render (comparing against the previous render's key, React's own documented pattern for this) rather than in a `useEffect`, since the project's `eslint-plugin-react-hooks`/React Compiler config rejects a synchronous `setState` call inside an effect (`react-hooks/set-state-in-effect`) as a cascading-render risk. A _separate_ effect imperatively syncs the DOM's actual `scrollTop` to 0, keyed specifically on that same reset-key (**not** on `filterListScrollTop` itself) — keying it on `filterListScrollTop` instead re-applies a slightly-stale scroll position on every scroll-driven state update (not just on an actual reset), fighting the browser's own live native scroll and making the list appear to not scroll at all (a real bug hit in testing: `list.scrollTop` stayed pinned at 0 across repeated wheel ticks). React's `DataTableView.tsx` otherwise has zero manual `useMemo`/`useCallback` — it relies entirely on the React Compiler for memoization — so `stringValueCounts` and the virtual-range computation are plain `const`s, not wrapped in `useMemo`, to match.
  - **Vue**: same shape as React (a `ref` for scroll position, rAF-throttled `@scroll` reading the live `scrollTop`), but the reset naturally lives in a `watch([filterActiveKey, searchTerm], ...)` callback scoped to exactly those two triggers — Vue has no render-phase-state-update restriction the way React Compiler does, so this never had the "fights live scrolling" bug in the first place.
  - **Solid/vanilla have no equivalent scroll-position-tracking code at all** — this bookkeeping exists only to feed `computeVirtualRange`'s `scrollTop` argument, and Solid's checklist isn't virtualized (see above), so there's nothing for it to drive. The native browser scrollbar on `.dt-filter-list`/`.dt-date-tree-wrap` (both plain `overflow-y:auto`) handles scrolling entirely on its own. Earlier revisions of this doc described a hand-rolled vanilla scroll handler (a capture-phase `scroll` listener patching `buildFilterListInnerHtml`'s output into the DOM) — that code predates the Solid extraction and no longer exists in `packages/vanilla/src/`.
- **`type: 'number'`/`type: 'date'` range filters get a slider alongside their 2 min/max inputs** — a "2 inputs + a slider" control, using the two-native-`<input type="range">`-thumbs-sharing-one-track trick (only the thumb itself is a hit target via CSS/pseudo-elements, so grabbing either one works regardless of z-order) rather than a fully custom drag widget, for free keyboard/touch accessibility and a small per-adapter diff. `computeValueBounds(data, col)` (core) is the slider's own `min`/`max` — the column's actual bounds across the full, unfiltered `data` (`'date'` via `parseDate`, `'number'` via `Number`), deliberately not `processedData`, so the slider's range doesn't shrink out from under a mid-drag user just because some other filter narrowed the row set; returns `null` when no row has a parseable value, in which case the slider is omitted and the two plain inputs keep working alone. Both thumbs share one change handler: the actual applied min/max is always `Math.min`/`Math.max` of both thumbs' live values (not "thumb A is always min"), so dragging one thumb past the other just swaps their visual roles on the next render instead of needing cross-clamping — the standard behavior for this widget trick. A date column's slider works in epoch-ms space (`step` = one day, `86400000`) and converts back to an ISO `YYYY-MM-DD` string (`setRangeFilter`'s existing value shape) on commit.
  - **The two plain min/max inputs default to the column's own data bounds when no range filter is set**, rather than sitting empty — a blank box gives no hint of what range is even meaningful for a given column, and it means the slider's thumbs (which already fell back to `computeValueBounds`) no longer visually disagree with the text inputs next to them. This is purely a display default: `rangeFilters[key]` stays unset until the user actually edits a value, so it doesn't light up the column's filter dot, doesn't add an active-bar chip, and isn't persisted in view state — functionally identical to before, just no longer blank. `formatRangeBound(n, col)` (one per adapter — vanilla/React module-level, Vue a `<script setup>` function, Solid its own small module, `packages/solid/src/components/formatRangeBound.ts`, shared by `FilterDropdown.tsx` and `RangeSlider.tsx`) converts a bound (epoch ms for `'date'`, a plain number otherwise) back into the string shape `RangeFilter.min`/`.max` expects; it replaces what used to be an inline `fmt` closure duplicated between the slider's drag and commit handlers, and is now also the one place both the inputs' default value and the slider's `onChange`/`onInput` go through. Each adapter computes the column's bounds once per render (vanilla/React: a plain `computeValueBounds` call passed into the slider-building function as a parameter instead of it recomputing internally; Vue: a `filterDetailBounds` computed, with `rangeSliderFor` taking it as a parameter the same way; Solid: a `bounds` memo in `FilterDropdown.tsx`, passed as a `bounds` prop into `RangeSlider.tsx`) so the number/date detail pane's two consumers of "this column's bounds" — the inputs' default and the slider itself — never compute it twice.
  - **For a `type: 'date'` column, the range filter narrows the Year › Month › Day tree itself** ("runs before the tree"), not merely an independent filter ANDed onto the final row set — same idea as the existing search box, one step earlier in the same pipeline. `filterValuesByRange(values, range, parseDate)` (core) is `filterValuesBySearch`'s sibling: given the column's flat value list and its `rangeFilters` entry, it drops every value outside `[min, max]` (parsed via `parseDate`; a value that fails to parse is dropped whenever a bound is active, same "not part of any chronological range" reasoning as `selectDateRange`) — a no-op when the range has no bounds set, and safe to call unconditionally for every column type since a string/number column never populates `rangeFilters` in the first place. Each adapter's `filterDetailValues`/`filteredValuesFor`/`_filterDetailValues` pipeline calls it between `filterValuesBySearch` and `filterValuesByCount`, so both the flat leaf list and the tree built from it (`computeDateTree`) shrink together. `computeStringValueCounts`'s existing facet-count exclusion (own checklist filter excluded, but never `rangeFilters` — see above) already meant a column's own range filter was never excluded from its own counts either, so the tree's per-leaf counts narrow along with the visible leaves with no core change needed there.
  - `processData`'s range-filter loop is now type-aware instead of always coercing via `Number(...)`: a `type: 'date'` `rangeFilters` entry parses each row's value with `col.parseDate ?? defaultParseDate` (matching sort/tree), but always parses the _bounds themselves_ with the default ISO parser regardless of `col.parseDate` — the bounds are always `YYYY-MM-DD` from the range filter's native `<input type="date">`s, a fixed format the column's own custom parser (built for its own raw value format, e.g. `DD/MM/YYYY`) isn't meant to read. Every other column type keeps the original `Number(...)` behavior, unchanged.
  - **Vanilla's old hand-rolled implementation was the one adapter that couldn't just fire a full `render()` on every slider `input` tick** — that code predates the Solid extraction and no longer exists in `packages/vanilla/src/`. `render()` rebuilt the whole filter panel via `innerHTML`, and replacing the thumb `<input>` the mouse had mid-drag would abort the native drag (same reasoning column header drag-and-drop already avoided `render()` until `drop`, and the filter-list scroll handler avoided it entirely — see above), so the old slider's `data-action="range-slider"` split across `input` (patching only the fill `<div>`'s `left`/`right` inline style, no state write) and `change` (where `rangeFilters` actually updated and `render()` ran). React, Vue, and now Solid (`packages/solid/src/components/RangeSlider.tsx`) don't need this split at all — reconciling a controlled input's `value` prop on a state-driven re-render/re-run updates the same DOM node in place rather than destroying and recreating it, so a native drag's pointer capture is never disturbed; all three just call the equivalent of `setRangeFilter`/`table.filter.setRange` on every `input`/`@input`/`onInput` tick, identical to how the plain min/max text inputs already work. `RangeSlider.tsx`'s own doc comment calls this out explicitly as a simplification Solid's migration got for free, the same one React/Vue's own equivalents already had. Vanilla inherits this controlled-input behavior through the Solid wrapper.
  - **React has no stylesheet mechanism at all otherwise** (see "Cross-package resolution", the whole package is styled via inline `style` objects) — but a properly-styled thumb (round handle, hidden default track) needs `::-webkit-slider-thumb`/`::-moz-range-thumb`, pseudo-elements no inline `style` prop can reach. `ensureRangeSliderStyles()` injects one small, idempotent `<style data-dt-range-slider-styles>` tag into `<head>` on first mount (from a `useEffect`, so it never runs during SSR) — the same "inject once into `<head>`" precedent the old vanilla adapter used for its whole stylesheet before the Solid extraction. Vue needs no such exception — `DataTableView.vue`'s existing `<style scoped>` block (and a sibling `components/RangeSlider.vue`, mirroring `DateTreeItem.vue`'s existing self-contained-component pattern) can declare the same pseudo-element rules directly, the way `.dt__tr--clickable:hover` already does elsewhere in this file. Solid needs no exception either, for the same reason as Vue: `packages/solid/src/styles.ts` (the one CSS string `injectStyles()` puts into `<head>` once, per CLAUDE.md's "Solid package") declares `.dt-range-slider-thumb::-webkit-slider-thumb`/`::-moz-range-thumb` directly alongside every other rule — vanilla gets these rules for free by bundling that same stylesheet.
